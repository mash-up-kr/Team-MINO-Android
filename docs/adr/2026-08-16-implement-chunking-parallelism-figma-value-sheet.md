# mino-implement는 배정을 잘게 쪼개 병렬로 돌리고, Figma 값은 착수 시점에 한 번만 추출해 공유한다

- **상태**: Accepted
- **작성일**: 2026-08-16
- **작성자**: Jaesung Lee

## 컨텍스트

[SDD Implement 단계는 오케스트레이터 + 전문가 서브에이전트로 실행한다](2026-08-09-implement-agent-orchestration.md)는 마지막에 이렇게 남겼다 — *"실행 실적이 없는 상태의 결정이다. 첫 적용에서 배정 단위나 동시 3종 제한이 실제와 어긋나면 이 기록을 갱신한다."*

이제 실적이 생겼다. 2026-08-13 `group-room-form` 기능(45개 작업)을 이 구조로 완주시켰고, 그 세션 트랜스크립트를 계측했다. 결론은 **구조는 맞았지만 배정 방식이 틀렸다**는 것이다.

### 무슨 일이 있었나 — 실측치

| 항목 | 값 |
|---|---|
| 전체 소요 (wall clock) | **136분** (그중 21분은 시스템 절전으로 인한 중단) |
| 서브에이전트 호출 | 25건 / 9종 |
| 서브에이전트 실행 시간 합 | 191분 → **병렬도 1.4배** |
| └ 모델이 생각하고 쓰는 시간 | 148분 (**77%**) |
| └ 툴 응답을 기다린 시간 | 43분 (Figma 31.6 · Gradle 6.1 · 나머지 5) |
| 출력 토큰 | 리드 390k + 전문가 520k = **910k** |
| 서브에이전트 툴 호출 | 1,046회 |
| **컨텍스트 재읽기 총량** | **117.9M 토큰** |

### 원인 1 — 시간을 먹는 건 빌드가 아니라 컨텍스트다

가장 오래 걸린 에이전트는 `design-system-builder`(T005–T009)로 **20분·157턴·출력 62.9k**를 썼다. 이 중 Gradle 빌드는 40초다. 전체로 봐도 Gradle은 37콜 6.1분이 전부다.

진짜 원인은 **컨텍스트가 198k 토큰까지 부풀어 오른 상태로 157턴을 돌았다**는 것이다. LLM은 매 턴마다 그때까지의 대화 전부를 다시 읽는다. Figma 응답 하나, Gradle 로그 하나가 컨텍스트에 얹히면 그 뒤 100턴 내내 계속 실린다. 실행 전체의 컨텍스트 재읽기가 117.9M에 달한 이유이고, 뒤로 갈수록 느려지는 이유다.

**작업 5개를 한 에이전트에 몰아준 것이 20분짜리 병목을 만들었다.** 같은 에이전트가 나중에 작업 2개만 받았을 때는 8.6분, 10.5분에 끝났다.

### 원인 2 — 병렬 구조인데 실제로는 거의 직렬로 돌았다

에이전트가 하나라도 돌던 134.5분을 동시 실행 개수로 쪼개 보면:

| 동시 실행 | 시간 | 비중 |
|---|---|---|
| 0개 | 14.0분 | 10.4% |
| **1개** | **58.0분** | **43.2%** |
| 2개 | 54.4분 | 40.5% |
| 3개 | 8.1분 | 6.0% |

절반이 넘는 시간을 한 명 이하로 돌았고, 3개 동시는 마지막 게이트에서 딱 한 번 8분뿐이었다. SKILL.md가 정한 "한 번에 최대 3종" 상한은 **걸리지도 않았다.**

원인은 둘이다.

1. **상한이 "3종"이라 같은 종을 여러 개 못 띄우는 것처럼 읽힌다.** `ui-developer`는 9번 호출됐는데 전부 순차였다.
2. **"다음 단계로 넘어가기 전에 각 단계를 완료한다"는 규칙을 Phase 배리어로 해석했다.** 20분짜리 한 명이 끝날 때까지 나머지가 놀았다. 검수도 마찬가지여서, 55분에 시작한 재검수가 끝난 뒤에야 68분에 다음 화면 작업이 시작됐다 — 검수자는 코드를 고치지 않으므로 겹쳐 돌려도 충돌하지 않는데도 그랬다.

### 원인 3 — 같은 Figma 노드를 여러 에이전트가 각자 다시 판다

Figma 호출 285회를 뜯어보면:

- 고유 노드는 **106개**, 고유 (툴, 노드) 조합은 174개
- 중복 111회 중 **한 에이전트 안에서의 중복은 34회뿐**, 나머지 **77회가 에이전트 경계를 넘은 중복**
- 106개 노드 중 **39개(37%)를 두 명 이상이 각자 조회**했다

즉 문제는 "한 에이전트가 까먹고 다시 부른다"가 아니라 **`ui-developer` → `design-system-builder` → `design-auditor`가 같은 노드를 처음부터 다시 판다**는 것이다. 출발점은 `context-analyst`다. 이 분석가는 0.9분·5k 만에 끝나는데, **노드 ID 표만 만들고 값은 하나도 뽑지 않기** 때문이다.

그리고 이 중복은 대기 시간(31.6분)보다 **컨텍스트를 무겁게 만드는 비용**이 더 크다. `get_design_context` 응답은 크고, 한 번 들어오면 그 에이전트의 남은 턴 전부에 실린다.

### 원인 4 — 검수는 제 역할을 했는데, 재작업이 뒤에 몰렸다

`design-auditor`는 4번 돌아 40.4분을 썼고 실제로 위반을 잡아냈다. 문제는 그게 **Phase가 끝난 뒤**여서, 지적을 받은 시점에는 이미 만들어 놓은 것을 다시 만들어야 했다는 점이다. 재배정으로 나간 시간이 약 40분(칩 10.5 · T005 위반 8.6 · Modifier 17.8 · 기타)이다.

근본 원인은 **구현자와 검수자가 같은 노드를 서로 다른 절차로 본다**는 데 있다. 구현자는 `figma-design-fidelity.md` §3(구조 확보)을 따르고, 검수자는 §4(변수 전수 대조)를 따른다. 구현자가 전수 값을 안 보고 만들었으니 검수자가 잡아내는 건 당연한 결과다.

### 원인 5 — 리드가 단일 최대 생성자다

리드 혼자 실행 구간에 **390k**를 냈다. 전문가 상위 3종을 합친 것과 맞먹는다. 전문가 보고를 받을 때마다 표와 산문 요약을 새로 쓰는 패턴이 25번 반복됐다.

SKILL.md는 "보고는 리드가 파싱할 한 줄"이라는 계약을 **전문가에게만** 건다. §범위 가드가 "전문가에게 거는 제약은 리드에게도 적용된다"고 적어 두긴 했지만, 출력 형식은 그 목록에 없다.

## 결정

`mino-implement`의 실행 구조(리드 허브 · 피어 통신 금지 · 게이트의 수정 권한 박탈)는 그대로 두고, **배정 방식과 Figma 데이터 흐름을 아래 다섯 가지로 바꾼다.**

### 1. 배정 단위를 쪼개고 동시 실행 상한을 인스턴스 기준으로 바꾼다

- **한 배정이 건드리는 서로 다른 파일은 최대 3개**다. 세는 단위는 작업이 아니라 파일이며, 같은 파일을 건드리는 작업은 개수와 무관하게 한 배정으로 묶는다. 파일이 3개를 넘으면 쪼개서 여러 인스턴스에 나눈다. **지적이 확정된 기계적 수정의 재배정에는 이 상한을 적용하지 않는다** — 무엇을 어떻게 고칠지가 이미 정해진 수정은 파일 수만큼 컨텍스트를 늘리지 않기 때문이다. 판정이 남아 있는 재작업은 예외가 아니다.
  - **2026-08-18 개정.** 최초 문안은 *"한 번의 배정에 넣는 작업은 최대 3개"* 였다. [Round 2](../measurements/2026-08-17-implement-round2.md)에서 이 상한이 **같은 파일을 여러 배정으로 쪼개는 원인**으로 드러났고(파일 8개가 작업 22개로 갈려 링크 14개가 사슬에 얹혔다), 세는 단위를 파일로 바꾼 [Round 3](../measurements/2026-08-18-implement-round3.md)이 효과를 확인했다(배정당 파일 2.9 → 2.0 · 배정 링크 70 → 61). 상한의 목적인 **컨텍스트 억제는 파일 수가 더 정확히 대리한다** — 같은 파일에 걸린 작업 4개가 컨텍스트를 4배로 만들지 않는다. 예외 조항은 Round 3의 상한 초과 2건이 전부 판정이 끝난 기계적 수정이었던 관측을 규칙으로 옮긴 것이다.
- "한 번에 최대 3**종**" → **"동시 최대 5 인스턴스"**. 같은 종의 인스턴스를 여러 개 띄우는 것을 명시적으로 허용하고, 조건은 **파일 경로가 겹치지 않을 것** 하나로 한다.

### 2. Phase 배리어를 작업 의존성 배리어로 바꾼다

- 기다리는 기준은 Phase가 아니라 **선행 산출물을 실제로 쓰는지 여부**다. 같은 Phase라는 이유로 기다리지 않는다.
- **검수 대기 중에 다음 작업을 착수한다.** 게이트 3종은 코드를 고치지 않으므로 겹쳐 돌아도 충돌하지 않는다.

### 3. Figma 값 시트를 착수 시점에 한 번만 만든다

- `context-analyst`의 역할을 **노드 ID 표 → 값 시트 산출**로 확장한다. Figma 읽기 도구와 `Write` 권한을 준다.
- 산출물은 스크래치패드에 두는 파일이며, `figma-design-fidelity.md` §4가 요구하는 대조 항목 — 노드별 변수 전수 + 변수 없는 실측 치수 + 스크린샷 경로 — 을 그대로 담는다.
  - **2026-08-18 개정.** 최초 문안은 포맷을 *"스크래치패드 JSON … 노드 ID 표기를 정규화해 키로 쓴다"* 로 못 박았다. 시트에 무엇이 어떤 형식으로 담기는지는 [`context-analyst` 정의](../../.claude/agents/context-analyst.md)가 단일 출처이며, 이 ADR은 **착수 시점에 한 번만 뽑아 파일로 공유한다**는 결정까지만 갖는다.
- 노드 추출은 서로 독립적이므로 **추출 인스턴스 3~5개를 병렬로** 띄운다.
- 구현자(`ui-developer` · `design-system-builder`)는 **값을 시트에서 먼저 읽는다.**
  - **2026-08-18 개정.** 최초 문안은 여기서 *"값 조회 도구는 회수한다"* 까지 정했다. 회수는 시트 품질을 확인한 뒤의 2단계였고, 아래 §결과에서 **가지 않기로 확정**했다 — 조회 도구는 시트가 틀렸을 때의 안전망이자 시트의 구멍을 드러내는 장치로 남는다. 구현자가 시트를 두고 원본을 다시 열면 그 사유를 보고에 적는다(`sheet-miss`).
- **`design-auditor`의 도구는 그대로 둔다.** 검수자는 계속 원본을 직접 연다.

### 4. 검수는 깎지 않고, 검수에 걸릴 일 자체를 줄인다

- **시점 규정의 상태**: Superseded by [디자인 검수는 Phase 종료가 아니라 컴포넌트가 완성되는 즉시 붙인다](2026-08-18-design-audit-at-component-completion.md). 아래 둘째 줄이 대체 대상이며, 첫째 줄(값 시트 선점)은 유효하다.

- 구현자가 §4 전수 기준의 값 시트를 처음부터 쥐고 시작하게 해서 위반 발생을 줄인다.
- 검수 시점은 Phase 종료를 유지하되, 위 2번으로 **크리티컬 패스에서 빼낸다.**

### 5. 리드의 출력 계약을 SKILL.md에 명시한다

- 리드가 산문을 쓰는 지점은 셋뿐이다 — **게이트 판정 · 사용자 질문 · 최종 완료 보고.**
- 그 사이 진행 상황은 전문가 보고 줄을 **그대로 전달**하고 재작성하지 않는다. 진행 상태는 TodoWrite가 이미 들고 있으므로 중복 서술하지 않는다.

### 부수 조치

- 진행 로그를 작업당 `start`/`done` 2줄 → **`done`·`blocked`·`failed`만** 1줄로 줄인다(echo 58콜의 절반).
- `context-analyst` 브리프에 **선행 작업이 만든 파일의 정확한 경로** 칸을 추가한다. Bash 탐색 218콜(grep 67 · ls/find 58 · cat 22 · sed 13)의 상당수가 경로를 몰라서 헤맨 것이다.
- 실행 착수 절차에 `caffeinate` 권고를 넣고, 리드가 **무응답 에이전트를 감지해 재배정**하는 규칙을 추가한다. 이번 실행에서 절전으로 21분과 출력 0토큰짜리 실패 에이전트 1건이 날아갔다.

## 근거

- **시간의 정체가 컨텍스트 길이이므로, 컨텍스트를 짧게 유지하는 것이 곧 시간 단축이다.** 생성 시간이 전체의 77%이고 그 생성 속도를 좌우하는 게 컨텍스트 길이다. 배정을 쪼개면 각 에이전트의 컨텍스트가 짧게 유지되고, 동시에 병렬로 겹칠 수 있다. 한 번에 두 가지가 해결된다.
- **병렬도를 올리는 것이 단일 최대 레버다.** 실행 시간 합 191분은 그대로여도 병렬도가 1.4배 → 2.5배가 되면 wall clock은 절반이 된다. 그리고 지금 병렬도가 낮은 이유는 자원 제약이 아니라 **규칙의 문구**다 — 상한에 걸린 적이 한 번도 없다.
- **값 시트는 원시 호출 수를 줄이는 게 아니라 컨텍스트 오염과 재작업을 줄인다.** 값 시트를 만드는 데도 결국 174번의 조회가 필요하므로 Figma 호출 총량 자체는 크게 안 준다. 얻는 것은 셋이다 — ① 무거운 원본 응답이 구현자 컨텍스트에 안 쌓인다, ② 이 조회가 실행 앞단에서 **병렬로 한꺼번에** 끝난다(값싼 분석가가, 비싼 구현자 대신), ③ 구현자가 검수 기준과 같은 데이터를 갖고 시작하므로 위반이 줄어든다.
- **값 시트는 헌법 원칙 I과 충돌하지 않는다.** 이슈 #150은 "브리프를 늘려 재작업을 줄이는 방향은 원칙 I(규약 본문을 브리프에 옮겨 적지 않는다)과 충돌할 수 있다"고 우려했다. 시트가 옮기는 것은 **규약 본문이 아니라 Figma 원본 데이터**다. 규약은 여전히 경로로만 지목하고 전문가가 작업 시점에 읽는다.
- **검수자의 독립 재조회는 품질의 마지막 방어선이라 손대지 않는다.** [2026-08-09 ADR](2026-08-09-implement-agent-orchestration.md)이 정한 "검증 주체와 구현 주체가 같으면 자기 산출물을 통과시킨다"가 그대로 적용된다. `design-auditor.md`의 "구현자가 낸 대조 보고를 판정 근거로 삼지 않는다"도 유지한다. 속도는 검수를 깎아서가 아니라 **검수에 걸릴 일을 줄여서** 얻는다.
- **리드 출력 계약은 이미 있던 원칙을 문장으로 옮기는 것뿐이다.** §범위 가드가 "전문가 제약은 리드에게도 적용된다"고 이미 선언했다. 출력 형식만 그 목록에서 빠져 있었다.

## 결과

### 목표 수치

아래는 같은 규모(45개 작업)의 기능 1건 기준이며, **개선 전은 실측, 목표는 추정**이다. 검증은 이슈 [#150](https://github.com/mash-up-kr/Team-MINO-Android/issues/150)의 완료 조건대로 실행 트랜스크립트를 같은 방법으로 계측해서 했고, **Round 3에서 닫았다**(아래 [§검증](#검증)). 라운드별 실측치와 판정은 계측 기록이 소유한다.

| 지표 | 개선 전 (실측) | 목표 | 근거 |
|---|---|---|---|
| wall clock | 136분 | **대기 제외 70분 이하** — 사용자 대기를 포함한 값을 병기한다 | 사슬 단축 — 검수 위치·파일 단위 배정·값 시트 |
| **코드 배정** 병렬도 | — | 유지 확인 (Round 3 1.82) | 코드 가동 구간이 wall clock의 하한이다 |
| 최대 단일 에이전트 | 20.1분 / 157턴 | 8분 이하 | 배정 파일 수 상한 3개 + 값 시트 |
| **구현자** 피크 컨텍스트 | 198k | 100k 이하 | Figma 원본이 구현자에 안 쌓임 |
| 게이트 피크 컨텍스트 | — | 100k 이하 | Gradle 출력을 통째로 싣지 않는다 |
| 리드 출력 토큰 | 390k | **배정당 브리프 3,000자 이하** | 출력 계약 |
| Figma 중복 — **구현자↔구현자** | 77회에 포함 | **0회** | 값 시트 |
| Figma 중복 — **에이전트 내부** | 34회 | **0회** | 이미 조회한 노드를 다시 부르지 않는다 |
| `design-auditor` 지적으로 인한 재작업 | 약 40분 | 15분 이하 | 구현자가 전수 값을 선점 |
| `sheet-miss` | Round 3에서 8건 | **시트 사정권 내 0회** | 값 시트 산출 규칙 |

**Round 2까지의 계측으로 네 축을 재산정했다.** 근거는 [Round 3 실행 계획 §지표 재산정](../measurements/2026-08-17-implement-round3-plan.md#지표-재산정)이 소유한다.

- **병렬도 2.5배는 지표에서 뺐다.** 두 라운드가 같은 값(1.96)에서 멈췄고 한계가 `tasks.md` 의존성 그래프임이 확인됐다. 실행 규칙으로 올릴 수 없는 값을 목표로 두면 매 라운드 "미달"만 찍는다. 속도는 **wall clock 하나로** 본다.
- **피크 컨텍스트를 구현자와 게이트로 갈랐다.** Round 2의 최댓값 210.4k 보유자는 Figma를 한 번도 안 부른 품질 게이트(208k)였다. 한 지표에 Gradle 로그 문제와 Figma 문제가 섞여 있어 값 시트가 Gradle 문제로 실패 판정을 받는다.
- **Figma 중복 목표를 갈랐다.** "크로스 0회"는 이 ADR의 설계와 모순된다 — 결정 3이 `design-auditor`의 도구를 유지하기로 했으므로 검수자↔구현자 중복은 구조적으로 남는다(Round 2에서 30회). 값 시트가 없앨 수 있는 것은 **구현자↔구현자**(13회)뿐이다. 대신 **에이전트 내부 중복**을 목표로 올렸다 — 이 ADR이 §원인 3에서 "34회뿐"이라며 기각했으나 Round 2에서 60회(전체 호출의 27%)로 최대 항목이 됐다.
- **리드 출력을 절대량이 아니라 배정당 브리프 분량으로 바꿨다.** 150k는 결정 1(배정 25 → 40건)·부수 조치(브리프에 경로 추가)와 정면으로 충돌하는 목표였다. Round 2 실측은 배정당 3,037자다.

**Round 3 계측으로 네 축을 다시 재산정했다.**

- **wall clock의 판정 기준을 대기 제외로 바꿨다.** Round 2는 사용자 대기 0분, Round 3은 4.3분이라 두 값을 나란히 놓으면 실행 규칙의 효과가 대기 시간에 가려진다. 대기는 규칙이 아니라 노드 개통·검수 판정이 만드는 값이므로 따로 본다.
- **병렬도를 코드 배정 기준으로 되살렸다.** 위에서 뺀 것은 전체 병렬도다. Round 3의 전체 2.64는 검수 병렬화가 만든 숫자이고, 구현 배정의 동시성은 세 라운드(1.70 → 1.75 → 1.82) 정체다. **코드 가동 구간이 wall clock의 하한**이므로 이 축 없이는 다음 라운드부터 줄일 것이 없다.
- **`design-auditor` 지적 건수는 정규화해서 본다.** 작업 수(45 → 47)와 검수 인스턴스 수가 함께 늘어 절대 건수로는 라운드끼리 비교가 안 된다. 트립와이어는 **인스턴스당·작업당**으로 읽는다.
- **`sheet-miss` 목표를 시트 사정권 안으로 좁혔다.** `에셋 export 결과 구조`는 `context-analyst`에 `download_assets`가 없어 **구조적으로 시트에 못 담긴다.** 절대 0회를 목표로 두면 값 시트가 도구 부재로 실패 판정을 받는다.

### 무엇이 바뀌나

- **고치는 파일**: `.claude/skills/mino-implement/SKILL.md`(§5 동시 배정 규칙 · 의존성 배리어 · §에이전트 공통 계약에 리드 출력 계약 추가), `.claude/agents/context-analyst.md`(도구·산출물 확장), `ui-developer.md` · `design-system-builder.md`(값 시트를 먼저 읽도록 규칙 추가 — 조회 도구 회수는 2단계이며 아래 §결과에서 가지 않기로 했다), **`mino-sdd/template/tasks-template.md` · `.claude/skills/mino-task/SKILL.md`**(Phase 배리어 문구를 산출물 의존성 표현으로 교체 — 최초 작성 때 빠졌고 Round 1에서 드러나 반영했다).
- **`design-auditor.md`는 고치지 않는다.** 이 ADR이 성립하려면 검수 기준이 그대로여야 한다.
- **적용 순서를 나눈다.** 1·2·5(SKILL.md만 고침, 위험 낮음)를 먼저 적용해 한 번 돌리고, 3·4(에이전트 계약 변경)는 시트 품질을 확인한 뒤 구현자의 도구를 회수하는 2단계로 간다. 시트가 부실한 채로 도구부터 뺏으면 구현자가 값을 추측하게 되고, 이건 품질이 조용히 무너지는 경로다.
- **새로운 실패 모드가 생긴다** — 값 시트가 실행 단위 캐시이므로, **실행 도중 Figma 원본이 바뀌면 시트가 낡는다.** 시트는 세션 스크래치패드에 두고 실행이 끝나면 버린다. 실행을 이어받는 경우에는 시트를 재사용하지 않고 다시 만든다.
- **동시 4~5 인스턴스는 리드의 대조 부담을 늘린다.** 2026-08-09이 "3종"을 정한 이유가 "리드가 보고를 대조할 수 있는 한도"였다. 보고가 한 줄 형식으로 강제되고 있으므로 5개까지는 감당 가능하다고 보지만, 마킹 누락이나 오배정이 늘면 이 숫자가 첫 번째 되돌릴 대상이다.
- **품질 지표를 함께 본다.** 속도만 보면 검수가 헐거워진 것을 놓친다. 다음 실행에서 `design-auditor` **지적이 늘면 3번이 실패한 것**이고, wall clock만 줄면서 지적이 0에 수렴하면 검수 범위가 좁아진 것을 의심해야 한다. **건수는 인스턴스당·작업당으로 정규화해서 읽는다**(위 §목표 수치).

### 검증

라운드마다 실행 트랜스크립트를 같은 방법으로 계측하고, 조건·실측·판정·후속 과제는 [계측 기록](../measurements/README.md)이 소유한다. 이 ADR은 목표 수치와 그 산정 근거만 갖는다. **계측은 Round 3에서 닫았다** — 세 라운드를 관통한 변화와 남은 과제의 처분은 [종합 기록](../measurements/2026-08-18-implement-summary.md)이 소유한다.

| 라운드 | 조건 | 판정 | 기록 |
|---|---|---|---|
| Round 1 (2026-08-16~17) | 결정 1·2·5만 적용 · 45개 작업 · 사용자 대기 129분 | 7개 목표 중 1개 달성, 리드 출력은 악화 | [계측](../measurements/2026-08-16-implement-round1.md) |
| Round 2 (2026-08-17) | 결정 1·2·5 + Round 1 해소 3건 · 47개 작업 · 사용자 대기 0 | 7개 목표 중 1개 달성, wall clock 78.2분으로 목표에 근접 | [계측](../measurements/2026-08-17-implement-round2.md) |
| Round 3 (2026-08-18) | 결정 1~5 전부 + 검수 위치 이동 · 파일 단위 배정 · 웨이브 선계획 · 내부 중복 금지 · 게이트 로그 · 47개 작업 전건 완료 | 8개 목표 중 1개 달성, 레버 6개 중 4개가 자기 축에서 효과 | [계측](../measurements/2026-08-18-implement-round3.md) |

**Round 3에서 계측을 닫은 근거**는 셋이다 — 실행 규칙이 겨냥한 여섯 레버 중 넷이 자기 축에서 효과를 냈고, wall clock이 목표에 1.9분까지 붙었으며(대기 제외 71.9분), 남은 병목이 **구현자의 절대 속도**로 옮겨 가 이 ADR의 사정권 밖으로 나갔다. 자세한 것은 [종합 기록](../measurements/2026-08-18-implement-summary.md)이 소유한다.

Round 3이 이 ADR에 남긴 것은 셋이다.

- **결정 3(값 시트)은 겨냥한 축을 맞혔다.** 구현자↔구현자 Figma 중복 13 → **0회**, 구현자 Figma 적재 86 → **34콜**. 다만 **2단계(구현자 도구 회수)로 가지 않는다** — 구현자가 시트를 두고 원본을 다시 판 8건의 사유가 시트 산출 규칙의 결함을 가리키므로, 규칙을 먼저 고친다.
- **결정 4의 반전이 검증됐다.** 검수를 컴포넌트 단위로 앞당기자 사슬 안 `design-auditor`가 31.1 → **12.9분**으로 줄었고, 품질 트립와이어(지적 건수 12+1 → **16건**)가 버텼다. 기각 근거였던 "검수 인스턴스가 늘어 비용이 증가한다"는 최장 검수 13.4분/120턴 → 7.2분/35턴으로 반증됐다. **새 ADR로 확정할 사안이다.**
- **"게이트 피크 100k" 축은 다시 갈라야 한다.** 조치 6은 `quality-gate-runner`를 208.2 → **35.4k**로 내렸으나 게이트 피크 보유자가 `constitution-auditor`(212.5k)로 옮겨 갔다. 로그 절삭이 닿지 않는 부하이며, 한 축에 두 문제를 묶은 것이 오류였다.

> **결정 4의 시점 규정은 Round 3에서 반전을 검증 중이다.** 결정 4는 *"검수 시점은 Phase 종료를 유지하되 크리티컬 패스에서 빼낸다"* 인데 두 라운드 다 빼내지 못했다(Round 2에서 사슬 65.5분 중 `design-auditor`가 31.1분). 계측이 가리키는 처방은 **컴포넌트 단위로 앞당기는 것**이며, 이는 아래 §고려한 대안이 기각했던 안이다. 기각 근거("검수 인스턴스가 늘어 Figma 호출과 토큰이 증가한다")는 검수자 시간이 호출량이 아니라 **턴 수**에 걸려 있다는 계측으로 반증됐다.
>
> 그래서 **`SKILL.md`가 이 ADR보다 먼저 바뀐다** — Round 3은 반전된 규칙으로 돌고, 효과와 품질 트립와이어(`design-auditor` 지적 건수)가 함께 확인되면 그때 [`adr-format.md`](../../.claude/skills/adr-writer/adr-format.md)에 따라 **새 ADR로 확정**한다. **그때까지 SKILL.md와 이 ADR의 결정 4가 어긋나는 것은 의도된 상태이며, 규범 위반으로 지적할 대상이 아니다.**
>
> **2026-08-18 확정.** Round 3 계측이 효과(사슬 −18.2분)와 트립와이어(지적 12+1 → 16건)를 함께 확인해 [새 ADR](2026-08-18-design-audit-at-component-completion.md)로 확정했다. **이 어긋남은 해소됐다** — 검수 시점의 단일 출처는 그 ADR이다.

- **병렬도 2.5배는 이 ADR의 오진이다.** "상한에 걸린 적이 없으니 원인은 규칙의 문구"라고 진단했으나, 상한을 5로 올린 두 라운드가 모두 1.96배에서 멈췄다. 실제 한계는 `tasks.md`의 의존성 그래프이며 목표치를 재산정해야 한다.
- **최대 단일 에이전트의 병목은 배정 크기가 아니라 Figma다.** 두 라운드 모두 최장 에이전트가 배정 상한(3개)에 걸리지 않았고, Figma를 만지는 에이전트가 에이전트 시간의 70%대를 차지한다. 결정 1로는 8분에 닿지 않으며, 이는 결정 3을 뒷받침하는 증거다.
- **재작업 감소는 값 시트 없이 달성됐다.** 이 ADR은 그 개선을 "구현자가 전수 값을 선점"에 귀속시켰으나, 실제로는 배정 축소와 검수 파이프라이닝만으로 나왔다. 결정 3·4의 남은 기대 이득은 위 두 축으로 좁혀 평가한다.

## 고려한 대안

- **`design-auditor`의 독립 재조회를 없애고 구현자의 대조 보고를 판정 근거로 쓴다** — Figma 호출 100여 회와 검수 40분이 통째로 사라지는 가장 큰 절감이다. 그러나 구현한 주체가 자기 구현을 통과시키는 구조가 되고, 이 저장소는 디자인 일치를 검사하는 자동 장치가 없어 그 자기검증이 마지막 방어선이다([`figma-design-fidelity.md`](../conventions/figma-design-fidelity.md) §6). 속도를 위해 품질 장치를 끄는 것이라 기각.
- **검수를 Phase 종료가 아니라 컴포넌트 단위로 앞당긴다** (이슈 #150 원안) — 재작업 시점을 앞당기는 정공법이지만, 검수 인스턴스가 컴포넌트 수만큼 늘어 Figma 호출과 토큰이 되레 증가한다. 검수 자체를 앞당기는 대신 **구현자에게 검수 기준 데이터를 선주입**하고 검수는 파이프라인으로 겹치는 쪽을 택했다. 같은 목적을 더 싸게 달성한다.
- **브리프에 규약 본문을 옮겨 적어 위반을 줄인다** — 헌법 원칙 I 위반이고, 규약이 바뀌면 브리프와 문서가 갈라진다. 기각. 대신 규약이 아닌 **Figma 원본 데이터**를 옮기는 값 시트로 대체했다.
- **"같은 노드를 두 번 부르지 마라"를 에이전트 정의에 규칙으로 적는다** — 가장 싸게 시도할 수 있지만, 계측해 보니 한 에이전트 안에서의 중복은 34회뿐이고 나머지 77회가 에이전트 경계를 넘은 중복이다. 각 에이전트는 다른 에이전트가 뭘 조회했는지 알 수 없으므로 프롬프트로는 풀리지 않는다. 기각.
- **배정 상한을 작업 수로 유지하고 같은 파일 작업만 예외로 둔다** — 실측된 상한 초과가 전부 같은 파일 묶음이었으므로 이것으로도 Round 3의 수치는 나온다. 그러나 상한의 목적이 컨텍스트 억제라면 **세는 단위 자체가 틀린 것**이고, 예외를 덧대면 규칙이 목적을 설명하지 못한다. 기각. **재작업에도 상한을 그대로 적용하는 안**도 함께 기각했다 — 7개 파일짜리 기계적 수정이 3개 배정으로 갈리고 그 인계가 전부 완료 검증 꼬리에 얹힌다.
- **Gradle 빌드를 최적화한다** (구성 캐시, 빌드 범위 축소) — 직관적으로 가장 먼저 떠오르는 후보이나, 계측 결과 37콜 6.1분으로 전체의 4.5%다. 최장 단일 빌드도 34초다. 투자 대비 효과가 없어 기각.
- **전문가를 없애고 리드가 직접 구현한다** — [2026-08-09 ADR](2026-08-09-implement-agent-orchestration.md)이 이미 기각한 안이며, 이번 계측은 그 결정을 뒤집을 근거가 되지 못한다. 병렬도가 낮았던 것이지 분업 자체가 손해는 아니었다.
