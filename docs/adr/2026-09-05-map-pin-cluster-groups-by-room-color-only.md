# 지도 핀 클러스터는 같은 방(색)의 핀끼리만 묶는다

- **상태**: Accepted
- **작성일**: 2026-09-05
- **작성자**: Chea-yunzi

## 컨텍스트

PRD([`docs/prd/business-context.md`](../prd/business-context.md) Flow C)는 "지도 축소 시 핀이 겹치는 구간을 클러스터로 묶는다. 1~99개는 `50+`식 숫자 표기, 100개 이상은 `100+` 아이콘"이라고만 정의하고, **서로 다른 방(색)의 핀이 한 클러스터에 섞였을 때 원을 무슨 색으로 그릴지는 명시하지 않았다.**

Figma에서 클러스터 원의 색 견본(node `2392-128633`~`2392-128643`)을 확인해 보니 정확히 `RoomColor`(GRAY 제외) 12색과 1:1로 대응했다 — 즉 클러스터 원도 일반 핀처럼 "그 방의 대표 색"을 쓰는 것으로 보인다. 그런데 이 전제가 성립하려면 클러스터 하나가 **단일 색**이어야 한다 — 여러 방의 핀이 섞인 클러스터는 원 하나로 그릴 색이 없기 때문이다.

## 결정

**클러스터링은 같은 방(정확히는 같은 `MinoRoomColor`)의 핀끼리만 묶는다.** 서로 다른 방의 핀은 화면상 완전히 겹쳐 있어도 클러스터로 합치지 않고 각자 낱개 핀으로 남긴다.

구현은 [`MapPinClustering.kt`](../../feature/room/src/main/java/team/mino/feature/room/main/model/MapPinClustering.kt)의 `toMapPinClusters`가 먼저 `color`로 나눈 뒤 그 안에서만 그리디 반경 클러스터링을 한다.

## 근거

- Figma 클러스터 원 색 견본이 방 색상 팔레트와 정확히 일치해, "클러스터 색 = 방 대표색"이 디자인 의도로 가장 자연스럽다.
- 일반 핀이 이미 "그 방의 대표색"으로 그려지므로(`RoomMapPin`), 클러스터도 같은 규칙을 따르는 편이 사용자에게 "같은 지도, 같은 색 언어"로 일관되게 읽힌다.
- 여러 방 색을 섞는 대안(예: 그라데이션, 다수결 색, 회색 처리)은 Figma에 근거가 전혀 없어 새로 지어내는 것이 되고, 나중에 진짜 디자인이 나오면 다시 갈아엎어야 한다.

## 결과

- 다른 방의 핀들이 지도에서 시각적으로 겹쳐 있어도(예: 같은 건물에 여러 방이 각자 저장한 경우) 클러스터로 묶이지 않고 낱개로 겹쳐 보인다 — 이 경우의 시각적 처리(예: 살짝 벌려 그리기)는 이 결정의 범위 밖이며 별도 이슈다.
- 클러스터 색 팔레트(`RoomMapClusterPinTokens`)는 `RoomColor` 12색과 1:1 유지가 전제다. `RoomColor`에 색이 추가되면 이 토큰도 함께 늘려야 한다.
- 클러스터 원의 정확한 지름·테두리 두께·폰트 크기는 Figma에서 스크린샷 스케일 값만 확인돼(dev-mode px 미확보) 이번 구현은 임의값을 썼다 — 리드 확인 후 별도로 값만 교체하면 된다(이 ADR의 결정 범위에는 포함되지 않는다).

## 고려한 대안

**1. 방 색과 무관하게 화면상 가까운 모든 핀을 하나로 묶는다** — 클러스터링 자체는 더 단순해지지만, 클러스터 원의 색을 무엇으로 그릴지 답이 없다(여러 방이 섞이면 대표색이 없다). Figma 견본이 방 색 팔레트와 정확히 일치한다는 근거와도 어긋난다.

**2. 항상 기본(회색/무채색) 클러스터 색을 쓴다** — 구현이 가장 간단하지만 Figma의 12색 견본을 버리는 선택이라, 이미 확보한 디자인 근거를 무시하게 된다.
