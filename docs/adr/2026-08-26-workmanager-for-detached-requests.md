# 화면보다 오래 살아야 하는 요청은 WorkManager가 소유하고, 재시도 정책을 워커가 든다

- **상태**: Accepted
- **작성일**: 2026-08-26
- **작성자**: Jaesung Lee

## 컨텍스트

외부 공유 수신([`shared-link-receiver` spec](../specs/shared-link-receiver/spec.md), 이슈 #158)에서 처음 마주친 문제다. 이 기능의 요구사항은 서로 당긴다.

- **FR-011**: 저장 완료 토스트가 사라지면 꾹의 화면을 남기지 않고 물러나 외부 앱으로 되돌린다.
- **FR-017**: 링크 분석은 `[저장하기]` 이후에 수행한다. 시트는 분석을 기다리지 않는다.
- **spec §4 가정**: "`저장하기`를 누른 뒤 저장 결과가 확정되기 전에 사용자가 앱을 떠나도 저장 요청은 취소되지 않는다."

즉 **요청이 살아 있어야 하는 구간이 Activity가 살아 있는 구간보다 길다.** `viewModelScope`는 Activity 종료와 함께 취소되므로 마지막 가정을 지킬 수 없다.

진입 특성이 문제를 키운다. 이 화면은 OS 공유 시트에서 곧바로 뜨는 별도 진입점이라([`contracts/share-intent.md`](../specs/shared-link-receiver/contracts/share-intent.md)) **프로세스가 방금 뜬 콜드 스타트가 잦고**, 저장 직후 곧바로 종료된다. 프로세스가 오래 살아 있으리라 기대할 근거가 없다.

EC-009(저장 요청 시점에 네트워크가 끊겨 있다)도 같은 구간에 걸린다. 사용자는 이미 외부 앱으로 돌아간 뒤라 재시도를 지시할 화면이 없다.

서버 계약도 결과를 되물을 수단을 주지 않는다. `POST /api/v1/place/places`는 202로 접수만 확정하고 `pinId`를 돌려주지 않으며, 진행 상태를 조회할 엔드포인트가 없다. 성공·중복·실패는 서버가 알림함으로 사후 전달한다(FR-014·FR-015). 따라서 클라이언트가 보장해야 하는 것은 **"요청을 확실히 전달하는 것"** 하나로 좁혀진다.

## 결정

**화면 수명주기보다 오래 살아야 하는 요청은 WorkManager 워커가 소유한다.** `androidx.work:work-runtime-ktx`와 `androidx.hilt:hilt-work`를 버전 카탈로그에 추가한다.

- 워커는 `:core:data/work/`에 둔다. 워커는 Repository를 호출해 네트워크 요청을 수행하는 데이터 레이어 인프라이며, feature 모듈은 `:core:data`를 의존하지 않는다([`core/data/README.md`](../../core/data/README.md) §10). feature는 도메인 계약 뒤에 감춰진 예약 함수를 호출할 뿐 `WorkManager`를 직접 만지지 않는다.
- **제약과 재시도 정책을 워커가 든다.**
  - `NetworkType.CONNECTED` 제약을 걸어, 오프라인이면 연결이 돌아올 때까지 실행 자체를 미룬다.
  - `MinoDomainException.Network`와 5xx `Http`는 `Result.retry()`로 지수 백오프에 맡긴다.
  - 4xx `Http`는 같은 입력에 같은 응답이 오므로 `Result.failure()`로 즉시 확정한다.
- 워커는 결과를 화면에 돌려주지 않는다. 화면은 이미 없다.

### 기존 재시도 규칙과의 경계

[익명 세션 확보의 재시도·지연 판정은 호출 화면이 소유하고, 데이터 레이어는 멱등한 1회 확보만 제공한다](2026-08-22-session-retry-owned-by-caller.md)와 반대 방향으로 보이지만 뒤집는 것이 아니다. **그 ADR이 성립하는 전제가 여기서는 성립하지 않는다.**

그 결정의 근거는 "재시도는 진입 화면을 벗어났는가로 끝나는데 데이터 레이어는 그 화면의 수명주기를 알지 못한다"였다. 재시도를 소유할 화면이 존재하고, 그 화면이 종료 조건을 안다는 것이 전제다.

이 경우는 **화면이 종료되는 것이 요구사항 자체다**(FR-011). 소유할 주체가 설계상 사라지므로 정책을 화면에 둘 수 없다. 두 결정은 같은 판단 기준의 양쪽 결과다 — 재시도의 종료 조건을 아는 쪽이 정책을 갖는다.

| | 세션 확보 | 화면 분리 요청 |
|---|---|---|
| 재시도 종료 조건 | 진입 화면을 벗어남 | 요청이 서버에 접수됨 |
| 그 조건을 아는 주체 | 화면 | 워커 |
| 정책 소유 | 호출 화면 | 워커 |

## 근거

**프로세스 종료를 견디는 선택지가 이것뿐이다.** Application scope 코루틴(`@Singleton CoroutineScope`)은 Activity 생애주기에서는 벗어나지만 프로세스가 죽으면 함께 사라진다. 공유 수신은 콜드 스타트가 잦고 저장 직후 종료되는 경로라, 시스템이 프로세스를 회수할 여지가 다른 화면보다 크다. 요청 유실이 예외가 아니라 상시 위험이다.

**제약·백오프를 직접 구현하지 않아도 된다.** EC-009를 구제하려면 "연결될 때까지 기다렸다가 보낸다"가 필요한데, 이를 손으로 만들면 네트워크 콜백 구독·백오프 타이머·중복 실행 방지를 전부 떠안는다. WorkManager가 이미 갖고 있는 기능이고, 잘못 만들면 배터리를 태우는 종류의 코드다.

**유실이 조용하지 않다.** 요청이 전달되지 않으면 서버가 알림을 만들 근거도 없어 사용자는 아무 소식도 받지 못한다. 반면 요청만 도달하면 성공·중복·실패 어느 쪽이든 알림함으로 전달된다(UX-007). 클라이언트 쪽 유실을 줄이는 것이 사용자에게 보이는 차이를 만든다.

**4xx를 재시도하지 않는 이유**는 결과가 달라지지 않기 때문이다. `INVALID_INSTAGRAM_URL`·`VALIDATION_ERROR`는 URL이 바뀌지 않는 한 몇 번을 보내도 같은 응답이고, 백오프로 되풀이하면 배터리만 쓴다. 지원하지 않는 URL의 판정은 서버가 소유하므로([`shared-place-save-api.md`](../specs/shared-link-receiver/contracts/shared-place-save-api.md)) 클라이언트가 재해석할 여지도 없다.

## 결과

- **새 의존성이 생긴다.** `androidx.work:work-runtime-ktx`, `androidx.hilt:hilt-work`, 그리고 Hilt 워커 팩토리 설정이 `:app`의 `Application`에 붙는다. `androidx.work:work-testing`이 테스트 의존성으로 따라온다.
- **`:core:data`에 `work/` 패키지가 생긴다.** 이후 백그라운드 작업(알림 예약, 데이터 동기화)도 같은 자리를 쓴다. feature 모듈이 `WorkManager`를 직접 만지지 않는 경계는 이 ADR이 정한다.
- **워커에서 도메인 예외를 소비할 때 4xx/5xx를 갈라야 한다.** `MinoDomainException.Http(code)`의 `code`를 보고 `retry()`와 `failure()`를 나눈다. 구분 없이 전부 `retry()`로 넘기면 지원하지 않는 URL이 백오프 루프에 갇힌다.
- **`CancellationException`을 `retry()`로 흡수하지 않는다.** 워커 취소는 시스템이 작업을 회수하는 정상 신호이며, 재시도로 되살리면 취소가 무의미해진다.
- **결과를 화면에 돌려주는 경로를 만들지 않는다.** `WorkInfo`를 관찰해 토스트를 갱신하려는 시도는 FR-011(화면을 남기지 않는다)과 충돌한다. 결과 전달은 알림함이 소유한다.
- 이 결정은 공유 수신에 한정되지 않는다. **"완료 전에 화면이 사라지는 것이 요구사항인 요청"** 이면 같은 형태를 쓴다. 반대로 화면이 결과를 기다리는 요청은 [기존 규칙](2026-08-22-session-retry-owned-by-caller.md)대로 호출자가 재시도를 소유한다.
- 검증 시나리오는 [`quickstart.md` §5](../specs/shared-link-receiver/quickstart.md)가 소유한다 — Activity 종료 후 잔존, 오프라인 예약, 프로세스 강제 종료 후 잔존, 4xx 단일 실행.

## 고려한 대안

**Application scope 코루틴 (`@Singleton CoroutineScope`)** — 신규 의존성이 없고 구현이 몇 줄로 끝난다. Activity 종료와도 분리된다. 다만 프로세스가 죽으면 요청이 유실되고, `NetworkType.CONNECTED`에 해당하는 대기와 지수 백오프를 직접 구현해야 한다. 콜드 스타트가 잦은 이 진입점에서 유실 위험이 상시적이라 기각했다. 무게로만 보면 이쪽이 가벼워, 프로세스 생존을 전제할 수 있는 화면에서는 여전히 유효한 선택지다.

**`viewModelScope` 유지** — 추가 장치가 전혀 없다. Activity가 `finish()`되면 스코프가 취소되어 spec §4 가정을 정면으로 어긴다. 사용자가 토스트를 보고 외부 앱으로 돌아간 뒤 저장이 조용히 사라지는 결과가 되어 기각했다.

**방마다 워커를 분리** — spec §4 가정("저장은 선택한 방마다 독립적으로 성립한다")을 실행 단위까지 관철할 수 있다. 다만 서버에 요청할 계약이 `roomIds` 배열 1회 전송이고 방 단위 분해는 서버가 맡는다. 클라이언트가 다시 쪼개면 계약과 어긋나고 요청 수만 늘어 기각했다.

**Foreground Service** — 즉시 실행과 생존을 함께 보장하지만, 사용자에게 알림을 띄워야 해서 "조용히 물러난다"(FR-011)와 정면으로 어긋난다. 요청 하나 보내는 데 쓰기에 과하다. 검토 즉시 기각했다.
