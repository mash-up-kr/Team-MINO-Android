# plan-gen 고도화는 에이전트 팀이 아닌 서브에이전트 오케스트레이션으로 한다

- **상태**: Superseded by [SDD 파이프라인은 단계별 단일 스킬로 구성하고 spec-gen·plan-gen 서브에이전트 오케스트레이션을 폐기한다](2026-08-07-sdd-single-skill-per-stage.md)
- **작성일**: 2026-07-15
- **작성자**: Jaesung Lee

## 컨텍스트

`plan-gen` 스킬은 현재 메인 단일 컨텍스트의 직렬 실행(spec 읽기 → docs 읽기 → MVI 번역 → plan.md 작성)이다. `spec-gen`과 달리 자가검수 게이트가 없고, 출력 규약이 SKILL.md에 내장되어 SSOT가 분리되어 있지 않다. 이를 멀티에이전트 구조로 고도화하기로 하면서, 실행 구조를 두 가지 중에서 골라야 했다.

- **서브에이전트 오케스트레이션**: 메인이 시작 전에 계약(입력·출력·네이밍)을 확정해 주입하고, 서브에이전트는 결과만 반환하는 단방향 구조 (`spec-gen`이 이미 쓰는 패턴)
- **에이전트 팀**: 피어 에이전트들이 공유 태스크와 상호 메시지로 작업 중에 인터페이스를 협상하는 양방향 구조

두 방식의 본질적 차이는 병렬 여부가 아니라 **에이전트 간 조율이 언제 일어나느냐**(시작 전 계약 vs 작업 중 협상)다.

## 결정

plan-gen 고도화는 **오케스트레이터 + 서브에이전트 구조**로 한다. 메인이 Phase 1에서 **번역 계약**(spec 기능 행 인벤토리 + 화면 목록 + UiState/Intent/Route/UseCase/Repository/모델 네이밍 계약)을 확정해 주입하고, 서브에이전트들은 계약을 입력으로 서로 대기 없이 병렬 실행된다. 에이전트 팀 구조는 채택하지 않는다.

## 근거

- **협상거리가 없다**: plan-gen에서 에이전트 간 유일한 공유 지점은 네이밍(화면 설계가 쓰는 UseCase 이름 = 데이터 설계가 정의하는 UseCase 이름)인데, 이는 spec의 기능 행에서 기계적으로 도출되므로 시작 전에 계약으로 전부 고정할 수 있다. 런타임 협상이 필요 없는 작업에 팀을 붙이면 통신 오버헤드만 추가된다.
- **재현성**: plan-gen은 같은 spec을 넣으면 같은 구조의 plan이 나와야 하는 스킬이다. 협상 경로에 따라 산출물이 흔들리는 팀 방식은 이 성격과 맞지 않는다.
- **예외 처리도 계약 기반이 더 싸다**: 작업 중 계약이 깨지는 경우(예: 화면 에이전트가 계약에 없는 UseCase 필요 판단)는 피어 협상이 아니라 "메인에 보고 → 메인이 계약 갱신 → 재디스패치"로 처리하는 편이 저렴하고 추적 가능하다.
- **레포 패턴 일관성**: `spec-gen`이 이미 Phase + 계약 + 팬아웃 + 배리어 패턴으로 굳어 있어, 같은 패턴을 쓰면 스킬 유지보수 멘탈 모델이 하나로 유지된다.

## 결과

- plan-gen 고도화는 spec-gen과 대칭인 Phase 구조로 설계한다: 번역 계약 확정(메인) → 컨텍스트 수집 팬아웃 → 설계 생성 팬아웃(화면 수 조건부) → 이중 검증(메인 결정적 체크 + plan-reviewer) → 핸드오프.
- 출력 규약은 `plan-format.md`로 분리해 작성자·검수자 서브에이전트가 공유하는 SSOT로 삼는다 (spec-gen의 `spec-format.md`와 동일 원칙).
- 에이전트 팀 구조는 배제가 영구적인 것은 아니다 — 작업 중 인터페이스 협상이 실제로 필요한 **plan 실행(실제 구현) 단계**의 스킬을 만들 때 별도로 재검토한다.

## 고려한 대안

- **에이전트 팀 (피어 협상 구조)**: 피어 간 상호 메시지·공유 태스크로 작업 중 조율. 분할 경계와 인터페이스가 일하면서 드러나는 개방형 작업에 적합하지만, plan-gen은 분할을 계약으로 사전 고정할 수 있어 협상 이득이 없고 토큰 비용·재현성 저하만 남는다. 기각.
