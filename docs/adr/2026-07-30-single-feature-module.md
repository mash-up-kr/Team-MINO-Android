# feature 모듈은 `api`/`impl`로 나누지 않고 단일 모듈로 둔다

- **상태**: Accepted
- **작성일**: 2026-07-30
- **작성자**: Jaesung Lee

## 컨텍스트

`:feature:main`에 BottomNavigation 탭 셸을 구현하면서(#95), 탭 콘텐츠는 전환 검증용 placeholder로 두고 각 탭의 실제 화면은 앞으로 탭별 feature 모듈로 분리한다는 전제를 세웠다.

그런데 당시 규칙으로는 셸이 다른 모듈의 화면을 `screen<T>`로 등록할 방법이 없었다.

- `:feature:x:impl`은 다른 feature의 `impl`에 의존할 수 없다.
- `:feature:x:api`는 compose·hilt를 적용하지 않고 Launcher 인터페이스와 `EXTRA_*` 상수만 노출한다. 화면 컴포저블을 참조하는 등록 함수를 둘 수 없고, `api`가 `impl`을 의존할 수도 없다.

세 가지 후보를 검토했다.

- **A.** 등록 함수(`NavGraphBuilder.savedScreen(...)`)를 화면과 같은 `impl`에 public으로 두고 셸이 상대 `impl`을 의존한다. 레퍼런스(ppac `FarmemeNavHost`)가 쓰는 형태이며, 그쪽은 `:app`이 조립을 맡는다.
- **B.** `:core:navigation`에 등록 계약(`TabGraph`)을 두고 각 `impl`이 Hilt `@IntoSet`으로 바인딩, 셸은 `Set<TabGraph>`를 주입받아 조립한다.
- **C.** `:app`이 탭 그래프를 조립한다.

A안이 유력하다고 보고 A안이 이 프로젝트에서 걸리는 제약을 하나씩 짚는 과정에서, 전제 자체가 문제라는 것이 드러났다.

- 탭 feature는 Activity로 진입하지 않으므로 Launcher도 `EXTRA_*`도 없다. `api`에 둘 것이 하나도 없어 **규약 때문에 빈 모듈을 만들게 된다**.
- A안을 쓰려면 Route와 등록 함수를 `impl`에서 public으로 열어야 한다. `api`가 담당했던 "공개 계약" 역할이 `impl`로 옮겨가므로 `api`의 존재 이유가 사라진다.
- 분리가 보장해준다고 여겼던 경계는 실제로 검증되지 않는다. `lint.xml`에는 룰이 38개 있지만 **모듈 의존 방향을 검사하는 룰이 없고**, 경계는 문서와 리뷰에만 의존한다.
- B안은 리포에 선례가 없는 multibinding 인프라를 요구하고, 등록 누락이 컴파일 에러가 아니라 런타임 크래시가 된다. C안은 화면 조립 책임을 `:app`으로 흘린다.

## 결정

**feature 모듈을 `api`/`impl`로 나누지 않고 단일 모듈로 둔다.** 기존 규약(feature는 두 모듈로 만든다, `api`는 경량 유지, `impl`→`impl` 의존 금지)을 폐기한다.

대신 feature를 성격에 따라 두 종류로 구분하고, 의존 규칙을 여기에 붙인다.

| 종류 | 무엇인가 | 의존 규칙 |
|---|---|---|
| **진입형 feature** | **Activity를 진입점으로 갖는 독립 플로우.** 두 성격을 모두 포함한다 — ① 여러 호출자가 재사용하는 기획 플로우(진입점이 여러 개), ② 온보딩·로그인처럼 호출자가 하나여도 탭 셸 바깥에서 화면 전체를 점유하고 자체 백스택으로 진행되는 플로우 | Activity 전환 계약을 통해 진입한다 |
| **탭 feature** | 바텀 네비게이션 탭에 해당하며 **중첩 navigation screen 단위**로 구성되는 플로우 | `:feature:main`이 이 모듈을 **직접 의존하는 것을 예외로 허용**한다 |

구분 기준은 재사용 여부가 아니라 **Activity로 독립 진입하는지, 탭 셸의 그래프에 편입되는지**다. 온보딩·로그인은 재사용되지 않아도 탭 셸과 생애주기가 분리되고(완료 후 종료하며 결과를 돌려준다) 자체 그래프를 가지므로 진입형이다.

- **feature 간 순환 참조는 금지한다.** 탭끼리 서로를 의존하지 않고, 탭 간 전환은 `:feature:main`이 콜백으로 배선한다.
- 진입형 feature의 Activity 전환 구조는 **단일 모듈 전제에 맞춰 다시 설계한다.** 계약과 구현이 같은 모듈에 있게 되므로 현행 `ActivityLauncher`/`BaseActivityLauncher` 사용 방식(`api`에 인터페이스, `impl`에 구현체 + Hilt 바인딩)이 그대로 성립하지 않는다. 구체안은 별도 작업으로 정한다.

이 문서는 같은 주제로 먼저 기록했던 "분리 방식을 첫 탭 화면 작업 시점까지 보류한다"(`Proposed`)를 대체한다. 보류의 전제였던 api/impl 분리가 없어지면서 A·B·C 후보 자체가 성립하지 않게 됐다.

## 근거

- `api`가 담당한 유일한 역할은 전환 계약(Launcher + `EXTRA_*`) 노출이다. 탭 feature에는 그 계약이 아예 존재하지 않으므로, 분리를 강제하면 빈 모듈이 늘어난다.
- A안을 채택하는 순간 공개 표면이 `impl`로 이동한다. 그러면 두 모듈 체계가 남긴 것은 "빌드 파일 두 개, 컨벤션 플러그인 두 종, `settings`·`:app` 등록 두 줄, `api`에 compose·hilt를 넣지 않는 규칙"뿐이다. 비용은 feature마다 반복되고 이득은 없다.
- 분리가 주던 보장이 실제로는 문서 수준이다. 모듈 의존을 검사하는 장치가 없으므로, 단일 모듈 + 문서 규칙으로도 같은 수준의 경계를 유지한다. 경계를 진짜로 강제하려면 Gradle 의존 검증을 넣는 편이 효과적이고, 그것은 모듈 분리 여부와 독립이다.
- 순환 참조 방지는 분리와 무관하게 성립한다. Gradle이 모듈 순환을 컴파일 타임에 거부하고, 탭 간 전환을 셸이 배선하는 규칙으로 순환이 생길 상황 자체를 없앤다.
- 탭 feature에서는 A안의 형태(모듈이 Route와 등록 함수를 노출하고 셸이 호출)가 예외가 아니라 **기본형**이 된다. 규칙 완화를 위한 예외 문장이 필요 없어진다.

## 결과

- 기존 `:feature:sample`·`:feature:home`·`:feature:main`의 `api`/`impl` 쌍을 각각 단일 모듈로 합친다.
- 컨벤션 플러그인 `mino.android.feature.api`·`mino.android.feature.impl`을 단일 플러그인으로 통합한다.
- 문서를 전면 갱신한다 — `feature-module.md`(1·2장 api/impl 구조·패키지 배치), `modularization.md`(의존성 흐름·안티패턴·새 feature 추가 절차), `feature-navigation.md`(Launcher 계약 위치와 전환 스켈레톤).
- #95 진행 중 반영한 "진입형/탭 feature 구분" 문서 수정은 api/impl 전제 위에 쓰여 있으므로, 이 결정에 맞춰 다시 쓴다.
- `:core:navigation`의 Activity 전환 API(`ActivityLauncher`·`BaseActivityLauncher`·`intentOf`)는 단일 모듈 전제에서 재검토 대상이다.
- 이 결정 이전에 머지된 api/impl 구조는 되돌리는 대상이 되므로, 마이그레이션 시점에 실패 기록(`docs/failures/`)을 함께 남길지 판단한다.

## 고려한 대안

- **A. `api`/`impl`을 유지하고 셸→탭 `impl` 직접 의존을 예외로 허용** — 규칙 문장 완화(모듈 경계 문서 3곳·구조 문서 2곳)와 하위 결정(탭 모듈에 `api`를 둘지, public 표면을 어디까지 열지)이 따라오고, 그 대가로 얻는 것은 진입형 feature에만 유효한 계약 분리다. 탭 feature의 `api`가 빈 껍데기가 되는 문제를 해결하지 못해 폐기.
- **B. `api`에 등록 계약만 두고 `impl`이 Hilt multibinding으로 제공** — 모듈 규칙을 건드리지 않고 셸이 탭 화면을 컴파일 타임에 모르게 되지만, 이점이 온전히 성립하려면 아이콘·라벨 같은 표현 정보를 네비게이션 계약에 넣어야 하고 탭 순서·등록 누락 검증이 런타임으로 밀린다. 리포에 multibinding 선례가 없어 도입 비용도 크다. 폐기.
- **C. `:app`이 탭 그래프를 조립** — 규칙 위반이 없는 대신 탭 셸의 UI 조립 책임이 `:app`으로 새어나가 `:feature:main`의 존재 의미가 옅어진다. 폐기.
- **api/impl 분리를 그대로 유지** — 진입형 feature에서는 계약과 구현을 갈라두는 이점이 있다. 그러나 그 이점이 실제로 강제되지 않고(의존 검사 부재), 탭 feature에는 적용조차 되지 않는다. 두 종류를 한 규약으로 묶어두는 비용이 이점보다 크다고 판단해 폐기.
