## 1. 유저 시나리오 (User Scenarios) *(필수)*

### 유저 플로우 1 - 이 설치가 알림을 받을 수 있게 만들기
앱이 설치된 뒤 서버가 이 설치로 알림을 보낼 수 있으려면, 앱이 자기 앞으로 온 메시지를 받을 주소를 확보해 서버에 알려 두어야 한다. 사용자가 관여하지 않고 앱이 스스로 하는 일이며, 화면에 어떤 흔적도 남기지 않는다.

**진입 조건**: 익명 세션이 확보된 상태로 앱이 시작된다. ([SCR-001] 스플래시가 세션 확보를 끝낸 시점)

1. 앱이 세션 확보를 마침 → 앱은 이 설치 앞으로 온 메시지를 받을 **등록 토큰**을 확보한다
2. 토큰을 확보함 → 앱은 그 토큰을 서버에 등록해, 서버가 이 설치를 알림 수신처로 삼을 수 있게 한다
3. 메시지 전달자가 토큰을 새로 발급함 → 앱은 갱신된 토큰을 서버에 다시 등록해 이전 토큰을 대체한다

**완료 조건**: 서버가 이 설치의 유효한 최신 등록 토큰을 보유한다.

### 유저 플로우 2 - 앱 밖에서 알림을 받아 열기
앱을 보고 있지 않을 때 알림이 도착하면 기기의 알림 영역에 뜨고, 그것을 누르면 앱이 열리며 그 알림이 가리키는 곳으로 이동한다. 도착지는 알림함에서 그 알림을 눌렀을 때 가는 곳과 같다 — 저장 오류와 위치 기반 대표 알림만 알림 탭 목록에서 멈춘다.

**진입 조건**: 알림 권한이 허용된 설치에서 앱이 화면에 없다(백그라운드 또는 종료 상태).

1. 서버가 이 설치로 알림을 보냄 → 기기 알림 영역에 시스템 알림이 뜨고, [SCR-007]의 유형 문구와 대상 이름을 그대로 보여준다
2. 사용자가 그 알림을 누름 → 앱이 열리며 그 알림 유형에 대응하는 도착지로 이동한다
3. 사용자가 알림을 누르지 않고 지움 → 앱은 열리지 않고 아무 상태도 바뀌지 않는다

**완료 조건**: 알림을 누른 사용자가 그 알림 유형에 대응하는 도착지 화면에 서 있다.

### 유저 플로우 3 - 앱을 보고 있는 동안 알림이 도착한다
사용자가 앱을 쓰는 중에 알림이 도착해도 앱 밖에 있을 때와 똑같이 알린다. 다만 보고 있던 화면을 앱이 가로채지는 않는다.

**진입 조건**: 알림 권한이 허용된 설치에서 사용자가 앱을 화면에서 사용하고 있다.

1. 서버가 알림을 보냄 → 앱이 그 알림을 받는다
2. 앱이 알림을 받음 → 앱 밖에 있을 때와 똑같이 시스템 알림을 띄운다
3. 사용자가 하던 일을 계속함 → 보고 있던 화면은 그대로이며, 화면이 바뀌는 것은 사용자가 그 알림을 누른 경우뿐이다

**완료 조건**: 알림이 사용자에게 전달되었고, 사용자가 보고 있던 화면의 작업이 끊기지 않았다.

|---|---|---|---|---|---|
| TS-015 | 사용 중 도착한 알림도 시스템 알림으로 뜬다 | 사용자가 앱의 임의 화면을 보고 있다 | 서버가 알림을 보낸다 | 기기 알림 영역에 앱 밖 수신과 같은 알림이 뜬다 | FR-011 |
| TS-016 | 사용 중 도착이 화면을 가로채지 않는다 | 사용자가 앱의 임의 화면을 보고 있다 | 서버가 알림을 보낸다 | 보고 있던 화면이 그대로 유지되고 화면 전환이 일어나지 않는다 | FR-011, UX-001 |
| TS-017 | 사용 중 수신도 알림함에는 남는다 | 사용자가 앱을 보고 있다 | 알림이 도착하고 이후 알림 탭에 들어간다 | 그 알림이 목록에 있다 | FR-011 |

### 유저 플로우 4 - 위치 기반 대표 알림을 받아 알림 탭으로 들어오기
반경 안에 저장해 둔 장소가 여럿일 때, 서버는 장소마다 알리는 대신 대표 알림 한 건으로 묶어 보낸다. 이 알림은 알림함 목록에 행으로 남지 않으므로([SCR-007] FR-019), 눌렀을 때 갈 개별 도착지가 없다.

**진입 조건**: 알림 권한이 허용된 설치에서 서버가 반경 안 여러 장소를 묶은 대표 알림을 보낸다.

1. 대표 알림이 도착함 → 알림 영역에 `근처에 저장한 곳 N개가 있어요`와 `반경 3km`를 담은 시스템 알림 한 건이 뜬다
2. 사용자가 그 알림을 누름 → 앱이 열리고 알림 탭 목록으로 이동한다
3. 사용자가 알림 탭을 봄 → 묶여 있던 장소들이 개별 리마인드 행으로 목록에 있다

**완료 조건**: 대표 알림을 누른 사용자가 알림 탭 목록 앞에 서 있다.

**테스트 시나리오**

|---|---|---|---|---|---|
| TS-018 | 대표 알림이 한 건으로 뜬다 | 반경 안에 저장한 장소가 3개 있다 | 서버가 대표 알림을 보낸다 | 알림 영역에 개별 3건이 아니라 대표 알림 1건이 뜬다 | FR-012 |
| TS-019 | 대표 알림을 누르면 알림 탭으로 간다 | 대표 알림이 떠 있다 | 사용자가 그 알림을 누른다 | 알림 탭 목록 화면이 보인다 | FR-012 |

**엣지 케이스**

| EC-016 | 개별 리마인드와 대표 알림이 함께 도착한다 | 앱은 받은 대로 각각 표시한다. 무엇을 묶어 보낼지는 서버가 정한다 | FR-012 |

## 2. 요구사항 (Requirements) *(필수)*

### 2.1 기능적 요구사항 (Functional Requirements)

- **FR-001**: 시스템은 반드시 익명 세션이 확보된 뒤 이 설치의 푸시 등록 토큰을 확보한다. (근거: 이슈 #275 범위 2 / PRD 10.1.0 「비회원 익명 세션」)
- **FR-002**: 시스템은 반드시 확보한 등록 토큰을 서버에 등록해, 서버가 이 설치를 알림 수신처로 삼을 수 있게 한다. (근거: 이슈 #275 범위 2)
- **FR-003**: 시스템은 반드시 메시지 전달자가 토큰을 새로 발급하면 갱신된 토큰을 서버에 다시 등록한다. (근거: 이슈 #275 범위 2 — 토큰 갱신 처리)
- **FR-004**: 시스템은 반드시 토큰 확보·등록의 실패를 사용자에게 노출하지 않고, 그 실패가 앱의 다른 기능을 막지 않게 한다. (근거: PRD 10.1.0 「비회원 익명 세션」 — 사용자는 세션·토큰의 존재를 인지하지 않는다)
- **FR-005**: 시스템은 반드시 알림 권한의 허용 여부와 무관하게 토큰을 확보·등록한다. (근거: PRD 10.1.0 「지연 권한 요청」 — 권한은 마이페이지 스위치 시점에만 묻는다)
- **FR-006**: 시스템은 반드시 서버가 보낸 알림을 기기 알림 영역의 시스템 알림으로 표시한다. (근거: 이슈 #275 범위 3)
- **FR-007**: 시스템은 반드시 시스템 알림의 문구를 [SCR-007] 알림함 FR-004가 정한 6종 유형 문구와 대상 이름 그대로 표시한다. (근거: [SCR-007] 알림함 spec 3.0.0 FR-004 — 유형이 곧 문구를 결정한다)
- **FR-008**: 시스템은 반드시 알림 채널을 **하나만** 두고 모든 유형의 시스템 알림을 그 채널로 표시한다. 유형별·성격별로 채널을 나누지 않는다. (근거: 사용자 확정 §5 Q3 / PRD 10.1.0 [SCR-008] Flow B — 사용자가 조작하는 알림 스위치도 하나다)
- **FR-009**: 시스템은 반드시 시스템 알림을 눌렀을 때 유형별로 지정된 도착지로 이동시킨다 — 중복 저장 · 위치 기반 리마인드 · 코멘트 기반 리마인드는 해당 장소의 장소 상세로, 공동방 참가 ①②는 해당 공동방의 방 상세로, 저장 오류와 위치 기반 대표 알림은 알림 탭 목록으로 보낸다. 저장 오류 안내 화면으로는 사용자가 그 목록에서 한 번 더 눌러 들어간다. 대상 장소가 여러 방에 저장돼 있을 때 어느 방을 기준으로 여는지는 FR-013이 정한다. (근거: 사용자 확정 §5 Q1·Q6 / [SCR-007] 알림함 spec 3.0.0 FR-005 — 장소·공동방 대상 알림은 앱 안 경로와 같은 도착지를 쓴다)
- **FR-010**: 시스템은 반드시 앱이 종료된 상태에서 알림을 눌렀을 때, 앱의 기존 시작 경로(세션 확보 포함)를 거친 뒤 도착지로 이동시킨다. (근거: PRD 10.1.0 [SCR-001] 스플래시 — 세션 확보 없이는 서버 조회가 성립하지 않는다)
- **FR-011**: 시스템은 반드시 앱을 화면에서 사용하는 동안 도착한 알림도 앱 밖에 있을 때와 똑같이 시스템 알림으로 표시하며, 그 표시가 사용자가 보고 있던 화면을 전환시키지 않게 한다. (근거: 사용자 확정 §5 Q2 / 이슈 #275 범위 3 — foreground·background 수신 처리)
- **FR-012**: 시스템은 반드시 위치 기반 대표 알림을 눌렀을 때 알림 탭 목록으로 이동시킨다. (근거: [SCR-007] 알림함 spec 3.0.0 FR-019 — 대표 알림은 앱 밖 알림으로만 존재하며 탭하면 알림 탭으로 진입한다)
- **FR-013**: 시스템은 반드시 알림이 담아 온 **유형과 대상 식별자 하나**(장소 대상 알림은 그 장소가 저장된 **핀** 식별자 — 장소·방 쌍, 공동방 대상 알림은 공동방 식별자)로 도착지를 정한다. 장소 대상 알림의 방은 앱이 따로 정하지 않고 알림이 가리키는 핀이 속한 방이다. 알림이 함께 싣는 장소 식별자는 도착지 판정에 쓰지 않는다. 대상 식별자가 없거나 해석할 수 없으면 알림 탭 목록으로 보낸다. (근거: 사용자 확정 §5 Q4의 1.0.2 재확정 — 서버 payload가 장소·핀 식별자를 함께 싣는 것이 확인됐고, 앱 안 경로([SCR-007] FR-005)도 같은 핀 식별자로 장소 상세를 연다)
- **FR-014**: 시스템은 반드시 알림 권한이 허용되지 않은 상태에서 도착한 알림에 대해 권한을 요청하거나 대체 표시를 두지 않는다. (근거: [SCR-007] 알림함 spec 3.0.0 §3.2 — 권한과 관련된 모든 것은 [SCR-008]이 정의한다)
- **FR-015**: 시스템은 반드시 등록 토큰의 폐기를 서버에 요청하지 않는다. 앱이 하는 일은 최신 토큰을 등록하는 것뿐이며, 도달하지 않게 된 토큰을 걷어내는 일은 서버가 소유한다. (근거: 사용자 확정 §5 Q5 / PRD 10.1.0 「비회원 익명 세션」 — 로그아웃이 없어 앱에는 폐기를 알릴 계기가 없다)

### 2.2 핵심 UX 규칙 (Core UX Rules)

- **UX-001**: 알림이 도착해도 사용자가 보고 있던 화면을 앱이 스스로 전환하지 않는다. 화면이 바뀌는 것은 사용자가 알림을 누른 경우뿐이다. (근거: PRD 10.1.0 「독립적 카드 소비 경험」 — 앱은 사용자의 진행을 가로채지 않는다)
- **UX-002**: 토큰 확보·등록의 성공도 실패도 화면에 어떤 표시도 남기지 않는다. 토스트·배너·오류 화면 어느 것도 두지 않는다. (근거: FR-004)
- **UX-003**: 여러 알림이 도착하면 각각 별개의 시스템 알림으로 알림 영역에 쌓인다. 앱이 임의로 묶거나 최신 것으로 덮어쓰지 않는다 — 묶는 일은 서버가 대표 알림으로 한다. (근거: [SCR-007] 알림함 spec 3.0.0 §4 가정 — 묶는 일은 서버가 한다)
- **UX-004**: 사용자가 누른 시스템 알림은 알림 영역에서 사라지고, 누르지 않은 알림은 그대로 남는다. (근거: 기기 알림 영역의 표준 동작)
- **UX-005**: 알림을 눌러 도착한 화면에서 뒤로 나가는 규칙은 그 화면이 원래 가진 규칙을 그대로 따른다. 알림에서 왔다는 이유로 다른 곳으로 되돌리지 않는다. (근거: [SCR-007] 알림함 spec 3.0.0 FR-020·§3.2)
- **UX-006**: 사용자가 기기 설정에서 알림을 끄면 모든 유형의 알림이 함께 꺼진다. 유형별로 골라 끄는 수단을 앱이 제공하지 않는다. (근거: FR-008 — 채널이 하나다)

### 2.3 주요 도메인 (Core Domain) *(데이터를 다루는 기능일 경우 포함)*

- **푸시 등록 토큰 (Push Registration Token)**: 서버가 이 설치 앞으로 알림을 보내기 위한 수신 주소. 설치마다 하나이며, 메시지 전달자가 발급하고 임의의 시점에 새 값으로 갈아 끼울 수 있다. 사용자가 만들거나 보거나 지우는 값이 아니고, 앱이 폐기하지도 않는다 — 앱은 최신 값을 등록할 뿐이다.
- **푸시 메시지 (Push Message)**: 서버가 보내온 알림 한 건. 어떤 사건인지를 나타내는 유형, 화면에 보일 문구와 대상 이름, 그리고 눌렀을 때 도달할 곳을 정하는 대상 식별자 하나를 가진다. 장소 대상 알림의 식별자는 장소 자체가 아니라 그 장소가 저장된 핀(장소·방 쌍)을 가리킨다. 유형은 [SCR-007]이 정한 6종과 위치 기반 대표 알림으로 나뉘며, 대표 알림과 저장 오류는 대상 식별자를 갖지 않는다.
- **알림 채널 (Notification Channel)**: 시스템 알림이 소리·진동·중요도를 어떤 규칙으로 표시할지 정하는 분류이자, 사용자가 기기 설정에서 끌 수 있는 단위. 이 앱에는 하나만 있으므로 켜고 끄는 선택도 전체 단위 하나다.
- **도착지 (Destination)**: 시스템 알림을 눌렀을 때 사용자가 도달하는 화면. 알림의 유형이 어떤 화면인지를 정하고, 대상 식별자가 그중 어느 것인지를 정한다. 정할 수 없을 때의 낙하 지점은 알림 탭 목록이다.

## 3. 범위 (Scope) *(필수)*

### 3.1 측정 가능한 성과 (Measurable Performance)

- **SC-001**: 앱을 새로 설치해 처음 실행한 뒤, 서버가 그 설치로 알림을 보내 기기에 도달시킬 수 있다.
- **SC-002**: 메시지 전달자가 토큰을 갱신한 뒤 서버가 보낸 알림이 계속 같은 설치에 도달한다 — 갱신으로 수신이 끊기지 않는다.
- **SC-003**: 서버가 보낸 알림이 기기 알림 영역에 표시되기까지 앱이 자체적인 대기·지연을 추가하지 않는다.
- **SC-004**: 시스템 알림을 누른 사용자가 추가 조작 없이 도착지 화면에 도달한다 — 앱이 종료된 상태에서 눌렀을 때도 같다.
- **SC-005**: 장소 대상 알림과 공동방 대상 알림은 앱 안(알림함 목록)에서 누르든 앱 밖(시스템 알림)에서 누르든 같은 화면에 도달한다.
- **SC-006**: 토큰 확보 또는 서버 등록이 실패해도 사용자가 앱의 모든 기능을 그대로 쓸 수 있고, 실패를 알리는 화면 요소를 보지 않는다.
- **SC-007**: 반경 안에 저장한 장소가 여러 개일 때 사용자가 받는 앱 밖 알림은 한 건이다.
- **SC-008**: 앱을 사용하는 중에 알림이 도착해도 사용자가 하던 입력·조작이 중단되지 않는다.

### 3.2 비목표 항목 (Out of Scope)

- **알림 권한(POST_NOTIFICATIONS)에 관한 모든 것은 [SCR-008] 마이페이지 스펙이 정의한다.** 권한을 언제 어떻게 묻는지도, 재요청이 막힌 상태에서 OS 설정으로 보내는 동작도 이 문서에 없다. 이 문서는 권한이 허용된 설치와 아닌 설치가 각각 어떻게 되는지만 적는다.
- **알림함 화면은 [SCR-007] 알림 탭 스펙이 정의한다.** 목록의 구성·정렬·페이징·빈 상태·저장 오류 안내 화면은 그쪽 몫이며, 이 문서는 그 화면을 도착지로 지목하는 데까지만 관여한다.
- **알림을 언제 만들어 누구에게 보낼지의 판정과 발송은 서버가 정의한다.** 대표 알림으로 묶는 기준, 반경·주기·대상 선정 모두 이 문서의 범위가 아니다.
- **도달하지 않게 된 토큰을 걷어내는 일은 서버가 정의한다.** 발송 실패를 어떻게 판정하고 언제 지우는지, 한 사용자에게 설치가 여럿일 때 어디로 보내는지 모두 서버가 소유한다. 앱은 폐기에 관여하지 않는다(FR-015).
- **알림 도착지 화면의 내용과 동작은 각자의 스펙이 정의한다.** [SCR-005] 방 상세와 [SCR-006] 장소 상세가 무엇을 보여주는지, 그 화면의 나가기 규칙이 무엇인지 여기서 정하지 않는다.
- **토큰 등록 API의 계약(경로·필드·인증·응답)은 서버가 정의한다.** 이 문서는 "등록한다"까지만 요구하고, 그것이 어떤 요청으로 성립하는지는 서버 계약과 `plan.md`가 다룬다.
- **[SYS-004] 현재 표시 기준 방을 정하고 바꾸는 일은 지도 & 마커가 정의한다.** 이 문서는 그 값을 읽지도 바꾸지도 않는다 — 장소 대상 알림의 방은 알림이 실은 핀이 정하며(FR-013), 알림을 눌러 연 장소 상세가 표시 기준 방에 어떤 영향을 주는지는 [SCR-006] 장소 상세가 정한다.
- **#90 디바이스 토큰 발급 게이트웨이는 별개 축이다.** 저장 인프라를 함께 쓸 수 있는지는 `plan.md`가 판단할 구현 사항이고, 이 문서는 두 축의 요구사항을 섞지 않는다.

## 4. 가정 (Assumptions)

- **서버가 알림을 만들어 보내고, 앱은 받은 것을 그대로 보여준다.** 앱은 어떤 알림도 스스로 만들지 않으며, 무엇을 알릴지 판정하지 않는다. 이는 [SCR-007] 알림함이 목록에 대해 두는 전제와 같다.
- **토큰 확보와 서버 등록은 앱을 시작할 때마다 시도한다.** 값이 이전과 같으면 서버가 같은 값을 다시 받아도 무해하다고 본다. 실패한 시도를 위해 별도의 재시도 큐나 대기 화면을 두지 않고, 다음 앱 시작을 재시도 시점으로 삼는다.
- **토큰 등록은 익명 세션을 전제로만 성립한다.** 서버가 토큰을 누구의 것으로 저장하려면 요청자가 특정되어야 하므로, 세션이 확보되기 전에는 등록하지 않는다. (PRD 10.1.0 「비회원 익명 세션」)
- **프로필 등록 전 설치에는 알림이 오지 않는다.** 토큰 등록은 프로필 등록을 마친 사용자에게만 성립하므로(위 익명 세션 전제의 연장), 온보딩 도중인 설치는 서버의 발송 대상이 아니다. 그런 설치에서 알림을 눌러 앱이 온보딩으로 갈라지는 일이 생기더라도 도착지 이동은 하지 않고 온보딩을 그대로 진행한다. 재현할 수 없는 상황이라 엣지 케이스로 올리지 않는다.
- **세션은 설치가 살아 있는 동안 만료되지 않으므로, 세션 만료로 토큰을 다시 등록하는 경로는 없다.** (PRD 10.1.0 「비회원 익명 세션」) 토큰을 다시 등록하는 계기는 앱 시작과 전달자의 토큰 갱신뿐이다.
- **알림 권한과 등록 토큰은 서로 독립이다.** 권한이 없어도 토큰은 확보·등록되고, 서버는 알림을 보낼 수 있다. 다만 기기가 그 알림을 화면에 띄우지 않을 뿐이다.
- **시스템 알림에 쓸 문구는 서버가 완성해 보낸다.** 유형별 문구가 고정 문자열이고 가변 부분이 대상 이름·참가자 이름뿐이라는 [SCR-007]의 전제를 그대로 따르며, 앱이 문구를 조립하거나 번역하지 않는다.
- **알림에 실을 이미지는 전제하지 않는다.** [SCR-007]의 목록 행이 쓰는 썸네일은 앱 안 화면의 구성 요소이며, 앱 밖 알림이 같은 이미지를 싣는다고 보지 않는다.
- **장소 대상 알림은 장소가 저장된 핀(장소·방 쌍)을 가리킨다.** 서버가 장소 대상 알림에 장소 식별자와 핀 식별자를 함께 싣는 것이 2026-09-03 확인됐다. 앱은 핀 식별자로 장소 상세를 열고 그 핀이 속한 방이 곧 도착지 방이므로, 앱이 현재 표시 기준 방을 따로 읽어 방을 정하지 않는다. 1.0.1까지의 가정("도착지 방은 앱이 이미 갖고 있다")은 이 사실로 대체됐다.
- **사용자는 알림을 누르는 시점에 온라인이다.** 도착지 화면이 서버 조회에 실패하는 경우는 그 화면의 오류 규칙을 따른다.
- **알림을 눌러 들어온 뒤 돌아갈 곳은 알림이 아니라 앱의 평소 화면 구조다.** 알림에서 온 진입이라는 이유로 특별한 되돌아가기 경로를 만들지 않는다. ([SCR-007] FR-020과 같은 기준)
- **서버의 토큰 등록 API는 존재한다.** 2026-08-31 조회에는 없었으나 2026-09-03 조회에서 확인됐고, 요청·응답이 FR-002·FR-003의 요구와 어긋나는 지점이 없다. 계약의 세부는 `plan.md`와 그 하위 계약 문서가 소유한다. "계약 자리를 비워 둔 채 진행한다"던 1.0.1까지의 가정은 해소됐다.
- **푸시 payload의 스키마는 서버가 소유하며 아직 확정되지 않았다.** FR-013이 요구하는 "유형과 대상 식별자 하나"를 서버가 그 형태로 실어 준다는 전제 위에 도착지 판정이 성립한다.
- **알림 탭([SCR-007], 이슈 #160)과 장소 상세·방 상세가 도착지로 존재한다고 전제한다.** 이 스펙의 진입 경로는 그 화면들과 탭 셸이 있어야 성립하며, 없는 동안에는 끝까지 검증할 수 없다.

### 확정된 항목

- **Q**: [FR-009] 시스템 알림을 눌렀을 때 어디로 보내는가? — 이슈 #275 본문 안에서 두 갈래가 충돌했다. 「범위」 4와 「완료 조건」은 "알림 탭으로 이동"이라 적고, 「논의 항목」 1은 "알림함 FR-005·FR-022가 `pinId`를 도착지로 쓰므로 푸시도 같은 식별자여야 두 경로의 도착지가 어긋나지 않는다"고 적어 최종 도착지를 가리킨다.
  → **A**: **유형별로 가른다.** 장소 대상 알림(중복 저장·위치 기반·코멘트 기반)은 장소 상세로, 공동방 참가 ①②는 방 상세로, 장소 대상 알림과 공동방 대상 알림은 [SCR-007] FR-005와 도착지를 맞춘다. 저장 오류와 위치 기반 대표 알림은 알림 탭 목록에서 멈춘다 — 대표 알림은 목록에 행이 없어 개별 도착지가 없고(FR-019), 저장 오류는 아래 Q에서 목록까지로 정했다. *(반영: FR-009·FR-012, 유저 플로우 2 스텝 2·완료 조건, TS-008~TS-010, EC-009·EC-010, §2.3 도착지, §3.1 SC-004·SC-005)*
- **Q**: [FR-009 세부] `저장 오류` 알림을 눌렀을 때 알림 탭 목록까지만 가는가, 저장 오류 안내 화면까지 가는가? — [SCR-007]은 저장 오류에 대해 알림 탭 안의 안내 화면을 따로 둔다.
  → **A**: **알림 탭 목록까지만 간다.** 사용자가 목록에서 그 알림을 한 번 더 눌러 안내 화면으로 들어간다. 이 유형만 앱 안·밖의 도착지가 한 단계 어긋나며, 그래서 §3.1 SC-005의 도착지 일치는 장소·공동방 대상 알림에 한정한다. *(반영: FR-009, TS-010, 유저 플로우 2 도입문, §3.1 SC-005)*
- **Q**: [FR-011] 앱을 화면에서 쓰는 동안 도착한 알림을 앱 밖 알림으로도 띄우는가? — 이슈가 "foreground·background 수신 처리"를 범위에 넣었을 뿐 어느 쪽인지 정하지 않았고, [SCR-007]에도 근거가 없다.
  → **A**: **앱 밖에 있을 때와 똑같이 띄운다.** 놓치는 알림이 없고 수신 상태에 따라 규칙이 갈리지 않는다. 다만 표시가 사용자의 화면을 전환시키지는 않는다. *(반영: FR-011, 유저 플로우 3 전체, TS-015~TS-017, EC-013·EC-014, §3.1 SC-008)*
- **Q**: [FR-013] 푸시 payload는 도착지를 정하기 위해 어떤 대상 식별자를 담는가? — 이슈가 후보로 든 `pinId`는 "장소·방 쌍"이라 방을 payload가 고정하게 되어, 도착지 방을 앱이 보관한 현재 표시 기준 방으로 정하는 [SCR-007] FR-022와 어긋난다.
  → **A (1.0.1까지)**: **장소 식별자 하나만 싣고, 방은 앱이 FR-022대로 정한다.** 공동방 대상 알림은 공동방 식별자를 싣는다. 이렇게 두면 앱 안·밖 두 경로의 도착지 규칙이 완전히 같아지고, 지도에서 사용자가 이미 내린 방 선택을 푸시가 뒤엎지 않는다.
  → **A (1.0.2 재확정, 2026-09-03)**: **장소 대상 알림은 핀 식별자로 도착지를 정한다.** plan 단계에서 서버의 실제 payload가 장소 식별자와 핀 식별자를 **함께** 싣는 것이 확인됐고, 앱 안 경로([SCR-007] FR-005)가 장소 상세를 여는 키도 이미 핀 식별자다. 반면 장소 식별자만으로 표시 기준 방을 되묻는 수단은 앱에도 서버에도 없다. 위 답이 우려한 "방 선택을 푸시가 뒤엎는" 문제는 어느 방의 저장을 알리는지가 서버 판정 사항(§3.2)이라는 점으로 받아들이고, 요구사항 경계("그 알림이 가리키는 장소의 장소 상세로 이동")는 그대로 둔다. *(반영: FR-013, EC-012, §2.3 푸시 메시지, §3.2 [SYS-004] 항목, §4 가정 1건)*
- **Q**: [FR-015] 앱을 지웠다 다시 설치했을 때 서버에 남는 이전 토큰을 누가 걷어내는가? — 익명 세션에는 로그아웃이 없어 앱이 "이 토큰을 더는 쓰지 않는다"고 알릴 계기가 없다(PRD 10.1.0 「비회원 익명 세션」).
  → **A**: **서버가 발송 실패로 판정해 스스로 걷어낸다.** 앱은 폐기에 관여하지 않고 최신 토큰을 등록하는 일만 한다. 앱을 지우는 순간에는 앱 코드가 돌지 않아 폐기 요청이 실효를 갖기 어렵다는 점도 같은 결론을 가리킨다. *(반영: FR-015, TS-005, EC-005, §2.3 푸시 등록 토큰, §3.2 비목표 1건)*
- **Q**: [FR-008] 알림 채널을 몇 개 두는가? — 채널이 곧 사용자가 기기 설정에서 골라 끌 수 있는 단위인데, 디자인·PRD 어디에도 이 축의 UI가 없다.
  → **A**: **단일 채널 하나.** 사용자가 조작하는 알림 스위치도 [SCR-008]에 하나뿐이므로 끄고 켜는 단위를 그와 같게 둔다. 유형별로 골라 끄는 수단은 제공하지 않는다. *(반영: FR-008, UX-006, TS-014, §2.3 알림 채널)*
