### 유저 플로우 1 - 앱을 처음 켠 사용자의 세션 확보

앱을 설치하고 처음 실행한 사용자에게, 서버가 검증할 수 있는 비회원 세션을 만들어 준다. 사용자는 이 과정을 인지하지 못한 채 다음 화면으로 넘어간다.

**진입 조건**: 앱 최초 실행. 단말에 이 앱의 세션이 없다.

1. 사용자가 앱을 실행한다 → 진입 화면이 첫 데이터 요청보다 먼저 세션 확보를 시작한다
2. 세션 확보가 성공한다 → 앱 전체에서 통용되는 사용자 식별자가 확보되고, 이후 모든 서버 요청이 이 세션에 귀속된다
3. 진입 화면이 다음 화면(프로필 없음 → 온보딩)으로 넘어간다 → 사용자는 대기를 인지하지 못한다

**완료 조건**: 사용자 식별자가 확보되어 있고, 앱을 껐다 켜도 같은 식별자가 복원된다.

### 유저 플로우 2 - 앱을 다시 켠 사용자의 세션 복원

이미 세션이 있는 사용자가 앱을 다시 켤 때, 네트워크 없이도 즉시 같은 사용자로 이어진다.

**진입 조건**: 앱 재실행. 단말에 이전 실행에서 확보한 세션이 남아 있다.

1. 사용자가 앱을 실행한다 → 진입 화면이 세션 확보를 요청한다
2. 저장된 세션이 복원된다 → 네트워크 왕복 없이 즉시 완료된다
3. 진입 화면이 직전 세션의 메인 탭으로 넘어간다 → 이전에 저장한 방·장소가 그대로 보인다

**완료 조건**: 이전 실행과 동일한 사용자 식별자로 앱이 동작하고, 서버가 그 사용자의 데이터를 돌려준다.

### 유저 플로우 3 - 서버가 요청자를 검증하는 흐름

feature 모듈이 서버 API를 호출할 때, 요청에 위조 불가능한 신원 증명이 실려 나가고 서버가 그것을 검증해 사용자를 특정한다.

**진입 조건**: 세션이 확보된 상태에서 임의의 feature 모듈이 Mino 서버 API를 호출한다.

1. 호출자가 서버 API를 호출한다 → 요청에 현재 세션의 신원 증명이 자동으로 실린다
2. 서버가 신원 증명을 검증한다 → 검증 결과에서 사용자 식별자를 꺼내 요청 주체로 삼는다
3. 서버가 그 사용자의 데이터로 응답한다 → 호출자는 인증을 직접 다루지 않는다

**완료 조건**: 호출자가 인증 코드를 작성하지 않아도 모든 Mino 서버 요청이 검증 가능한 신원 증명을 동반한다.

## 2. 요구사항 (Requirements) *(필수)*

### 2.1 기능적 요구사항 (Functional Requirements)

- **FR-001**: 시스템은 반드시 회원가입·로그인 입력 없이 사용자를 구분할 수 있는 비회원 세션을 발급한다. (근거: PRD §1 핵심 원칙 「비회원 디바이스 세션」, 이슈 #176)
- **FR-002**: 시스템은 반드시 한 번 발급한 세션을 앱 재실행 후에도 유지하며, 재실행 시 네트워크 없이 복원한다. (근거: 이슈 #176 「두 번째 실행부터는 로컬 복원」)
- **FR-003**: 시스템은 반드시 앱 시작 시 첫 서버 요청보다 먼저, 서버 요청과 구분되는 독립 단계로 세션을 확보한다. (근거: 이슈 #176 「호출 위치」)
- **FR-004**: 시스템은 반드시 세션 확보 요청을 멱등하게 처리한다 — 동시에 여러 번 호출해도 세션은 하나만 만들어지고, 이미 확보된 상태에서의 재호출은 네트워크 왕복 없이 즉시 완료된다. (근거: 이슈 #176 「동시 호출로 계정이 중복 생성되지 않게」·「멱등이라 매 실행 호출해도 됨」)
- **FR-005**: 시스템은 반드시 세션 확보 실패를 서버 API 호출 실패와 구분해 사용자에게 알리고, 사용자 조작 없이 세션 확보를 자동으로 다시 시도한다. 확보에 성공하면 추가 조작 없이 원래 흐름을 이어간다. (근거: 이슈 #176 「인증 확보 실패가 API 호출 실패로 뭉뚱그려지면 재시도 안내가 어긋난다」, PRD 5.0.0 [SCR-001] Flow E)
- **FR-006**: 시스템은 반드시 앱 삭제 후 재설치한 사용자를 새 사용자로 취급한다. 이전 세션과 그에 귀속된 데이터의 복구 수단은 제공하지 않는다. (근거: 이슈 #176 트레이드오프 「재설치 시 계정 소멸」)
- **FR-007**: 시스템은 반드시 세션 정보를 자동 백업·기기 이전 대상에서 제외해, 서로 다른 기기가 같은 사용자로 인식되지 않게 한다. (근거: 이슈 #176 완료 조건 「자동 백업 규칙을 실제 정책으로 정리」)
- **FR-008**: 시스템은 반드시 Mino 서버로 나가는 모든 요청에 현재 세션의 신원 증명을 자동으로 첨부하며, 호출하는 feature 모듈이 이를 직접 다루지 않게 한다. (근거: 이슈 #176 「모든 서버 요청에 신원 증명을 자동 첨부」)
- **FR-009**: 시스템은 반드시 앱이 생성한 사용자 식별자를 서버로 전송하지 않는다. 요청 주체의 식별은 서버가 신원 증명에서 도출한다. (근거: 이슈 #176 「앱은 사용자 식별자를 보내지 않는다 — 서버가 신원 증명에서 꺼낸다」)
- **FR-010**: 시스템은 반드시 신원 증명이 제3자에 의해 위조될 수 없는 형태 — 발급자가 서명하고 수신자가 독립적으로 검증할 수 있는 형태 — 로 사용자를 증명한다. (근거: 이슈 #176 「기존 식별자는 서버가 검증할 수 없다 — 식별자이지 자격 증명이 아니다」)
- **FR-011**: 시스템은 반드시 Mino 서버가 아닌 외부 호스트로 나가는 요청에는 신원 증명을 첨부하지 않는다. (근거: 이슈 #176 「남의 서버로 우리 신원 증명이 나가면 안 된다」)
- **FR-012**: 시스템은 반드시 신원 증명의 유효 기간을 스스로 관리해, 만료를 이유로 정상 요청이 실패하지 않게 한다. (근거: 이슈 #176 「만료 전에 갱신되므로 만료를 원인으로 한 요청 실패는 나지 않는다」)
- **FR-013**: 시스템은 반드시 세션 확보·신원 증명 발급 실패를 프로젝트의 기존 도메인 예외 체계로 전파해, 별도의 에러 처리 경로를 만들지 않는다. (근거: 이슈 #176 「실패는 기존 도메인 예외 체계로 전파」, [error_handling.md](../../conventions/error_handling.md))
- **FR-014**: 시스템은 반드시 사용자가 명시적으로 회원 탈퇴를 요청하지 않는 한 세션을 폐기하지 않는다. (근거: 이슈 #176 「익명 세션의 로그아웃은 계정과 데이터를 영구히 잃는 동작이다」)
- **FR-015**: 시스템은 반드시 기존 기기 식별자 기반 사용자 구분 경로를 제거하고, 사용자 구분의 단일 출처를 이 세션으로 둔다. (근거: 이슈 #176 완료 조건 「기존 기기 식별자 기반 경로 제거」)
- **FR-016**: 시스템은 반드시 세션이 확보되기 전에는 사용자를 진입 화면 밖으로 내보내지 않는다. 확보에 실패하면 진입 화면에 머무르며 재시도만 허용하고, 세션 없이 도달할 수 있는 대체 경로를 두지 않는다. (근거: §5 Q1 확정, EC-003)
- **FR-017**: 시스템은 반드시 이용자가 앱을 오랫동안 실행하지 않았다는 이유만으로 익명 세션을 무효화하지 않는다. 세션의 소멸 경로는 앱 삭제(FR-006)와 명시적 회원 탈퇴(FR-014) 둘뿐이다. (근거: §5 Q2 확정, PRD 5.0.0 §1 「설치가 살아 있는 동안 세션은 만료되지 않는다」, EC-006)
- **FR-018**: 시스템은 반드시 세션 확보 실패를 **연결 문제로 인한 실패**와 **그 밖의 실패** 두 가지로 구분해 안내하며, 두 경우에 서로 다른 안내를 노출한다. (근거: PRD 5.0.0 [SCR-001] Flow C·D)
- **FR-019**: 시스템은 반드시 세션 확보가 지연되는 상태를 실패와 구분해 다룬다 — 정상 진행 중임을 사용자에게 알리고, 지연이 정해진 한계를 넘으면 그 밖의 실패(FR-018)로 합류시킨다. 정상·지연·실패를 가르는 구체 임계 시간은 진입 화면 스펙이 정한다. (근거: PRD 5.0.0 [SCR-001] Flow B)

### 2.2 핵심 UX 규칙 (Core UX Rules)

- **UX-001**: 세션 확보에 실패했을 때의 안내는 실패 원인을 사용자가 이해할 수 있는 말로 번역한다 — 연결 문제면 연결 확인을 요청하고, 그 밖의 실패는 일시적인 오류임을 알린다. 어느 경우에도 데이터 조회 실패로 오인될 문구를 쓰지 않는다. (근거: 이슈 #176, PRD 5.0.0 [SCR-001] Flow C·D·E, FR-005, FR-018)
- **UX-002**: 세션 확보 실패 상태에서 복구를 위한 조작을 사용자에게 요구하지 않는다. 재시도 버튼을 두지 않고, 복구는 시스템이 자동으로 수행하며 사용자는 상태를 안내받기만 한다. (근거: PRD 5.0.0 [SCR-001] Flow E, FR-005, EC-002)
- **UX-003**: 세션 확보가 정상 속도로 끝나는 경로에서는 이를 알리는 별도의 화면·문구·로딩 표현을 노출하지 않는다. 확보가 지연될 때만 진행 중임을 알리는 표현을 노출하며(FR-019), 이 표현은 실패 안내와 시각적으로 구분된다. 어느 경우에도 사용자가 비회원 세션의 존재를 인지하게 만들지 않는다. (근거: PRD §1 「비회원 익명 세션」, PRD 5.0.0 [SCR-001] Flow A·B)
- **UX-004**: 재설치로 이전 데이터가 조회되지 않는 상황을 오류로 표현하지 않는다. 데이터가 없는 신규 사용자와 동일하게 취급한다. (근거: FR-006)

### 2.3 주요 도메인 (Core Domain)

- **익명 세션 (Anonymous Session)**: 회원가입 없이 한 명의 이용자를 구분하는 단위. 발급 주체는 인증 제공자이며, 앱은 이를 확보·복원할 뿐 직접 만들지 않는다. 앱 설치 수명과 함께한다 — 재설치 시 새로 발급된다. 향후 실제 계정으로 승격될 수 있다(이번 범위 밖).
- **사용자 식별자 (User Identifier)**: 익명 세션에 부여된 고유 값. 서버가 데이터의 소유자를 판정하는 키다. 앱은 이 값을 서버로 보내지 않으며, 앱 내에서는 크래시 리포트·분석 이벤트를 서버 로그와 대조하는 용도로만 쓴다.
- **신원 증명 (Identity Proof)**: 요청자가 특정 익명 세션의 주체임을 수신자가 독립적으로 검증할 수 있게 하는 증표. 유효 기간이 있고 자동으로 갱신되며, 요청 단위로 첨부된다.

## 3. 범위 (Scope) *(필수)*

### 3.1 측정 가능한 성과 (Measurable Performance)

- **SC-001**: 세션이 이미 확보된 상태(앱 재실행)에서 세션 확보 단계가 네트워크 요청 0회로 완료된다.
- **SC-002**: 최초 실행에서 세션 확보가 진입 화면의 브랜드 노출 시간 안에 끝나는 것이 정상 경로다. 그 시간을 넘긴 경우에는 진행 중임이 표시되어, 사용자가 멈춘 화면으로 오인하는 사례가 0건이다.
- **SC-003**: 서로 다른 단말 100대가 앱을 최초 실행했을 때 서로 다른 사용자 식별자 100개가 생성되고, 중복이 0건이다.
- **SC-004**: 앱을 최초 실행할 때 동시에 발생하는 세션 확보 요청이 몇 건이든 발급되는 사용자 식별자는 1개다.
- **SC-005**: 변조된 신원 증명으로 보낸 요청의 성공률이 0%다.
- **SC-006**: Mino 서버 API를 호출하는 feature 모듈이 인증을 위해 작성하는 코드가 0줄이다.
- **SC-007**: 신원 증명 만료를 원인으로 실패하는 서버 요청이 0건이다.
- **SC-008**: 기기 백업·복원을 거친 단말과 원본 단말이 같은 사용자 식별자를 갖는 사례가 0건이다.
- **SC-009**: 세션이 확보되지 않은 상태에서 진입 화면 밖으로 넘어간 사례가 0건이고, 그 상태로 나간 Mino 서버 요청도 0건이다.
- **SC-010**: 미사용 기간을 이유로 사용자 식별자가 바뀐 사례가 0건이다.
- **SC-011**: 세션 확보 실패에서 복구하기 위해 사용자가 수행해야 하는 조작이 0개다 — 상황이 회복되면 아무것도 누르지 않아도 진입 화면을 통과한다.
- **SC-012**: 세션 확보 실패 안내가 연결 문제와 그 밖의 실패로 구분되지 않은 사례가 0건이다.

### 3.2 비목표 항목 (Out of Scope)

- 실제 계정으로의 승격(소셜 로그인 연동, 계정 연결)과 그때의 사용자 식별자 이관 규칙 — PRD §2 비목표이며, 별도 스펙이 정의한다.
- 재설치·기기 변경 시의 데이터 복구·이관 수단 — 승격 경로가 도입될 때 함께 정의한다.
- 서버의 신원 증명 검증 구현, 사용자 식별자를 키로 하는 데이터 소유권 판정 규칙 — 서버가 소유한다.
- 세션 남용(대량 계정 생성) 방어 정책 — 별도 이슈로 분리되어 있다.
- 푸시 알림 수신 대상을 특정하기 위한 기기 단위 식별 — 이슈 #90이 정의한다. 이 스펙은 사용자 단위 식별만 다룬다.
- 진입 화면(스플래시) 자체의 디자인·전환 규칙, 그리고 세션 확보 상태별 표현의 구체값 — 안내 문구, 정상·지연·실패를 가르는 임계 시간, 표시 위치 — PRD [SCR-001]과 해당 화면 스펙이 정의한다. 이 스펙은 그 화면이 세션 확보를 어느 시점에 부르고 어떤 상태를 구분해야 하는지의 계약만 정한다.
- 서버 요청이 인증 이외의 이유로 거부됐을 때의 처리 — 기존 에러 처리 규약이 정의한다.

## 4. 가정 (Assumptions)

- 사용자는 앱을 처음 실행하는 시점에 네트워크에 연결되어 있다. 연결이 없는 최초 실행은 정상 경로가 아니라 실패 경로로 다룬다(EC-001).
- 서버는 신원 증명을 검증해 사용자 식별자를 도출하는 방식으로 전환할 수 있고, 앱이 보내던 기기 식별자에 더 이상 의존하지 않는다. 이 전환은 서버와 동시에 이뤄진다.
- 사용자 식별의 근거가 "앱이 발급한 기기 식별자"에서 "인증 제공자가 발급한 익명 계정 식별자"로 바뀐다. 이 변경은 PRD 4.2.0에서 §1 핵심 원칙 「비회원 익명 세션」·§2 비목표·[SCR-001]에 반영되었고, 5.0.0에서 실패·지연 상태까지 구체화되었다. 약관·개인정보 처리방침은 그 전제 위에 작성한다 — 본문 개정은 PRD가 미확정으로 남긴 항목이며 이 스펙의 범위가 아니다.
- 세션은 앱의 모든 화면이 전제하는 불변식이다(FR-016). 진입 화면 이후의 어떤 화면도 "세션이 없는 상태"를 표현할 필요가 없다.
- 진입 화면이 세션 확보의 완료·실패를 기다렸다가 다음 화면을 결정한다. 앱 프로세스 시작 시점에 결과를 기다리지 않고 실행하는 방식은 실패를 사용자에게 표시할 수 없으므로 채택하지 않는다.
- 세션 확보 실패 시의 자동 재시도에는 상한을 두지 않는다. 진입 화면을 벗어나는 경로가 세션 확보뿐이므로(FR-016) 재시도를 그만둘 지점이 없다. 재시도 간격은 실패가 이어질수록 늘려 인증 제공자에 부하를 주지 않는 방식을 전제하며, 구체 간격은 요구사항이 아니다.
- PRD 5.0.0에서 [SCR-001]의 상태 구분(정상·지연·연결 실패·그 밖의 실패)과 화면 설계가 확정되었으나 구현은 아직 없다. 그 화면이 만들어지기 전까지는 앱의 실제 진입 지점이 임시로 같은 역할을 맡으며, 스플래시 구현 시 이관된다.
- 기존 기기 식별자 기반 경로는 현재 어떤 화면에서도 사용되지 않으므로, 제거해도 기존 사용자 경험이 변하지 않는다.
- 신원 증명과 그 갱신 수단의 저장·만료·갱신은 인증 제공자가 관리한다. 앱은 이를 따로 저장하지 않는다 — 저장을 이중화하면 어느 쪽이 맞는지 판정할 수 없게 된다.
- 이 스펙이 정의하는 세션은 이용자 1명 단위다. 한 이용자가 여러 기기를 쓰는 상황은 이번 범위에서 다루지 않는다.

- **Q1 (사용자 경험)** : 최초 실행에서 세션 확보에 실패했을 때 사용자를 어디까지 들여보내는가 — 진입 화면에서 차단하고 재시도만 허용하는가, 제한된 화면만 여는가, 그대로 진행시키고 화면마다 실패시키는가?
  -> **A** : 진입 화면에서 차단한다. "세션은 항상 확보되어 있다"를 앱 전체의 불변식으로 두어, 실패 표현이 진입 화면 한 곳에만 존재하게 한다. 복구 수단은 PRD 5.0.0에서 **사용자가 누르는 재시도 버튼이 아니라 자동 재시도**로 확정되었고, 1.2.0에서 이를 반영했다. → FR-005, FR-016, EC-002, EC-003, TS-018, TS-021, SC-009, SC-011
