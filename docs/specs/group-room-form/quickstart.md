# 검증 가이드: 공동방 생성 및 편집 폼

**대상 스펙 경로**: `docs/specs/group-room-form` · **부속 문서**: [plan.md](./plan.md)

이 기능이 엔드투엔드로 동작함을 증명하는 실행 시나리오다. 구현 세부는 담지 않는다 — 타입과 계약은 [data-model.md](./data-model.md)·[contracts/](./contracts/)를 본다.

---

## 1. 선행 조건

| 항목 | 값 |
|---|---|
| 모듈 | `:feature:roomform`이 `settings.gradle.kts`와 `:app`에 등록되어 있다 |
| 서버 | **실서버를 쓴다.** `qa` flavor의 `API_BASE_URL`이 가리키는 곳이며, 계약은 [contracts/room-api.md](./contracts/room-api.md)가 소유한다 |
| 진입점 | `:feature:main`의 임시 검증 배선. 실제 진입점 feature는 아직 없다([plan.md](./plan.md) §범위 경계) |
| 시드 | **없다.** 편집 경로는 S-1에서 만든 방의 `roomId`로 진입한다 |

> [!WARNING]
> **세션·유저 등록이 배선되기 전에는 S-1~S-9가 전부 막힌다.** 익명 세션이 없으면 요청이 나가기 전에 `IllegalStateException`으로 끊기고, 세션이 있어도 서버에 유저가 등록되어 있지 않으면 `401 USER_NOT_REGISTERED`다. 둘 다 이 계획이 만드는 것이 아니다 — [contracts/room-api.md](./contracts/room-api.md) §7 · [research.md](./research.md) R-028 · [plan.md](./plan.md) §열린 항목 H.
>
> 그때까지의 검증은 **단위 테스트(§4)와 빌드**까지다. 시나리오가 401로 막히는 것은 이 feature의 결함이 아니며, **그 사실을 확인한 것만으로 S-1~S-9를 통과로 적지 않는다.**

## 2. 실행

```bash
# 빌드 (헌법이 정한 빌드 확인의 최소선)
./gradlew :app:assembleQaDebug

# 단위 테스트
./gradlew :core:domain:test :core:data:testQaDebugUnitTest :feature:roomform:testQaDebugUnitTest

# 설치·실행
./gradlew :app:installQaDebug
```

## 3. 시나리오

각 시나리오의 `TS-*`·`EC-*`는 [spec.md](./spec.md)의 번호다.

### S-1. 생성 — 입력에서 저장까지 (TS-001·TS-002·TS-005·TS-006·TS-012·TS-030·TS-031·TS-044·TS-045)

1. 임시 진입점에서 폼을 연다 → 타이틀이 `공동방 만들기`, 미리보기 카드에 **회색 썸네일**과 `방 이름을 입력해 주세요.` / `어떤 장소들을 모으는 방인가요?`가 보이고, 방 이름에 `*`가 붙으며 CTA `방 생성하기`가 **비활성**이다.
2. 비활성 CTA를 눌러 본다 → 아무 일도 일어나지 않는다 (TS-038).
3. 방 이름에 `민호야 잘하자`를 입력한다 → 미리보기 이름이 같은 값으로 바뀌고 CTA가 **활성**이 된다. **방 이름에는 카운터가 없다** — 상한 안내는 필드 아래 문구가 대신한다 (TS-045).
4. 방 설명에 `팀 회식 장소 모음`(공백 포함 10자)을 입력한다 → 카운터가 `10/30`, 미리보기 설명이 바뀐다.
5. `cyan` 칩을 누른 뒤 `red` 칩을 누른다 → 체크가 하나만 남고 미리보기 썸네일의 색과 캐릭터가 함께 바뀐다 (TS-029).
6. 방 이름을 전부 지운다 → 미리보기가 안내 문구로 되돌아가고 CTA가 비활성이 된다 (TS-005).
7. 다시 이름을 채우고 [방 생성하기]를 누른다 → **방이 만들어지지 않고** `공동방을 저장하시겠어요?` 모달이 뜬다 (TS-030).
8. [취소]를 누른다 → 모달만 닫히고 입력값이 그대로다 (TS-031).
9. 다시 CTA → [저장하기] → 폼이 닫히고 진입점 화면으로 돌아온다.

**기대**: 임시 진입점이 결과 `created`와 `roomId`를 받아 그 값을 화면에 표시한다. 스낵바 문구·도착점은 진입점 feature의 몫이라 이 범위에서 검증하지 않는다([plan.md](./plan.md) §범위 경계).

### S-2. 입력 상한과 오류 (TS-003·TS-004·TS-008·TS-009·TS-010·TS-011·EC-002·EC-005·EC-006·EC-025)

1. 방 이름에 16자를 입력한다 → **16번째 글자가 들어가지 않고 화면의 방 이름은 15자 그대로다** (TS-003).
2. 20자를 붙여넣는다 → 앞 15자만 반영된다 (EC-002).
3. 방 이름을 `민호야 잘하자^^`로 만든다 → 필드가 오류 상태가 되고 아래 문구가 `한글·영문·숫자만 입력 가능해요. (공백 포함 15자 이내)`로 오류 색이 된다. **상단 배너·토스트는 없다** (TS-011).
4. 그 상태에서 설명과 색상을 채운다 → CTA는 계속 비활성이다 (TS-009).
5. `^^`를 지운다 → 오류가 풀리고 CTA가 활성이 된다 (TS-010).
6. 방 이름에 이모지를 넣는다 → 오류 상태다 (EC-005).
7. 방 이름을 `ㄱㄱㄱ`으로 만든다 → 오류가 아니다 (EC-025). 한글을 치는 동안에도 오류가 번쩍이지 않는지 함께 본다.
8. 방 설명에 `!!!`를 넣는다 → 오류가 아니다 (EC-006).
9. 방 설명에 31자를 입력한다 → 30자에서 멈추고 카운터가 `30/30`을 유지한다 (TS-004).

### S-3. 편집 (TS-018·TS-019·TS-020·TS-044·EC-011·EC-019)

**선행**: S-1이 방을 하나 만들어 두었고, 임시 진입점이 그 `roomId`를 들고 있다. 시드가 없으므로 **S-1 없이 S-3을 먼저 돌릴 수 없다.**

1. 임시 진입점에서 S-1이 만든 방의 `roomId`로 폼을 연다 → 타이틀이 **`방 편집`**, 이름 `민호야 잘하자` · 설명 `팀 회식 장소 모음` · `red` 선택 상태로 열리고 설명 카운터가 `10/30`, CTA 라벨이 `방 편집 완료`다. 우상단에 액션이 없다.
2. 이름을 모두 지운다 → CTA가 비활성이 된다 (TS-020).
3. 이름을 `야호야호`로 고치고 색을 `blue`로 바꾼다 → 미리보기 썸네일의 캐릭터가 함께 바뀐다 (EC-019).
4. [방 편집 완료]를 누른다 → **저장 확인 모달 없이** 폼이 닫힌다 (TS-019).
5. 다시 같은 방의 편집 폼을 연다 → 방금 고친 값으로 **서버에서 다시 읽어** 채워져 있다. mock과 달리 이 왕복이 실제 `PATCH` → `GET`이므로, **여기서 값이 되돌아 있으면 저장이 서버에 닿지 않은 것이다.**
6. **설명을 전부 지우고** [방 편집 완료] → 다시 열어 설명이 비어 있는지 본다. 비어 있지 않으면 `description`이 요청 본문에서 빠진 것이다 ([research.md](./research.md) R-027).
7. 아무것도 고치지 않고 CTA를 누른다 → 그대로 닫힌다 (EC-011).

### S-4. 이탈 — 생성 (TS-025·TS-028·TS-034·TS-035·EC-020·EC-021·EC-022)

1. 폼을 열고 아무것도 입력하지 않은 채 뒤로가기 → **모달 없이** 즉시 닫힌다 (TS-028).
2. 다시 열어 이름 `야호`를 입력하고 뒤로가기 → `공동방 만들기 화면에서 나가시겠어요?` 모달이 뜬다 (TS-025).
3. [취소] → 모달만 닫히고 `야호`가 남아 있다 (TS-034).
4. 다시 뒤로가기 → 모달에서 **딤 바깥**을 탭한다 → [취소]와 같게 동작한다 (UX-009·EC-022).
5. 다시 뒤로가기 → **OS 뒤로 제스처**로 모달을 닫는다 → 역시 [취소]와 같다 (EC-022).
6. 다시 뒤로가기 → [나가기] → 방이 만들어지지 않은 채 닫힌다 (TS-035).
7. 이름을 지우지 않고 **색상만** 고른 뒤 뒤로가기 → 모달이 뜬다 (EC-020).
8. 입력했던 값을 모두 지운 뒤 뒤로가기 → 모달 없이 닫힌다 (EC-021).

### S-5. 이탈 — 편집 (TS-039·TS-040·TS-041·TS-042·TS-043·EC-023·EC-024)

1. S-1이 만든 방의 편집 폼을 열고 아무것도 고치지 않은 채 뒤로가기 → 모달 없이 닫힌다 (TS-042).
2. 이름을 `야호야호`로 고치고 뒤로가기 → `공동방 **편집** 화면에서 나가시겠어요?` 모달이 뜬다. 생성용 문구가 아니다 (TS-039).
3. [취소] → 고치던 값이 남는다 (TS-040). [나가기] → 방 정보가 편집 전 그대로다 (TS-041).
4. 이름을 고쳤다가 원래 값으로 되돌린 뒤 뒤로가기 → **모달이 뜨지 않는다** (TS-043).
5. 색상만 다른 색으로 바꾸고 뒤로가기 → 모달이 뜬다 (EC-023).
6. 이름을 모두 지워 CTA가 비활성인 상태로 뒤로가기 → 모달이 뜬다 (EC-024).

### S-6. 온보딩 chrome (TS-023·TS-024·TS-026·EC-015)

1. 임시 진입점의 "온보딩으로 열기"로 폼을 연다 → 우상단에 [건너뛰기]가 보이고 **좌상단 뒤로가기가 없다** (TS-026).
2. OS 뒤로 제스처를 쓴다 → 폼을 벗어나지 못한다 (EC-015).
3. [건너뛰기]를 누른다 → 확인 없이 닫히고 결과가 `skipped`다 (TS-024).
4. 온보딩이 아닌 진입으로 다시 연다 → [건너뛰기]가 없고 뒤로가기가 보인다 (TS-023).

### S-7. 스크롤과 고정 CTA (UX-005·EC-004)

1. 작은 화면(또는 글꼴 크기가 큰 기기)에서 폼을 연다 → 입력 영역이 세로로 스크롤되고 CTA는 하단에 계속 보인다.

### S-8. 중복 제출 (UX-001·SC-005)

1. 네트워크 왕복 동안 저장 확인 모달의 [저장하기]를 빠르게 여러 번 누른다 → 방이 하나만 만들어진다 (EC-008). **실서버에서는 중복 생성이 서버에 남으므로, 실패하면 방 목록에 같은 이름이 여러 개 쌓인 것으로 확인된다.**
2. 편집 CTA도 같게 확인한다.

### S-9. 서버 계약 확인 ([contracts/room-api.md](./contracts/room-api.md) §2)

**서버 계약의 어긋남이 0건이 됐다.** 색 계약은 `enum` 배포로 확정됐고(2026-08-28T00:55 · R-030), 마지막 한 건인 방 설명 길이는 **2026-08-31T12:51 재조회에서 상한 자체가 제거되며 닫혔다**(R-035). 이 시나리오는 이제 **전부 통과해야 하는 확인**이다.

1. 대표 색상 `red orange`를 골라 방을 만들고 폼을 다시 연다 → **유지되어야 한다.** `color.maxLength`가 제거됐으므로 실패하면 우리 식별자가 `enum`과 다른 것이다.
2. `light blue`도 같게 확인한다.
3. 색을 고르지 않고 방을 만든 뒤 다시 연다 → 회색이 유지되어야 한다. **`RoomMapper`가 `"gray"`를 보내는지 확인하는 유일한 경로다** — 서버 `enum`에 `"grey"`는 없으므로 철자가 틀리면 요청이 거절된다.
4. 방 설명에 **25자**를 입력해 저장한다 → **성공해야 한다.** 서버가 `description`의 상한을 걷어냈으므로 21~30자가 더는 거절되지 않는다. 실패하면 서버 스키마가 다시 바뀐 것이니 [contracts/room-api.md](./contracts/room-api.md) §1의 인용을 재조회로 대조한다.
5. 방 이름에 자모 단독(`ㄱㄱㄱ`)을 넣어 저장한다 → **성공해야 한다.** 서버 `pattern`이 자모 구간을 허용하므로 FR-004·EC-025와 어긋나지 않는다(R-035). 거절되면 서버 `pattern`이 좁아진 것이다.

**1~5가 전부 통과해야 한다.** 서버 배포를 기다리는 항목은 더 없다.

### S-10. 합병 회귀 — 방 선택 시트가 그대로 동작한다 ([research.md](./research.md) R-032)

3.0.0이 `RoomListRemoteDataSource`를 `RoomRemoteDataSource`로 흡수한다. **그 경로를 무는 것은 이 폼이 아니라 다른 feature다** — `:feature:sharereceiver`의 방 선택 시트가 `getRooms()`로 목록을 그린다. 합병이 그 화면을 깨뜨리지 않았는지는 이 폼을 아무리 눌러도 드러나지 않으므로 별도 시나리오로 세운다.

1. 외부 앱에서 링크를 공유해 방 선택 시트를 연다 → **참여 중인 방 목록이 그대로 그려져야 한다.** 목록이 비면 합병 과정에서 `listRooms()`의 경로나 봉투 해제가 깨진 것이다.
2. 시트에서 개인방이 **최상단**에 있는지 본다 → 정렬 판정은 UseCase의 몫이고 합병이 건드리지 않는다. 순서가 뒤집혔다면 Repository가 받은 순서를 보존하지 않는 것이다.
3. S-1로 방을 새로 만든 뒤 시트를 다시 연다 → **새 방이 목록에 있어야 한다.** 폼과 시트가 같은 DataSource를 무는 것을 확인하는 유일한 경로다.

> [!IMPORTANT]
> **세션이 배선되기 전에는 1~3도 401로 막힌다.** 그때는 이미 있는 `RoomApiServiceTest`의 **기존 케이스가 그대로 통과하는지**로 대신한다 — 그 테스트가 `listRooms()`의 경로·봉투 해제·기본값 흡수를 덮고 있고, 합병으로 그 케이스를 고쳐야 했다면 동작이 바뀐 것이다.

## 4. 통과 판정

| 축 | 판정 기준 | 누가 |
|---|---|---|
| 빌드 | `./gradlew :app:assembleQaDebug` 성공 | 구현자 |
| 단위 테스트 | `ValidateRoomNameUseCase`·`RoomFormViewModel` 전부 통과. 대상 목록은 [contracts/room-repository.md](./contracts/room-repository.md) §2 · [contracts/room-form-ui.md](./contracts/room-form-ui.md) §5 | 구현자 |

| 서버 계약 | S-9 — **1~3은 통과해야 하고**, 4는 서버 배포 전이면 "대기"로 적는다 | 구현자 |
| 합병 회귀 | S-10 — 세션 배선 전이면 **기존 `RoomApiServiceTest` 케이스 무수정 통과**로 대신한다 | 구현자 |
| 디자인 일치 | 노드 대조 결과를 `<노드 ID> \| 대조: <변수명>=<값> … \| <불일치>` 형식으로 제출 | Figma를 조회할 수 있는 검수자 |
| 모듈 경계 | [contracts/room-form-launcher.md](./contracts/room-form-launcher.md) §5의 세 확인 | 리뷰 |

**빌드·테스트 통과를 디자인 일치의 근거로 삼지 않는다** — 게이트가 그 축을 전혀 검사하지 않는다([figma-design-fidelity §6](../../conventions/figma-design-fidelity.md)).

## 5. 이 가이드가 검증하지 **않는** 것

| 항목 | 왜 | 어디서 검증되는가 |

| FR-011 진입점별 도착점 · FR-012·FR-015 완료 스낵바 | 도착점 feature가 없다 | 각 진입점 feature의 spec |
