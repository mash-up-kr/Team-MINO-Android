# 검증 가이드: 알림함 (Notifications)

**대상 스펙**: [spec.md](./spec.md) 7.0.0 · **계획**: [plan.md](./plan.md)

기능이 엔드투엔드로 동작함을 증명하는 절차다. 계약과 데이터 모델의 세부는 반복하지 않고 링크로 지목한다.

---

## 1. 선행 조건

- 기기·에뮬레이터에서 앱을 설치하고 프로필 설정까지 마친 상태([SYS-011]). 알림 목록은 익명 세션 인증을 타므로 미등록 상태에서는 401이 온다.
- 서버 `https://api.gguk.org`에 닿는 네트워크.
- **알림이 실제로 쌓인 계정.** 알림을 만드는 것은 서버이므로 클라이언트에서 생성할 수 없다. 아래 §2로 만든다.

## 2. 검증 데이터 만들기

| 유형 | 만드는 법 |
|---|---|
| 중복 저장 | 외부 앱에서 링크를 공유해 이미 그 장소가 있는 방을 골라 저장([SYS-002]). 또는 홈 카드 `[...]` → `다른 방 저장`에서 이미 저장된 방 선택([SCR-003] Flow C) |
| 저장 오류 | 장소를 특정할 수 없는 게시물(사진만 있는 글, 해외 장소)을 공유 |
| 공동방 참가 ①② | 초대 링크로 다른 계정을 방에 합류시킨다([SYS-010]) |
| 위치 기반 · 코멘트 기반 | **클라이언트에서 만들 수 없다.** 서버 발송 주기에 달렸다(spec §3.2) |

FR-021 검증(§3.2)에는 **한 번의 저장에서 여러 방이 중복인 상황**이 필요하다 — 같은 장소가 이미 있는 방을 두 개 이상 골라 한 번에 저장한다.

## 3. 빌드와 실행

```sh
./gradlew :app:assembleQaDebug
```

헌법 §개발 워크플로가 정한 빌드 확인의 최소선이다. `lintDebug`는 JBR JIT 이슈로 데몬이 죽을 수 있으며, 돌린다면 `-XX:-TieredCompilation`으로 회피한다.

단위 테스트:

```sh
./gradlew :feature:notifications:testDebugUnitTest :core:domain:test
```

## 4. 검증 시나리오

### 4.1 목록 조회 — 유저 플로우 1

바텀 네비게이션 세 번째 `알림` 탭 진입.

| 확인 | 기대 | spec |
|---|---|---|
| 정렬 | 가장 최근 알림이 맨 위 | TS-001 |
| 행 구성 | 썸네일·유형 문구·대상 이름·경과 시간 네 요소 | TS-002 |
| 6종 문구 | 각 행의 문구가 FR-004 표와 **글자까지 일치** | TS-003, SC-003 |
| 경과 시간 | `방금` / `N시간 전` / `N일 전` / `N월 N일` 네 구간 | TS-004~007, SC-005 |
| 읽음 무구분 | 눌러 본 행과 안 눌러 본 행이 어떤 요소로도 다르지 않다 | TS-032 |
| 탭 배지 없음 | `알림` 탭에 건수 배지·점 없음 | TS-033 |
| 권한 배너 없음 | OS 알림 권한을 끈 상태로도 목록이 화면 최상단부터 시작 | TS-035 |
| 최상단 시작 | 첫 진입은 목록 맨 위 | spec §4 |

> **문구 일치(SC-003)는 클라이언트 테스트로 지킬 수 없다.** 서버 `typeLabel`을 그대로 그리므로([research.md D4](./research.md)) 여기서 눈으로 확인하는 것이 유일한 게이트다.

### 4.2 썸네일 두 갈래 — FR-012

6.0.0에서 바뀐 항목이라 별도로 본다.

| 유형 | 기대 | spec |
|---|---|---|
| 저장 오류 | 오류 아이콘 이미지 | TS-010 |
| 나머지 5종 | 서버가 준 `thumbnailUrl`. 없으면 플레이스홀더 | TS-009 · TS-054 |

**공동방 참가 행에 무엇이 오는지를 본다.** 서버가 그 방의 이미지를 실어 주는지, `null`이라 플레이스홀더가 서는지 확인한다 — 어느 쪽이든 화면이 깨지지 않아야 하고, 방 목록을 부르는 요청이 나가지 않아야 한다([research.md D5](./research.md)).

> `null`이 흔하다면 디자인이 그 결과를 받아들일지 확인이 필요하다. 방 대표 색상+캐릭터는 6.0.0에서 포기한 값이다(spec §5 Q13).

### 4.3 묶음 — FR-021

같은 장소가 이미 있는 방 2개 이상을 한 번에 골라 저장한 뒤 알림 탭 진입.

| 확인 | 기대 | spec |
|---|---|---|
| 행 수 | 방이 몇 개 중복이든 **그 장소에 대한 행은 1개** | TS-045, SC-013 |
| 대상 이름 | 장소명만. 방 이름도 방 개수도 붙지 않는다 | TS-046 |
| 다른 시도 | 시각을 달리해 두 번 시도하면 행 2개 | TS-052 |
| 홈 경로 | 홈 `다른 방 저장`으로 낸 중복도 외부 공유와 같은 문구·같은 묶음 | EC-026 |

> **묶는 것은 서버다**(spec §4). 여기서 행이 방 수만큼 나오면 클라이언트 결함이 아니라 [contracts/notification-api.md §4](./contracts/notification-api.md)의 협의 항목 3번이 미해결인 것이다.

### 4.4 페이징 — FR-018

알림이 21건 이상인 계정.

| 확인 | 기대 | spec |
|---|---|---|
| 첫 묶음 | 20건만 표시 | TS-036 |
| 이어 붙이기 | 끝까지 스크롤하면 **조작 없이** 다음 묶음이 붙고, 보던 행의 위치가 흔들리지 않는다 | TS-037, UX-011 |
| 끝 도달 | 더 붙지 않고 오류·빈 상태로 바뀌지 않는다 | TS-038, EC-018 |
| 추가 실패 | 비행기 모드로 끊고 끝까지 스크롤 → **이미 본 20건이 남은 채** 목록 끝에만 재시도 표시 | TS-039, EC-016 |
| 전체 도달 | 스크롤만으로 끝까지 | SC-010 |

### 4.5 빈 상태와 오류 — FR-006 · UX-002

| 확인 | 기대 | spec |
|---|---|---|
| 빈 상태 | 알림 0건 계정에서 스팟 일러스트 + `받은 알림이 없어요` | TS-008, SC-008 |
| 로딩 중 | 조회하는 동안 **빈 상태 문구가 보이지 않는다** | UX-001 |
| 오류 | 비행기 모드로 진입 → 빈 상태가 아니라 재시도 가능한 오류 | EC-001, UX-002 |
| 권한 없는 빈 상태 | 알림 권한 거부 + 0건 → 권한 유도 없이 빈 상태만 | EC-015 |

### 4.6 이동과 나가기 — 유저 플로우 2

| 확인 | 기대 | spec |
|---|---|---|
| 장소 대상 → 상세 | 중복 저장·위치 기반·코멘트 기반 탭 → 그 장소의 상세 | TS-020~022 |
| 방 선택 없음 | 여러 방에 저장된 장소도 **방을 고르는 단계 없이** 바로 열린다 | TS-048, SC-004·SC-014 |
| 몰입 진입 | 도착한 화면에 바텀 네비게이션이 보이지 않는다 | TS-042 |
| 대상 소멸 | 삭제된 장소의 알림 탭 → 이동하지 않고 목록에 머문 채 안내 | EC-009, UX-006 |
| 중복 탭 | 빠르게 두 번 탭 → 한 번만 이동 | EC-011 |
| 재탭 | 눌러 본 알림을 다시 탭 → 같은 동작, 행 표시도 그대로 | EC-012 |
| 탭 복귀 | 빠져나온 뒤 `알림` 탭 재선택 → 직전 스크롤 위치 | TS-043, TS-011 |

### 4.7 저장 오류 안내 — 유저 플로우 3

| 확인 | 기대 | spec |
|---|---|---|
| 진입 | 저장 오류 알림 탭 → `확인해주세요` + 3줄 안내 + 스팟 일러스트 | TS-025, TS-028 |
| **바텀 네비게이션 유지** | 안내 화면에서도 계속 보이고 `알림` 탭이 선택 상태 | TS-030 |
| 뒤로가기 | 상단 뒤로가기 → 알림 목록 | TS-029 |
| 시스템 뒤로가기 | 같은 결과 | EC-014 |
| 다른 탭 이탈 | `홈` 갔다 `알림` 복귀 → 안내 화면이 아니라 **목록** | TS-031, UX-008 |
| 여러 건 | 어느 저장 오류를 눌러도 같은 화면 | EC-013 |

### 4.8 성능

| 확인 | 기대 | spec |
|---|---|---|
| 첫 화면 | 탭을 누르고 2초 이내 | SC-001 |
| 스크롤 | 눈에 띄는 끊김 없음 | SC-002 |

SC-001은 **알림 목록 한 요청에만 걸린다**([research.md D5](./research.md) 폐기). 알림 탭 진입에서 나가는 서버 요청이 그 하나뿐인지도 함께 확인한다.

## 5. 이번 구현에서 검증되지 않는 것

아래는 결함이 아니라 **선행 spec·서버 대기**로 성립하지 않는 항목이다. 근거 없이 통과 처리하지 않는다.

| 항목 | 사유 |
|---|---|
| TS-027 · TS-041 · EC-021 · EC-022 (장소 상세·방 상세의 나가기) | 나가기 규칙의 소유자가 [SCR-006]·[SCR-005]다(FR-020, spec §3.2). 알림함이 검증할 대상이 아니다 — 다만 `PlaceDetailEntryOrigin.NOTIFICATION`이 홈과 다른 갈래를 타는지는 눈으로 본다 |
| TS-012 (위치 권한 미허용 시 위치 기반 알림 없음) | 서버가 걸러 내려주므로 클라이언트에 판정이 없다. 서버 동작 확인 항목이다 |
| TS-040 · EC-002 (대표 알림이 목록에 없음) | 서버 `type` enum에 대표 알림 값이 아예 없어 **구조적으로 실릴 수 없다**([contracts/notification-api.md §1](./contracts/notification-api.md)). 재현할 상태가 없다 |
| SC-012 (진입 경로에 따른 나가기 차이 없음) | 알림·지도 마커·방 상세 목록 셋이 같은 갈래(방 상세로 나감)를 타는지는 place-detail이 이미 검증한다. 알림함이 더하는 것은 `NOTIFICATION`을 싣는 배선 하나다 |
| EC-009 · EC-010 (대상 소멸 시 도착지 화면이 알린다) | spec 7.0.0이 이 판정을 [SCR-006]·[SCR-005]의 몫으로 옮겼다. **알림함이 검증할 것은 「이동은 평소대로 일어난다」까지**이며, 그 화면이 무엇을 보여주는지는 그쪽 spec의 과제다(spec §5 Q14) |

## 6. 확인이 끝나면

- [contracts/notification-api.md §3](./contracts/notification-api.md)의 서버 협의 항목 2건(썸네일·묶음) 중 실제로 드러난 것을 서버팀에 전달한다.
- push-notification spec의 EC-012 단서(「표시 기준 방과 달라도 그대로 연다」)를 그쪽 개정 대상으로 올린다 — 비교 대상이던 앱 안 경로의 표시 기준 방 판정이 사라졌다([research.md 「인접 spec에 전할 것」](./research.md)).
