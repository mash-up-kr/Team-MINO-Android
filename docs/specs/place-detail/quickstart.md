# 검증 가이드: 장소 상세 & 코멘트 (Place Detail & Comments)

**대상 스펙 경로**: `docs/specs/place-detail`

**계획서**: [plan.md](./plan.md)

이 문서는 **기능이 엔드투엔드로 동작함을 증명하는 절차**다. 계약과 데이터 형태는 [contracts/](./contracts/)·[data-model.md](./data-model.md)가 소유하므로 여기서 되풀이하지 않는다.

---

## 1. 선행 조건

- Android 기기 또는 에뮬레이터 (`minSdk` 이상), 네트워크 연결
- 서버 <https://api.gguk.org> 접근 가능 — **이번 라운드는 실 API 연결이라 Fake로 대체되지 않는다**
- 위치 권한을 허용할 수 있는 상태 (FR-002 카메라 이동 확인용)
- **계정 상태**: 온보딩을 마쳐 개인방이 있고, 공동방이 **2개 이상**이며, 그중 **한 장소가 두 방 모두에 저장돼 있어야 한다.** [저장된 방] 전환(FR-023~025)은 이 조건에서만 활성이다

---

## 2. 빌드 · 실행

```sh
./gradlew :app:assembleDebug
./gradlew :app:installDebug
```

**모듈 구성이 바뀌었는지 먼저 확인한다** — 편입([research.md D17](./research.md))으로 `:feature:placedetail`이 사라져야 한다.

```sh
./gradlew projects | grep -i placedetail   # 출력이 없어야 한다
grep -rn "placedetail" settings.gradle.kts app/build.gradle.kts   # 남은 참조가 없어야 한다
```

---

## 3. 품질 게이트

```sh
./gradlew :core:domain:test :core:data:test :feature:room:test
./gradlew lintDebug -Dorg.gradle.jvmargs="-XX:-TieredCompilation"
```

> `lintDebug`의 JVM 플래그는 로컬 JBR 크래시 회피용이다. 빼면 Compose Lint 위반을 놓친다.

## 4. 시나리오 A — 저장 탭 안에서의 진입과 복귀 (FR-001·FR-002·FR-009)

가장 중요한 검증이다. **구조 전환의 성패가 여기서 갈린다.**

| # | 조작 | 기대 결과 | 근거 |
|---|---|---|---|
| 1 | 저장 탭 → 방 A 카드 탭 | 방 상세 `Half`. 지도는 그대로 | 기존 |
| 2 | 지도의 장소 마커 탭 | **지도가 다시 그려지지 않는다** — 타일이 깜빡이거나 하얗게 비지 않고, 카메라만 그 장소로 부드럽게 이동한다 | **FR-002 · D17의 핵심** |
| 3 | 같은 순간 | 마커가 선택 핀으로 바뀌고 색은 방 A의 대표 색 | FR-002, TS-002 |
| 4 | 시트 확인 | `Half` 369dp. 등록자 아바타 + **등록자 닉네임** + [나가기]가 한 줄, 그 아래 장소명·주소 각 한 줄 | FR-003, **FR-005**, TS-001·TS-003 |
| 5 | 헤더 확인 | **장소분류 라벨·`저장한 지 N일째`·카테고리가 어디에도 없다** | **FR-005**, TS-008 |
| 6 | 바텀 네비게이션 | 보이지 않는다 | FR-020, TS-010 |
| 7 | [나가기] 탭 | **방 A의 방 상세 `Half`로 돌아간다.** 지도는 여전히 재생성되지 않는다 | FR-009, TS-006 |
| 8 | 다시 열고 시트를 아래로 드래그 | [나가기]와 같게 방 상세로 복귀 | EC-003 |
| 9 | 다시 열고 시스템 뒤로가기 | 방 상세로 복귀. 한 번 더 누르면 방 리스트 | [place-detail-entry.md §4](./contracts/place-detail-entry.md) |

**2번에서 지도가 깜빡이면 편입이 제대로 안 된 것이다.** 장소 상세가 자기 지도를 그리고 있다는 뜻이다.

## 5. 시나리오 B — 홈 탭에서의 진입 (FR-009·FR-027)

plan 1.1.0에서 **부채로 남아 있던 경로**다. 이번 라운드가 닫는다.

| # | 조작 | 기대 결과 | 근거 |
|---|---|---|---|
| 1 | 홈 탭 → 방 A의 카드 덱에서 카드 본문 탭 | 저장 탭으로 전환되며 방 A 기준 장소 상세 `Half`가 열린다. 카드는 넘어가지 않는다 | TS-036 |
| 2 | [나가기] 탭 | **홈 탭이 아니라 방 A의 방 상세 `Half`** | **FR-009, TS-037** |
| 3 | 다시 홈 탭 → 다른 카드 탭 | 새 장소의 상세가 열린다(직전 요청이 남아 같은 장소가 다시 열리지 않는다) | [place-detail-entry.md §3.1](./contracts/place-detail-entry.md) — `consume()` |
| 4 | 홈 탭 → 카드 탭 → [나가기] → 홈 탭으로 이동 | 홈의 덱 위치가 보존돼 있다 | `restoreState` 유지 확인 |

**2번이 plan 1.1.0에서는 홈으로 돌아갔다.** 그것이 이번 구조 전환의 직접적 성과다.

**4번은 요청 홀더를 고른 이유를 검증한다** — Route 인자 확장이었다면 `restoreState`를 끄면서 이 보존이 깨졌을 자리다([research.md D18](./research.md)).

## 6. 시나리오 C — 코멘트 (FR-010·FR-013·FR-014·FR-015·**FR-028**)

> 3~6번은 서버에 각 구간에 걸치는 `createdAt`의 코멘트가 있어야 한다. 기준 시각은 주입한 `Clock`이 공급하므로([main-contract §6.1](./contracts/place-detail-main-contract.md)), 육안 검증이 어려운 구간은 `PlaceDetailClockModule`이 제공하는 `Clock`을 고정 시각으로 바꿔 끼워 확인할 수 있다.

| # | 조작 | 기대 결과 | 근거 |
|---|---|---|---|
| 1 | 시트를 위로 한 번 드래그 | `Full`로 올라가며 코멘트 영역까지 도달 | SC-001 |
| 2 | 코멘트 목록 확인 | 오래된 것이 위. 각 항목에 작성자 아바타·닉네임·본문 + **우측 아래에 작성 시각** | FR-010, **FR-028**, TS-018 |
| 3 | 방금 쓴 코멘트 확인 | **`방금`** | TS-050 |
| 4 | 3시간 전 코멘트 | **`3시간 전`** | TS-051 |
| 5 | 3일 전 코멘트 | **`3일 전`** | TS-052 |
| 6 | 7일 이상 지난 코멘트 | **`NNNN년 NN월 NN일`** (`2027.01.01` 같은 점 구분자가 아니다) | TS-053 |
| 7 | 입력창에 글을 쓰고 [등록] | 목록 끝에 붙고 입력창이 비며 **시각이 `방금`** | FR-014, TS-054 |
| 8 | 201자째 입력 시도 | 받아들여지지 않는다 | FR-012, EC-011 |
| 9 | 공백만 입력 | [등록] 비활성 | EC-012 |
| 10 | 내 코멘트 [⋮] → [댓글 삭제] | 목록에서 사라진다 | FR-015 |
| 11 | 남의 코멘트 | [⋮]가 없다 | FR-015 |
| 12 | 목록 최상단까지 스크롤 | 더 오래된 페이지가 **앞에** 붙는다 | FR-010, [comment-api.md §1.2](./contracts/comment-api.md) |
| 13 | `59분 전` 코멘트를 띄운 채 1분 넘게 그대로 둔다 | 표기가 `1시간 전`으로 **저절로 바뀌지 않는다.** 목록을 다시 그려야 갱신된다 | EC-028, [main-contract §6.1](./contracts/place-detail-main-contract.md) |

**3~6번의 시각 데이터를 만들려면** 서버에 시점이 다른 코멘트가 필요하다. 즉시 만들 수 없으면 기기 시각을 앞으로 돌려 구간을 넘긴 뒤 화면을 다시 그려 확인한다 — 그때 **이미 떠 있는 목록이 실시간으로 바뀌지 않는 것**도 함께 본다(EC-028).

**plan 1.1.0에서 구현 보류였던 기능이다.** 선행 조건(§1)의 "두 방에 저장된 장소"가 필요하다.

## 10. 회귀 확인 — 편입이 기존 화면을 깨뜨리지 않았는가

구조 전환이 `:feature:room`을 건드리므로 **기존 두 화면을 반드시 다시 본다.**

| # | 확인 | 근거 |
|---|---|---|
| 1 | 방 리스트 `Peek`/`Half`/`Full` 3단이 그대로 동작 | room-list spec |
| 2 | 방 리스트 ↔ 방 상세 전환에서 지도 카메라가 리셋되지 않는다 | `RoomNavigation.kt` KDoc |
| 3 | 방 상세에서 바텀 네비게이션이 숨는다 | room-detail FR-003 |
| 4 | 공동방 0개일 때 넛지 팝업이 뜨고, 그 아래 지도가 하얗게 남지 않는다 | `RoomListUiState.isNudgeSheetVisible` KDoc의 실기기 결함 |
| 5 | 공동방 생성 직후 지도가 정상 | 커밋 `6778d31a` |
| 6 | 홈 카드 덱의 스와이프·액션 메뉴가 그대로 | home spec |

**4·5번은 이 저장소가 실제로 겪은 결함이다.** `LocalBottomNavVisibility` 판정식에 조건을 더하는 변경([place-detail-main-contract.md §2.5](./contracts/place-detail-main-contract.md))이 그 자리를 직접 건드리므로 반드시 확인한다.
