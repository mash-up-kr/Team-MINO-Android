# Pull Request 컨벤션

실제 본문 스켈레톤은 [`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md)에 있다. 웹 UI·`gh pr create`·`/pr` 커맨드 모두 이 파일을 기반으로 한다. 본 문서는 **작성 규칙·섹션별 작성 주체·메타 설정** 만을 정의한다.

## 제목 포맷

**이슈 제목을 그대로 PR 제목으로 사용한다.** prefix·번호 표기 없이 간결하게.

- ✅ `로그인 API 연동`
- ✅ `디자인 시스템 KDoc 작성`
- ❌ `feat: 로그인 API 연동`
- ❌ `[#12] 로그인 API 연동`

이슈 번호는 제목이 아닌 본문(`Closes #N`)에서 연결한다.

## base 브랜치

- **기본**: `develop`
- **예외**: `hotfix/*` → `main`, `release/*` → `main`, 기타 상황에 맞춰 조정 가능
- `/pr` 커맨드는 기본값으로 `develop`을 사용하되, 현재 브랜치·이슈 성격에 따라 다른 base가 더 맞으면 사용자에게 한 번 확인한 뒤 진행

## 이슈 연결

- **모든 PR은 `Closes #N` 형식으로 연결한다.** 머지 시 해당 이슈가 자동 닫힌다.
- 이슈 번호는 브랜치 이름(`<prefix>/<N>-<slug>`)에서 자동 추출
- 여러 이슈를 동시에 해결하는 경우 `Closes #12`, `Closes #15`와 같이 여러 줄로 표기

## 섹션별 작성 주체

| 섹션 | 작성 주체 | 내용 |
|---|---|---|
| 요약 | **Claude 자동** | 전체 변경을 2~3줄로 요약 |
| 관련 이슈 | **Claude 자동** | `Closes #N` 자동 삽입 |
| 변경 내용 | **Claude 자동** | 커밋 로그(`git log <base>..HEAD`) 기반으로 리뷰어가 읽기 좋게 정리. 필요 시 하단에 mermaid 다이어그램 자동 삽입 (아래 "Mermaid 다이어그램" 참고) |
| 주요 스크린샷 | **사용자** | UI 변경이 많다면 주요 화면 최대 3개 첨부. 없으면 "해당 없음" |
| 리뷰 포인트 | **사용자** | 특히 꼼꼼히 리뷰받고 싶은 영역 직접 기술 |
| 관련 레퍼런스 자료 | **사용자** | Figma, 디자인 시스템, 외부 문서 링크 등 |

Claude는 "사용자" 섹션은 섹션 헤더와 힌트 주석만 유지하고 내용은 채우지 않는다.

## Mermaid 다이어그램

"변경 내용" 섹션 **내부 하단**에 mermaid 코드 블록을 삽입하여 변경의 구조·흐름·상태를 시각화할 수 있다. 템플릿에는 고정 섹션을 두지 않으며, `/pr` 커맨드가 diff를 분석해 **유용하다고 판단하면 사용자 동의 없이 자동 생성**한다. 웹 UI·`gh pr create`로 만들 때는 작성자가 직접 추가해도 좋다.

### 허용 타입 (4종만)

| 타입 | 용도 |
|---|---|
| `flowchart` | 조건 분기·로직 흐름, UI 네비게이션, 파이프라인 |
| `sequenceDiagram` | API 호출 순서, 비동기 상호작용, 컴포넌트 간 메시지 흐름 |
| `classDiagram` | 새 클래스/인터페이스, 상속·의존 관계 변경 |
| `stateDiagram-v2` | ViewModel UiState 전이, 상태 머신 신규/변경 |

`erDiagram`, `gitGraph`, `pie` 등 그 외 타입은 사용하지 않는다.

### 자동 생성 기준

아래 중 하나라도 해당할 때 `/pr`이 자동 삽입:
- 새 API 호출 흐름 또는 비동기 시퀀스 2단계 이상 → `sequenceDiagram`
- 조건 분기 3갈래 이상의 로직, UI 네비게이션 변화 → `flowchart`
- 새 클래스/인터페이스 2개 이상 또는 상속·의존 관계 변경 → `classDiagram`
- 상태 전이가 명시된 sealed class/enum 신규 또는 기존 상태 머신 변경 → `stateDiagram-v2`

단순 버그 수정·리네이밍·임포트 정리·포맷팅·문서만 변경 등에는 **삽입하지 않는다**.

### 작성 가이드
- 노드/엣지 텍스트는 **간결하게**. 타입 시그니처 전체를 라벨에 붙이지 않는다.
- 한국어 라벨 사용 가능 (GitHub 렌더링 지원)
- 복잡도 상한: **노드 ≤ 15, 엣지 ≤ 20**. 초과하면 PR을 쪼갤 것을 권고
- 한 PR당 **최대 2개**

## draft 정책

PR을 draft로 생성할지 ready로 생성할지 `/pr` 실행 시 **매번 선택**한다. 기본값은 없고, 사용자가 명시적으로 고르도록 한다.

- **draft**: 작업이 아직 정리 중이거나 CI·셀프 체크를 더 돌려봐야 할 때
- **ready**: 리뷰 요청할 준비가 완료된 상태

## Assignee / 레이블 / 리뷰어

- **Assignee**: 현재 `gh` 사용자(`@me`) 자동 할당
- **레이블**:
  - **D-n 라벨**: `/pr` 커맨드가 PR 생성 직후 사용자에게 선택받아 부착한다. 수동 부착도 가능. 상세는 아래 "D-n 라벨 정책" 참조
  - **그 외 라벨**: 자동 부여하지 않음 (필요 시 수동)
- **리뷰어**: [`.github/CODEOWNERS`](../../.github/CODEOWNERS) 기반으로 **GitHub가 자동 요청**한다. `/pr` 커맨드는 `--reviewer` 옵션을 지정하지 않는다. PR 작성자 본인은 자동 제외됨.
  - 리뷰를 강제하려면 레포 설정의 Branch protection rules에서 **"Require review from Code Owners"** 를 활성화

## D-n 라벨 정책

PR의 리뷰 마감일을 `D-n` 라벨로 표기한다. `n`은 리뷰 완료까지 남은 일수.

### 사용 라벨

| 라벨 | 의미 | 색상 |
|---|---|---|
| `D-1` | 긴급 / 1일 내 리뷰 | 빨강 |
| `D-2` | 2일 내 리뷰 (**기본값**) | 주황 |
| `D-3` | 3일 내 리뷰 | 노랑 |
| `D-4` | 4일 내 리뷰 | 연녹 |

### 부착 시점

- `/pr` 커맨드 실행 시 PR 생성 직후 AskUserQuestion으로 라벨을 선택받아 부착
- 웹 UI/`gh pr edit`으로 수동 부착도 동일하게 동작
- "붙이지 않음"을 선택한 PR은 카운트다운 대상에서 제외됨

### 자동 카운트다운

[`.github/workflows/d-day-labeler.yml`](../../.github/workflows/d-day-labeler.yml)이 매일 자정(KST)에 [`naver/d-day-labeler`](https://github.com/naver/d-day-labeler) Action으로 모든 열린 PR의 `D-n` 라벨을 1씩 감소시킨다 (`D-4` → `D-3` → `D-2` → `D-1`). Draft PR은 제외(`skipDraft: true`).

## 보호 브랜치에서 실행

현재 브랜치가 `main`/`develop`인 상태에서 `/pr`을 실행하면 **경고만 출력하고 진행**한다. 차단하지 않는다. 판단은 개발자 몫.

## 원격 푸시

현재 브랜치가 원격에 없거나 뒤처져 있으면 `/pr`이 `git push -u origin <branch>`를 **자동 실행**한 뒤 PR을 생성한다.

## 중복 PR

이미 같은 브랜치로 열려 있는 PR이 있으면 **생성하지 않고** 기존 PR URL을 출력한 뒤 종료한다.
