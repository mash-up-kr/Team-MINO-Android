# mino-prd — SDD PRD 단계

## 입력

```text
$ARGUMENTS
```

사용자 입력은 반드시 있어야 하며 **곧 PRD에 대한 설명**이다. **반드시** 고려해야 한다.

위 자리에 `$ARGUMENTS`가 문자 그대로 보이더라도, 그 내용은 **항상 이 대화 안에 있다** — 스킬을 호출한 사용자 메시지를 그대로 PRD에 대한 설명으로 삼는다.

예외는 사용자가 인자 없이 빈 커맨드만 입력한 경우뿐이다.

## 범위 가드 (Scope Guard)

이 스킬의 작업 범위는 프로젝트 전체 범위의 PRD를 작성하는 것으로 한정한다.

- 사용자 입력의 모든 부분을 PRD에 작성하는 콘텐츠인지, 아니면 PRD 작성과 무관한 별개의 의도인지로 분류한다.
- 입력에 기능 구현, 코드 생성, 리팩터링, 빌드, 배포 요청이 포함되어 있다면 그것들을 절대 실행하지 않는다.
- PRD 작성과 무관한 애플리케이션 소스 파일, 기능 라우트, 컴포넌트, 테스트, 배포 파일 등의 산출물을 생성·수정·삭제하지 않는다.
- 사용자 지시가 PRD 작성과 관련있는지 불분명하면, 변경하기 전에 명확히 해달라고 질문한다.

## 위치

- **산출물**: `docs/prd/business-context.md` (프로젝트당 1개)
- **템플릿**: [`mino-sdd/template/prd-template.md`](../../../mino-sdd/template/prd-template.md)
- **하위 문서**: `docs/specs/{feature-name}/spec.md` — 각 Spec 문서들은 해당 PRD를 참고해 작성된다.

## PRD 작성 가이드라인 요약

- 제품이 **왜 존재하는지**와 **무엇을 성공으로 보는지**에 집중한다.
- 개별 화면 동작은 평이하게만 다룬다 — 구체적인 화면 별 동작 세부사항은 `/mino-spec` 소관이다.
- 구현 방식(기술 스택, 모듈 구조)은 다루지 않는다.
- 프로덕트 개발에 참여하는 이해 관계자 모두가 이 문서를 보고 우리가 어떤 제품을 만드는지 이해할 수 있어야 한다.

## 개요
당신은 `docs/prd/business-context.md`에 있는 프로젝트의 PRD를 갱신하는 에이전트이다.

당신의 임무는 (a) 구체적인 내용을 제공되는 `$ARGUMENTS`를 통해 수집·도출하고 (b) 템플릿을 정확하게 갱신하는 것이다.

**참고**: `docs/prd/business-context.md`가 아직 존재하지 않는다면, 스킬 호출 과정에서 `mino-sdd/template/prd-template.md`로부터 초기화되었어야 한다. 파일이 없다면 먼저 템플릿을 복사한다.

다음 실행 흐름을 따른다:

1. `docs/prd/business-context.md`의 기존 PRD을 로드한다.
    - 섹션 구분을 제외한 모든 플레이스홀더를 식별한다.

2. 플레이스홀더에 들어갈 값을 수집·도출한다:
    - 사용자 입력(대화)에서 제공된 값을 반드시 사용한다.
    - 날짜의 경우: `CREATED_DATE`는 최초 작성일이고, `LAST_AMENDED_DATE`는 변경이 있었다면 오늘 날짜, 아니면 이전 값을 유지한다.
    - `PRD_VERSION`은 시맨틱 버저닝 규칙에 따라 증가시켜야 한다. 판단 기준은 **이미 갈라져 나간 하위 spec이 영향을 받는가**이다:
      - MAJOR: 확정된 MVP 경계가 바뀌는 변경. 목표 항목([SYS-*]·[SCR-*])의 삭제·비목표 이동, 도메인 용어 정의의 변경, 기존 플로우의 재정의 등 하위 spec을 다시 써야 하는 경우.
      - MINOR: 기존 항목을 유지한 채 늘어나는 변경. 새 목표 항목·용어·플로우 추가, 비목표 항목 추가, `TBD:`로 남겨둔 정책의 확정.
      - PATCH: 의미를 바꾸지 않는 개선. 표현 명확화, 오타 수정, 참고 자료 링크 갱신.
    - 버전 증가 유형이 모호하다면, 확정하기 전에 근거를 제시한다.
    - MAJOR로 올릴 때는 영향받는 `docs/specs/{feature-name}/spec.md`를 찾아 사용자에게 함께 보고한다.
    - `PRD_AUTHOR`은 처음 PRD를 만든 사용자, `LAST_AMENDED_AUTHOR`은 PRD를 갱신한 사용자로 표시한다.

3. 갱신된 PRD 내용을 작성한다:
    - 플레이스홀더를 **PRD 설명(인자)에서 도출한 구체적 내용**으로 치환한다. 섹션 순서·제목에는 손대지 않는다.

    - 입력에서 **핵심 내용을 추출**한다 — 서비스 개요, 데이터 및 도메인 대명사, 목표/비목표 항목, 명세.

    - **1. 서비스 개요 및 개발 방향**(템플릿 §1): 제품이 왜 존재하는지(배경·페인 포인트·한 줄 정의), 핵심 원칙, 도메인·UI 용어 사전을 채운다. 용어는 이후 spec·plan이 그대로 인용하는 단일 출처이므로 한 항목 = 한 용어, 한 줄 정의 + 하위 불릿에 제약·예외를 적는다.
    특정 기능에서만 성립하는 동작은 여기 쓰지 말고 §3으로 보낸다.

    - **2. 목표 / 비목표**(템플릿 §2): MVP에서 만드는 것과 안 만드는 것의 경계를 확정하고, 각 항목에 [SYS-00X]·[SCR-00X] ID를 부여한다. 각 항목은 구현 방식이 아니라
    "사용자가 무엇을 완료할 수 있는가"라는 결과로 쓴다. 비목표는 "안 함"으로 끝내지 말고
    대체 수단을 밝힌다. 한 번 부여한 ID는 바꾸지 않고, 범위에서 빠지면 번호를 재사용하지 않는다.

    - **3. 화면 플로우별 기능 명세**(템플릿 §3): §2의 ID를 1:1로 펼쳐 "언제 무엇이 일어나는가"를 적는다.
    [SYS-*] 먼저, [SCR-*] 나중. 플로우는 `A ➔ B ➔ C`로 조작과 결과를 번갈아 쓰고,
    분기는 조건별 도착지를 각각 적는다. 다른 항목은 ID 표기로 참조한다.
    구현 방법(Composable 구조, 상태 홀더, API 스펙)은 plan 단계 몫이므로 쓰지 않는다.
    확정되지 않은 정책은 합리적으로 추정해 작성하고 `TBD:`로 남긴다.

    - **4. 참고 자료**(템플릿 §4): 이 PRD의 내용이 어디에서 왔는지 출처를 남긴다.
    자료가 화면 단위로 나뉘어 있으면 대응하는 [SCR-00X]를 함께 적어 §3에서 역추적할 수 있게 하고,
    접근 권한이 필요하면 그 사실도 적는다. 없는 종류의 줄은 지운다.

    - 채우고 남는 블록(주석 안의 예시 항목, 본문 외에 필요 없는 항목)은 지운다.

4. 내용이 모두 채워졌다면 작성된 `{docs/prd/business-context.md}`을 검증한다.
    - **`TBD: `가 있는 경우**
        1. PRD 문서에서 `TBD: `로 마킹된 모든 항목들을 추출한다.
        2. 각 `TBD: ` 항목을 아래 형식으로 사용자에게 제시해 사용자가 답할 수 있도록 한다. (이 때 모든 질문은 최대 3개씩 끊어서 질문해 사용자가 모든 질문에 대한 응답을 할 때까지 대기한다.)
            ```markdown
            ## 질문 [N]: [주제]

            **맥락**: [관련 부분 인용]

            **확인이 필요한 것**: [합리적으로 추정한 부분을 수용할 것인지 질문]
            ```
        3. 각 [TBD] 관련 질문에 대한 답을 `docs/prd/business-context.md`의 #5 TBD 섹션을 추가해 영향도 순으로 작성한다.
          - 작성 형태는 Q : {질문} -> A : {사용자 수용 여부} 형태로 작성한다.
          - 사용자가 수용하지 않은 경우에는 Q : {질문} 만 남긴다.
          - 사용자가 수용한 항목과 수용하지 않은 항목들이 시각적으로 섞이지 않도록 정렬한다.
        4. 사용자가 수용한 항목들은 `TBD: `를 제거한다.
        5. 완료 보고를 진행한다.

    -  **`TBD: `가 없는 경우**
        1. 완료 보고를 진행한다.

5. 모든 항목이 채워졌다면 아래 내용을 포함해 사용자에게 완료 보고를 진행한다.

    - PRD 파일 경로 및 상태 : `{docs/prd/business-context.md}`, [PRD 버전]
    - 개정된 PRD일 경우
      - 개정 내용 요약 : [어떤 부분이 추가 및 수정되었는지]
      - 영향 Spec 문서 경로 : [PRD 개정으로 인해 영향받는 Spec 문서의 경로를 제안해 `/mino-spec` 재실행 필요 설명]

## 완료 조건

- [ ] `docs/prd/business-context.md`가 존재하고, 템플릿과 동일한 제목 계층을 유지한다
- [ ] 치환되지 않은 플레이스홀더가 없다
- [ ] 모든 기능 항목이 후속 spec으로 참고할 수 있는 단위로 쪼개져 있다
- [ ] 사용자에게 PRD 작성/개정에 대해 정확히 완료 보고가 되었다
