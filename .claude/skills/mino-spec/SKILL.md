# mino-spec — SDD Spec 단계

## 입력

이 스킬을 호출한 메시지에서 `/mino-spec` 뒤에 사용자가 입력한 텍스트가 **곧 기능 설명**이다.

$ARGUMENTS

위 자리에 `$ARGUMENTS`가 문자 그대로 보이더라도, 그 내용은 **항상 이 대화 안에 있다** — 스킬을 호출한 사용자 메시지를 그대로 기능 설명으로 삼는다.
따라서 기능 설명을 다시 말해 달라고 요청하지 않는다. 예외는 사용자가 인자 없이 빈 커맨드만 입력한 경우뿐이다.


## 스펙 문서 작성 가이드라인 요약

- 사용자가 **무엇을** 필요로 하는지, 그리고 **왜** 필요한지에 집중한다.
- **어떻게** 구현할지는 다루지 않는다(기술 스택, API, 코드 구조 없음).
- 개발자가 아니라 비즈니스 이해관계자를 위해 작성한다.
- 명세 안에 체크리스트를 삽입하지 않는다. 그것은 별도의 커맨드가 담당한다.

### 섹션 별 요구사항

- **필수 섹션**: 모든 기능에 대해 반드시 작성해야 한다
- **선택 섹션**: 해당 기능과 관련 있을 때만 포함한다
- 적용되지 않는 섹션은 통째로 제거한다("N/A"로 남기지 않는다)

### 입력 프롬프트 유의사항

사용자 프롬프트로부터 이 명세를 작성할 때:

1. **합리적으로 추정한다**: 맥락, 업계 표준, 일반적 패턴을 사용해 빈틈을 채운다
2. **테스터처럼 생각한다**: 모호한 요구사항은 모두 "테스트 가능하고 명확한가" 체크리스트 항목에서 실패해야 한다

## 버전 규칙

`spec.md` 헤더의 **버전**은 `MAJOR.MINOR.PATCH` 시맨틱 버저닝을 따른다. 신규 작성은 항상 `1.0.0`이다.

개정 시 등급 판단 기준은 **이미 갈라져 나간 하위 문서(`plan.md`·`tasks.md`)가 영향을 받는가**이다.

- **MAJOR**: 확정된 요구사항의 경계가 바뀌는 변경. 요구사항 항목(FR-*·UX-*)의 삭제·의미 변경, 유저 시나리오의 재정의, §3 범위의 축소·확대 등 설계를 다시 해야 하는 경우.
- **MINOR**: 기존 항목을 유지한 채 늘어나는 변경. 새 요구사항·엣지 케이스·가정 추가, `[TBD]`로 남겨둔 항목의 확정.
- **PATCH**: 의미를 바꾸지 않는 개선. 표현 명확화, 오타 수정, 근거 링크 갱신.

- 등급이 모호하다면, 확정하기 전에 근거를 제시한다.
- 버전을 올릴 때는 **최종 수정일**을 오늘 날짜로 갱신한다.
- MAJOR·MINOR로 올릴 때는 같은 `{SPEC_DIR}`의 `plan.md`·`tasks.md` 존재 여부를 확인해, 재실행이 필요하다는 사실을 완료 보고에 포함한다.

헤더의 **기준 PRD 버전**은 spec 자신의 버전과 별개다. 실행할 때마다 읽어 들인 `docs/prd/business-context.md` 헤더의 버전으로 갱신하며, PRD가 없는 프로젝트면 `없음`으로 둔다. spec 개정 등급이 PATCH여도 이 값은 이번 실행에서 읽은 값으로 맞춘다. 이 값이 PRD 개정 때 어느 spec이 뒤처졌는지 판정하는 유일한 근거이므로 비워 두지 않는다.

## 작업 순서

### 1. feature 결정 · 작업 디렉터리 생성

1. 입력에서 **feature-name 후보**를 뽑는다. 기능을 대표하는 유니크한 이름이며, 한국어 입력이어도 이름은 영문 kebab-case(소문자·숫자·하이픈)로 만든다.
2. `docs/specs/{feature-name}`의 존재 여부로 **신규 작성인지 개정인지**를 가른다. 이 갈래는 이후 모든 단계에서 그대로 이어진다.
3. **확인 게이트** — 갈래에 맞는 승인을 사용자에게 받는다(`AskUserQuestion`). 승인 전에는 어떤 파일·디렉터리도 만들거나 고치지 않는다.
   - **신규 작성**: 후보 이름을 제시하고 승인을 받는다. 이름은 이후 모든 단계의 산출물 경로가 되므로, 모델이 매번 새로 지어내 흔들리는 것을 여기서 막는다.
   - **개정**: 같은 이름의 디렉터리가 이미 있다는 사실을 알리고, 기존 feature의 개정인지 이름 충돌인지 확인한다. 이름 충돌이면 다른 이름을 받아 신규 작성으로 되돌아간다.
     개정이 맞으면 위 "버전 규칙"으로 판정한 등급(MAJOR·MINOR·PATCH)과 그 근거를 함께 제시해 승인을 받는다 — 등급이 하위 문서(`plan.md`·`tasks.md`)의 재작업 범위를 결정하므로 모델이 혼자 정하지 않는다.
4. `{SPEC_DIR} = docs/specs/{feature-name}` 을 `mkdir -p`로 확보한다. 이 feature의 spec.md와 이후 단계의 모든 문서가 이 디렉터리 아래에 들어간다.

### 2. 템플릿 확보

내용을 쓰기 전에 **빈 골격부터 디스크에 놓는다.**

1. `{SPEC_FILE} = {SPEC_DIR}/spec.md`. 이후 단계는 이 경로를 편집한다.
2. **신규 작성**: [`mino-sdd/template/spec-template.md`](../../../mino-sdd/template/spec-template.md)를 `{SPEC_FILE}`로 **그대로 복사**한다(`cp`). 이 시점의 spec.md는 플레이스홀더가 남은 껍데기다.
3. **개정**: `{SPEC_FILE}`이 이미 존재하므로 **복사하지 않는다.** 기존 내용을 로드해 그 위에서 이어 쓴다 — 덮어쓰면 앞선 개정에서 확정한 내용과 §5 TBD 기록이 사라진다.

복사를 먼저 하는 이유는 MASC 대시보드가 업로드 시 spec 구조를 하드 차단으로 검증하기 때문이다. 복사본을 제자리 편집하면 섹션 순서·제목의 템플릿 일치가 절차상 보장되고, 골격을 기억으로 재생성할 때 생기는 드리프트가 사라진다.

### 3. **존재하는 경우**: 프로젝트 전반적인 기획 PRD를 확인하기 위해 `docs/prd/business-context.md`를 로드한다.

내용 채우기 섹션은 PRD에서 해당 Spec과 관련된 내용을 사전 확인해 기반하여 진행한다.

로드하면서 **PRD 헤더의 버전을 기억해 둔다.** 4단계에서 헤더의 **기준 PRD 버전**으로 기록한다. PRD가 없으면 `없음`을 쓴다.

개정이라면 헤더에 이미 적힌 기준 PRD 버전과 방금 읽은 PRD 버전을 비교한다. 값이 다르면 그 사이에 PRD가 개정되었다는 뜻이므로, **바뀐 PRD 항목이 이 spec의 요구사항과 어긋나지 않는지 확인하고 어긋나는 부분을 사용자에게 보고한다.** 이번 입력이 지목하지 않은 부분까지 임의로 고치지는 않는다 — 반영할지는 사용자가 정한다.

### 4. 내용 채우기

`{SPEC_FILE}`을 **제자리 편집**한다. 새 파일을 쓰거나 전체를 덮어쓰지 않는다.

- 플레이스홀더를 **기능 설명(인자)에서 도출한 구체적 내용**으로 치환한다. 섹션 순서·제목에는 손대지 않는다.
- 개정이라면 입력이 지목한 부분만 고치고 나머지는 그대로 둔다. 이미 확정된 요구사항을 근거 없이 다시 쓰지 않는다.
- 어떤 섹션이 필수이고 무엇을 미정으로 표기하는지는 템플릿이 정한다.
- 불분명한 부분은:
  - 스펙의 맥락과 업계 표준에 근거해 합리적으로 추정하고, 추정한 것은 §4 가정에 기록한다.
  - 다음 중 하나에 해당할 때만 `[TBD: 구체적 질문]`으로 표시한다:
    - 그 선택이 기능 범위나 사용자 경험에 큰 영향을 미치는 경우
    - 명확한 정책으로 서술되어 있지 않아 서로 다른 결론을 갖는 합리적 해석이 여러 개 존재하는 경우
    - 합리적인 기본값이 존재하지 않는 경우
  - `[TBD]` 마커는 영향도 순으로 남긴다 — 사용자 경험 > 범위 > 보안·프라이버시 > 기술 세부사항.

1. 입력에서 **핵심 개념을 추출**한다 — 행위자, 행동, 데이터, 제약.
2. **헤더**를 채운다 — 기능 이름, 대상 스펙 경로(`{SPEC_DIR}`), 기준 PRD 버전(3단계에서 읽은 값), 최초 작성일, 최종 수정일, 상태, 버전, 입력. 버전은 위 "버전 규칙"을 따른다.
   - **신규 작성**: 버전은 `1.0.0`, 최종 수정일은 최초 작성일과 같다.
   - **개정**: 1단계에서 승인받은 등급으로 버전을 올리고, 최종 수정일을 오늘 날짜로 갱신한다. 최초 작성일은 그대로 둔다.
3. **유저 시나리오**(템플릿 §1)를 채운다. 화면 없는 작업이면 "사용자"를 호출자로 바꿔 같은 구조로 쓴다. 흐름을 정할 근거가 입력에 없으면 지어내지 말고 사용자에게 되묻는다.
4. **요구사항**(템플릿 §2)을 생성한다. 각 요구사항은 테스트 가능해야 한다 — 그 문장만 읽고 통과·실패를 판정할 수 있어야 한다. 명시되지 않은 세부사항에는 합리적인 기본값을 쓰고, 그 가정은 §4에 기록한다.
5. **범위**(템플릿 §3)를 정의한다. 측정 가능하고 기술 중립적인 결과로 쓴다. 정량 지표(시간·성능·처리량)와 정성 지표(사용자 만족·작업 완수)를 모두 포함하고, 각 기준은 구현 세부사항 없이도 검증 가능해야 한다.
6. **가정**(템플릿 §4)을 채운다 — 위 판정 기준과 4에서 기본값으로 정한 것들이 여기 모인다.
7. 채우고 남는 예시 블록(쓰지 않은 유저 플로우 골격, 주석 안의 예시 항목)은 지운다.

**완료 조건: 치환되지 않은 플레이스홀더 0건.** 하나라도 남으면 미완성이다.

### 5. 품질 검증

내용을 다 채웠으면, 다음 단계로 넘길 자격이 되는지 **체크리스트로 검증**한다.

1. **품질 체크리스트 확보**
   - `{CHECKLIST_FILE} = {SPEC_DIR}/quality/spec-checklist.md`.
   - **신규 작성**: [`mino-sdd/template/spec-checklist-template.md`](../../../mino-sdd/template/spec-checklist-template.md)를 `{CHECKLIST_FILE}`로 **그대로 복사**한다(`mkdir -p {SPEC_DIR}/quality` 후 `cp`).
   - **개정**: `{CHECKLIST_FILE}`이 이미 있으면 복사하지 않고, 체크 표시를 모두 `- [ ]`로 되돌리고 하단 문제 기록을 비운 뒤 재검증한다 — 이전 버전에 대한 통과 기록은 갱신된 spec의 근거가 되지 않는다. 파일이 없다면 신규 작성과 똑같이 복사한다.
   - 헤더를 채운다 — 기능 이름, 작성일(개정이면 이번 검증일), 대상 스펙 링크(`[spec.md](../spec.md)`), 그 spec의 버전, 상태 (검증 전에는 DRAFT)
2. **검증 수행** : 품질 기준 체크리스트를 `{SPEC_FILE}` 본문과 대조한다.
   - 체크리스트의 각 항목이 통과/실패인지 판단한다. 통과일 경우 `- [x]`로 바꾼다.
   - 발견된 문제점들은 체크리스트 가장 하단에 관련 명세 부분을 인용하여 기록한다.
3. **검증 결과 처리** (**이 단계는 `{SPEC_FILE}`을 고치지 않는다.** 발견한 문제를 `{CHECKLIST_FILE}`에 기록하는 데서 끝난다.)
   - **[TBD]가 남아있는 경우** (**이 단계에서만 `{SPEC_FILE}`을 고칠 수 있다.**)
      1. {SPEC_FILE}에서 모든 [TBD]를 추출한다.
      2. 각 [TBD]를 아래 형식으로 사용자에게 제시해 사용자가 답할 수 있도록 한다. (이 때 모든 질문은 최대 3개씩 끊어서 질문해 사용자가 모든 질문에 대한 응답을 할 때까지 대기한다.)
         ```markdown
           ## 질문 [N]: [주제]

           **맥락**: [관련 명세 부분 인용]

           **확인이 필요한 것**: [해당 [TBD] 마커에서 도출한 구체적 질문]

           **제안 답변**:

           | 선택지 | 답변 | 의미 |
           |--------|------|------|
           | A      | [첫 번째 제안 답변] | [이 선택이 기능에 갖는 의미] |
           | B      | [두 번째 제안 답변] | [이 선택이 기능에 갖는 의미] |
           | C      | [세 번째 제안 답변] | [이 선택이 기능에 갖는 의미] |
           | 직접 입력 | 직접 답변 작성 | [직접 답변을 어떻게 전달하면 되는지 설명] |

           **검토 필요 여부** : [응답 할 수 없고, 검토가 필요할 경우 `검토`로 답한다.]
           ```
      3. 각 [TBD] 관련 질문에 대한 답을 `{SPEC_FILE}`의 #5 TBD 섹션을 추가해 영향도 순으로 작성한다.
         - 작성 형태는 Q : {질문} -> A : {사용자 선택 답변} 형태로 작성한다.
         - 검토가 필요하다고 판단되는 경우에는 Q : {질문} 만 남긴다.
         - 사용자가 응답한 항목과 검토가 필요한 항목들이 시각적으로 섞이지 않도록 정렬한다.
      4. 사용자가 제공한 답변을 기반으로 각 [TBD]를 치환한다.
      5. 모든 명확화가 해소되면 검증을 다시 수행한다.
   - **([TBD]를 제외한) 실패 항목이 있는 경우** :
      1. 실패 항목과 구체 문제를 나열한다.
      2. 각 문제가 해결될 수 있도록 사용자에게 질문을 통해 명세를 갱신한다.
      3. 체크리스트가 통과될 때까지 검증을 반복한다. (최대 3회)
      4. 3회 반복하고도 실패한 항목이 있다면 체크리스트에 기록 후 사용자가 확인할 수 있도록 알린다.
   - **체크리스트의 모든 검증 항목이 통과한 경우** : 체크리스트 상태를 PASS, 대상 Spec 상태를 CREATED 로 갱신하고 완료 보고를 진행한다.
4. **품질 체크리스트 갱신** : 각 검증에 대한 반복 후, 성공/실패 여부에 따라 체크리스트 상태를 갱신한다. (PASS/FAILED)
   - PASS일 경우 완료 보고를 진행한다.
