# mino-constitution — SDD Constitution 단계

## 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력을 **반드시** 고려해야 한다(비어 있지 않은 경우).

## 범위 가드 (Scope Guard)

이 스킬의 작업 범위는 프로젝트 헌법 자체를 갱신하는 것으로 한정된다. 헌법에 의존하는 템플릿과 스킬들은 런타임에 헌법을 읽어 들이며, 여기서 수정하지 않는다.

- 사용자 입력의 모든 부분을 헌법에 작성하는 콘텐츠인지, 아니면 헌법 작성과 무관한 별개의 의도인지로 분류한다.
- 입력에 기능 구현, 코드 생성, 리팩터링, 빌드, 배포 요청이 포함되어 있다면 그것들을 절대 실행하지 않는다.
- 헌법 작성과 무관한 애플리케이션 소스 파일, 기능 라우트, 컴포넌트, 테스트, 배포 파일 등의 산출물을 생성·수정·삭제하지 않는다.
- 사용자 지시가 헌법 작성과 관련있는지 불분명하면, 변경하기 전에 명확히 해달라고 질문한다.
- 헌법 갱신을 완료한 뒤에는 각 유예된 의도에 대해 `Next Actions` 섹션을 포함한다. 원래 의도를
  나열하고, `/mino-spec` 같은 적절한 후속 스킬을 제안하되 직접 호출하지는 않는다.
- 거버넌스와 무관한 의도가 없다면 `Next Actions` 섹션은 생략한다.

## 개요(Outline)
당신은 `docs/constitution.md`에 있는 프로젝트 헌법을 갱신하는 에이전트이다.

당신의 임무는 (a) 구체적인 값을 수집·도출하고 (b) 템플릿을 정확하게 채우는 것이다.

**참고**: `docs/constitution.md`가 아직 존재하지 않는다면, 스킬 호출 과정에서 `mino-sdd/template/constitution-template.md`로부터 초기화되었어야 한다. 파일이 없다면 먼저 템플릿을 복사한다.
이 파일은 대괄호로 감싼 플레이스홀더 토큰(예: `[PROJECT_NAME]`, `[PRINCIPLE_1_NAME]`)을 포함하는 템플릿이다.

다음 실행 흐름을 따른다:

1. `docs/constitution.md`의 기존 헌장을 로드한다.
   - `[ALL_CAPS_IDENTIFIER]` 형태의 모든 플레이스홀더 토큰을 식별한다.
   **중요**: 사용자가 템플릿에 사용된 것보다 더 적거나 더 많은 원칙을 요구할 수 있다. 개수가 명시되어 있다면 그것을 존중하되 전체 템플릿 구조는 따른다. 그에 맞춰 문서를 갱신한다.

2. 플레이스홀더에 들어갈 값을 수집·도출한다:
   - 사용자 입력(대화)에서 값이 제공되면 그것을 사용한다.
   - 그렇지 않으면 기존 저장소 내의 문서화 컨텍스트(README, docs, 문서에 포함된 이전 헌장 버전 등)에서 추론한다.
   - 거버넌스 날짜의 경우: `RATIFICATION_DATE`는 최초 채택일이고(알 수 없다면 질문하거나 TODO로 표시), `LAST_AMENDED_DATE`는 변경이 있었다면 오늘 날짜, 아니면 이전 값을 유지한다.
   - `CONSTITUTION_VERSION`은 시맨틱 버저닝 규칙에 따라 증가시켜야 한다:
     - MAJOR: 하위 호환되지 않는 거버넌스/원칙의 제거 또는 재정의.
     - MINOR: 새로운 원칙/섹션 추가 또는 실질적으로 확장된 가이드.
     - PATCH: 명확화, 표현 수정, 오타 수정 등 의미를 바꾸지 않는 개선.
   - 버전 증가 유형이 모호하다면, 확정하기 전에 근거를 제시한다.
   - `RATIFICATION_AUTHOR`은 최초 제정자다. 기존 값이 있으면 보존하고, 없을 때만 채운다.
   - `LAST_AMENDED_AUTHOR`은 이번 개정을 실행한 사용자다. **기존 값을 유지하지 말고 항상** `git config user.name` 값으로 덮어쓴다. 값이 비어 있으면 사용자에게 이름을 묻는다.

3. 갱신된 헌장 내용을 작성한다:
   - 모든 플레이스홀더를 구체적인 텍스트로 치환한다(프로젝트가 아직 정의하지 않기로 선택해 의도적으로 남겨 둔 템플릿 슬롯을 제외하고는 대괄호 토큰이 남아 있으면 안 되며, 남긴 경우에는 명시적으로 근거를 밝힌다).
   - 제목 계층 구조를 보존하며, 치환이 끝난 주석은 여전히 명확한 지침을 제공하지 않는 한 제거해도 된다.
   - 각 원칙(Principle) 섹션이 다음을 갖추도록 한다: 간결한 이름 줄, 타협 불가한 규칙을 담은 문단(또는 불릿 목록), 자명하지 않다면 명시적인 근거.
   - 거버넌스(Governance) 섹션에 개정 절차, 버저닝 정책, 준수 검토 기대치가 나열되도록 한다.

4. 동기화 영향 보고서(Sync Impact Report)를 작성한다(갱신 후 헌장 파일 최상단에 HTML 주석으로 붙인다):
   - 버전 변경: 이전 → 이후
   - 수정된 원칙 목록(이름이 변경되었다면 기존 제목 → 새 제목)
   - 추가된 섹션
   - 제거된 섹션
   - 의도적으로 유예한 플레이스홀더가 있다면 후속 TODO

5. 최종 출력 전 검증:
   - 설명되지 않은 대괄호 토큰이 남아 있지 않을 것.
   - 버전 줄이 보고서와 일치할 것.
   - 날짜가 ISO 형식(YYYY-MM-DD)일 것.
   - 원칙이 선언적이고 검증 가능하며 모호한 표현이 없을 것("should"는 적절한 경우 MUST/SHOULD 근거로 대체).

6. 사용자에게 다음을 담은 최종 요약을 출력한다:
   - 새 버전과 버전 증가 근거.
   - 수동 후속 조치가 필요한 TODO 플레이스홀더 또는 유예 항목.
   - 유예된 비(非)거버넌스 의도에 대한 `Next Actions` 섹션.

포맷 및 스타일 요구사항:

- 템플릿과 정확히 동일하게 Markdown 제목을 사용한다(레벨을 올리거나 내리지 않는다).
- 긴 근거 문장은 가독성을 위해 줄바꿈한다(이상적으로는 100자 미만). 다만 어색한 줄바꿈까지 강제하지는 않는다.
- 섹션 사이에는 빈 줄 하나를 유지한다.
- 줄 끝 공백을 남기지 않는다.

사용자가 부분적인 갱신만 제공하더라도(예: 원칙 하나만 수정), 검증과 버전 결정 단계는 그대로 수행한다.

핵심 정보가 누락된 경우(예: 비준일을 정말로 알 수 없는 경우) `TODO(<FIELD_NAME>): 설명`을 삽입하고 동기화 영향 보고서의 유예 항목에 포함한다.

새 템플릿을 만들지 말고, 항상 기존 `docs/constitution.md` 파일을 대상으로 작업한다.


## 완료 조건
- [ ] `docs/constitution.md`가 존재하고, 템플릿과 동일한 제목 계층을 유지한다
- [ ] 의도적으로 유예하고 근거를 밝힌 슬롯을 제외하고 `[ALL_CAPS_IDENTIFIER]` 플레이스홀더가 남아 있지 않다
- [ ] 모든 원칙에 출처 링크와 강제력 표기가 있다
- [ ] Governance 섹션에 개정 절차, 버저닝 정책, 준수 검토 기대치가 모두 기술되어 있다
- [ ] Sync Impact Report가 헌장 파일 최상단 HTML 주석으로 작성되었고, 보고서의 버전과 본문 버전 줄이 일치한다
