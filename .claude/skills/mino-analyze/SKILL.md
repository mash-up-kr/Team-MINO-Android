# mino-analyze — SDD Analyze 단계

## 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력을 **반드시** 고려해야 한다(비어 있지 않은 경우).

위 자리에 `$ARGUMENTS`가 문자 그대로 보이더라도, 그 내용은 **항상 이 대화 안에 있다** — 스킬을 호출한 사용자 메시지를 그대로 대상 지목으로 삼는다.
인자가 없으면 `docs/specs/` 하위 디렉터리 목록을 제시해 대상을 고르게 한다(`AskUserQuestion`).

## 목표(Goal)

구현 전에 세 가지 핵심 산출물(`spec.md`, `plan.md`, `tasks.md`) 전반의 불일치, 중복, 모호성, 명세 부족 항목을 식별한다.

본문 대조에 앞서 문서 간 **버전 체인**을 먼저 확인하고, 하위 문서가 크게 뒤처져 있으면 거기서 멈춘다. 옛 버전을 근거로 쓰인 문서를 최신 문서와 맞대 봐야 나오는 것은 재실행하면 사라질 허수이기 때문이다.

이 스킬은 `/mino-task`가 완전한 `tasks.md`를 성공적으로 생성한 이후에만 실행해야 한다.

## 동작 제약(Operating Constraints)

**엄격한 읽기 전용**: 어떤 파일도 수정해서는 **안 된다**. 구조화된 분석 보고서를 출력한다. 선택적 개선 계획을 제안할 수 있다(후속 편집 커맨드를 수동으로 호출하기 전에 사용자가 명시적으로 승인해야 한다).

**헌법의 권위**: 프로젝트 헌법(`docs/constitution.md`)은 이 분석 범위 안에서 **타협 불가**하다. 헌법 충돌은 자동으로 CRITICAL이며, 원칙을 희석하거나 재해석하거나 조용히 무시하는 것이 아니라 spec, plan, tasks를 조정해야 한다. 원칙 자체를 바꿔야 한다면, 그것은 `/mino-analyze` 밖에서 별도의 명시적인 헌법 갱신으로 이루어져야 한다.

## 실행 단계(Execution Steps)

### 1. 분석 컨텍스트 초기화

아래 세 가지 핵심 산출물을 **반드시** 얻는다.
- SPEC = `{SPEC_DIR}/spec.md`
- PLAN = `{SPEC_DIR}/plan.md`
- TASKS = `{SPEC_DIR}/tasks.md`

필수 산출물이 하나라도 없으면 오류 메시지와 함께 중단한다(누락된 선행 커맨드를 실행하도록 사용자에게 안내한다).

버전 대조에만 쓰는 선택 산출물도 확인한다(없으면 없는 대로 진행한다. 헤더만 읽는다).
- PRD = `docs/prd/business-context.md`
- CHECKLIST = `{SPEC_DIR}/quality/spec-checklist.md`

### 2. 버전 체인 대조

**각 문서의 헤더만 읽어** 상위 문서의 **버전**과 하위 문서가 적어 둔 **기준 버전**을 맞춰 본다. 본문 대조에 들어가기 전에 먼저 수행한다 — 하위 문서가 뒤처져 있으면 이후 단계에서 나오는 불일치 상당수가 "잘못 쓴 것"이 아니라 "옛 버전을 근거로 쓴 것"이고, 처방이 달라지기 때문이다.

대조할 짝(상위 문서 버전 → 하위 문서의 기준 버전 필드):

| 상위 | 하위 | 하위의 필드 |
|---|---|---|
| `docs/prd/business-context.md` 버전 | `spec.md` | **기준 PRD 버전** (PRD가 없는 프로젝트면 `없음`이 정상) |
| `spec.md` 버전 | `plan.md` | **기준 spec 버전** |
| `plan.md` 버전 | `tasks.md` | **기준 plan 버전** |
| `spec.md` 버전 | `{SPEC_DIR}/quality/spec-checklist.md` | **대상 스펙**의 버전 (파일이 있는 경우) |

`research.md`·`data-model.md`·`contracts/`·`quickstart.md`는 독자 버전을 갖지 않는 `plan.md` 부속 문서이므로 대조 대상이 아니다.

**PRD 행은 보고하되 게이트로 삼지 않는다.** PRD는 프로젝트 전체 범위라 다른 feature의 개정으로도 버전이 오르고, 그 개정이 이 feature와 관련 있는지는 버전 숫자만으로 판정할 수 없다. 등급은 갭 크기와 무관하게 **LOW 고정**이며, 처방은 "이 개정이 이 feature와 관련 있는지 확인하려면 `/mino-spec` 재실행" 한 줄이다. spec 헤더의 기준 PRD 버전은 `/mino-spec`이 실행할 때마다 갱신하므로, 이 값이 뒤처졌다는 것은 내용이 어긋난다는 뜻이 아니라 PRD 개정 후 `/mino-spec`을 돌린 적이 없다는 뜻이다.

판정과 심각도:

- **일치**: 통과
- **하위가 MAJOR만큼 뒤처짐**: CRITICAL — 근거 문서가 통째로 바뀐 상태다. 하위 단계를 재실행하기 전에는 본문 분석 결과를 신뢰할 수 없다
- **MINOR만큼 뒤처짐**: HIGH — 추가·변경된 요구사항이 하위 문서에 반영되지 않았을 수 있다
- **PATCH만큼 뒤처짐**: MEDIUM — 문구 수준 개정일 가능성이 높다. 재실행 권고에 그친다
- **기준 버전이 상위 문서 버전보다 높음**: CRITICAL — 존재할 수 없는 값이다(수기 편집·복사 실수). 사람이 확인해야 한다
- **기준 버전 필드가 비었거나 플레이스홀더(`[1.0.0]` 등) 그대로**: HIGH — 최신성을 판정할 근거 자체가 없다
- **버전은 일치하지만 하위 문서의 최종 수정일이 상위 문서보다 이름**: MEDIUM — 상위 개정 시 버전 갱신이 누락되었을 수 있다는 신호다. 단정하지 말고 확인을 요청한다

`tasks.md`에 **폐기된 작업** 섹션이 있으면, 폐기 사유가 지목한 plan 버전이 `tasks.md`의 기준 plan 버전보다 높은지도 본다. 높다면 헤더가 갱신되지 않은 것이므로 HIGH로 보고한다.

이 단계의 결과는 7단계 보고서의 **버전 체인** 표로 항상 출력한다(이슈가 없어도 표는 낸다).

**진행 판정(게이트).** 이 대조는 보고용 정보가 아니라 이후 단계를 진행할지 정하는 관문이다. feature 폴더 안의 짝(spec→plan, plan→tasks, spec→checklist) 중 가장 심각한 뒤처짐 하나를 기준으로 판정한다. **PRD 행은 판정에서 제외한다** — 이 feature와 무관한 개정으로 진행이 막히는 것을 피하기 위함이다.

- **MAJOR 뒤처짐 또는 기준 버전이 상위보다 높은 경우**: **여기서 중단한다.** 3단계 이후를 실행하지 않고, 버전 체인 표와 재실행 순서(8단계의 재실행 안내)만 출력한다. 본문을 대조해 봐야 재실행하면 문서가 바뀌므로, 발견 표는 대부분 지연이 만든 허수가 된다. 사용자에게 재실행 후 `/mino-analyze`를 다시 돌리라고 안내하고 끝낸다.
- **MINOR 뒤처짐 또는 기준 버전 필드가 비어 판정 불가한 경우**: 버전 체인 표를 먼저 보여 준 뒤 `AskUserQuestion`으로 어떻게 할지 묻는다 — "지금 중단하고 뒤처진 단계를 재실행한다"(권장) / "지연을 감안하고 본문 분석을 계속한다". 계속을 택하면 3단계로 진행하되, 이후 발견 표의 Notes에 어느 문서가 뒤처진 상태에서 나온 발견인지 표시하고, 보고서 서두에 이 분석이 뒤처진 문서를 포함해 수행되었음을 한 줄로 명시한다.
- **PATCH 뒤처짐, 최종 수정일 역전, 일치**: 그대로 3단계로 진행한다. 뒤처짐은 발견 표에 기록만 한다.

중단하는 경우에도 **파일은 수정하지 않으며**, 하위 단계를 대신 재실행하지도 않는다. 재실행 여부는 사용자가 정한다.

### 3. 산출물 컨텍스트 로드 (점진적 공개)

각 산출물에서 최소한으로 필요한 컨텍스트만 로드한다:

**spec.md에서:**

- 유저 시나리오
- 기능 요구사항
- 핵심 UX 규칙
- 성공 기준(측정 가능한 결과 — 예: 성능, 보안, 가용성, 사용자 성공, 비즈니스 영향)
- 엣지 케이스(존재하는 경우)

**plan.md에서:**

- 아키텍처/스택 선택
- 데이터 모델 참조
- 단계(Phases)
- 기술적 제약

**tasks.md에서:**

- 작업 ID
- 설명
- 단계 그룹핑
- 병렬 마커 [P]
- 참조된 파일 경로

**헌법에서:**

- 원칙 검증을 위해 `docs/constitution.md`를 로드한다

### 4. 의미 모델 구축

내부 표현을 생성한다(원본 산출물을 출력에 포함하지 않는다):

- **요구사항 인벤토리**: 각 기능 요구사항(FR-###), 핵심 UX 규칙(UX-###), 성공 기준(SC-###)에 대해 안정적인 키를 기록한다. 명시적인 FR-/UX-/SC- 식별자가 있으면 이를 기본 키로 사용하고, 가독성을 위해 명령형 구문 슬러그를 함께 도출해도 된다(예: "User can upload file" → `user-can-upload-file`). 성공 기준 항목은 구축 가능한 작업이 필요한 것만 포함하고(예: 부하 테스트 인프라, 보안 감사 도구), 출시 이후의 결과 지표나 비즈니스 KPI(예: "지원 티켓 50% 감소")는 제외한다.
- **유저 시나리오/행동 인벤토리**: 테스트 시나리오를 갖춘 개별 사용자 행동
- **작업 커버리지 매핑**: 각 작업을 하나 이상의 요구사항 또는 스토리에 매핑한다(키워드 추론 또는 ID·핵심 문구 같은 명시적 참조 패턴 사용)
- **헌법 규칙 집합**: 원칙 이름과 MUST/SHOULD 규범 진술을 추출한다

### 5. 탐지 패스(토큰 효율적 분석)

신호가 강한 발견에 집중한다. 총 50개 발견으로 제한하고, 나머지는 초과 요약에 모은다.

#### A. 중복 탐지

- 거의 중복되는 요구사항을 식별한다
- 품질이 낮은 표현은 통합 대상으로 표시한다

#### B. 모호성 탐지

- 측정 가능한 기준이 없는 모호한 형용사(빠른, 확장 가능한, 안전한, 직관적인, 견고한)를 표시한다
- 해소되지 않은 플레이스홀더(TODO, TBD, ???, `<placeholder>` 등)를 표시한다

#### C. 명세 부족

- 동사는 있지만 목적어나 측정 가능한 결과가 빠진 요구사항
- 인수 기준과 정렬되지 않은 사용자 스토리
- spec/plan에 정의되지 않은 파일이나 컴포넌트를 참조하는 작업

#### D. 헌법 정합성

- MUST 원칙과 충돌하는 요구사항 또는 계획 요소
- 헌법이 요구하는 섹션이나 품질 게이트의 누락

#### E. 커버리지 공백

- 연결된 작업이 하나도 없는 요구사항
- 매핑된 요구사항/스토리가 없는 작업
- 구축 가능한 작업이 필요한 성공 기준(성능, 보안, 가용성)이 작업에 반영되지 않음

#### F. 비일관성

- 용어 표류(같은 개념이 파일마다 다르게 불림)
- plan에는 참조되지만 spec에는 없는 데이터 엔티티(또는 그 반대)
- 작업 순서 모순(예: 의존성 표기 없이 기반 셋업 작업보다 통합 작업이 앞서는 경우)
- 상충하는 요구사항(예: 한쪽은 Next.js를 요구하고 다른 쪽은 Vue를 명시)

### 6. 심각도 지정

다음 휴리스틱으로 발견의 우선순위를 정한다:

- **CRITICAL**: 헌법의 MUST 위반, 핵심 명세 산출물 누락, 기본 기능을 가로막는 커버리지 0 요구사항
- **HIGH**: 중복되거나 상충하는 요구사항, 모호한 보안/성능 속성, 테스트 불가능한 인수 기준
- **MEDIUM**: 용어 표류, 비기능 작업 커버리지 누락, 명세가 부족한 엣지 케이스
- **LOW**: 스타일/표현 개선, 실행 순서에 영향이 없는 사소한 중복

### 7. 간결한 분석 보고서 작성

다음 구조의 Markdown 보고서를 출력한다(파일 쓰기 없음).

### 8. 다음 행동 제시

보고서 끝에 간결한 Next Actions 블록을 출력한다:

- 버전 체인 뒤처짐이 있다면 **가장 위에** 둔다. 뒤처진 지점부터 아래로 순서대로 재실행해야 한다고 안내한다(plan이 뒤처졌다면 `/mino-plan` → `/mino-task`, tasks만 뒤처졌다면 `/mino-task`, spec-checklist가 뒤처졌다면 지금 spec이 품질 검증을 거치지 않은 상태이므로 `/mino-spec` 재실행). MAJOR·MINOR는 재실행 필수, PATCH는 권고로 구분해 적는다
- spec의 기준 PRD 버전이 뒤처졌다면 재실행 안내 아래에 한 줄로만 덧붙인다 — 진행을 막지 않으며, PRD 개정이 이 feature와 관련 있는지 확인하려면 `/mino-spec`을 다시 돌리라는 선택지로 제시한다
- 2단계 게이트에서 중단했다면 이 재실행 안내가 유일한 다음 행동이다. 재실행을 마친 뒤 `/mino-analyze`를 다시 실행해야 본문 분석을 받을 수 있다고 덧붙인다
- CRITICAL 이슈가 있다면: `/mino-implement` 전에 해결할 것을 권고
- LOW/MEDIUM만 있다면: 진행해도 되지만 개선 제안을 제공

### 9. 개선 제안 제공

사용자에게 묻는다: "상위 N개 이슈에 대해 구체적인 수정 편집안을 제안해 드릴까요?" (자동으로 적용하지 **말 것**.)

## 보고 원칙

- **결정적 결과**: 변경 없이 다시 실행하면 동일한 ID와 개수가 나와야 한다
- **버전 체인은 헤더에 적힌 값만으로 판정한다**: 본문을 훑어 최신 여부를 추측하지 않는다. 값이 없으면 "판정 불가"로 보고한다
- **누락된 섹션을 지어내지 않는다**: 없다면 없다고 정확히 보고한다
- **망라적 규칙보다 예시를 쓴다**: 일반적 패턴이 아니라 구체적 사례를 인용한다
- **이슈가 0건이어도 매끄럽게 보고한다**: 커버리지 통계와 함께 성공 보고서를 출력한다
