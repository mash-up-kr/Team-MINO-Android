# mino-task — SDD Task 단계

## 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력을 **반드시** 고려해야 한다(비어 있지 않은 경우).

위 자리에 `$ARGUMENTS`가 문자 그대로 보이더라도, 그 내용은 **항상 이 대화 안에 있다** — 스킬을 호출한 사용자 메시지를 그대로 대상 지목으로 삼는다.
인자가 없으면 `docs/specs/` 하위 디렉터리 목록을 제시해 대상을 고르게 한다(`AskUserQuestion`).

**분해의 입력은 `plan.md`이고, `spec.md`는 커버리지 검증의 기준이다.** 사용자가 함께 적은 보충 설명은 분해 순서·크기 판단의 힌트로 쓰되, plan에 없는 작업을 만들지 않는다.

## 범위 가드 (Scope Guard)

이 스킬의 작업 범위는 `{SPEC_DIR}/tasks.md` 작성으로 한정한다.

- 이 단계에서는 구현하지 않는다. 애플리케이션 소스, Gradle 스크립트, 리소스, 테스트 파일을 만들거나 고치지 않는다. 기존 코드는 **읽기만** 한다.
- `spec.md`·`plan.md`는 **절대 고치지 않는다.**
- 규약 문서(`docs/conventions/`·`docs/architecture/`)와 헌법을 고치지 않는다. 규약과 설계가 충돌하면 작업 목록으로 봉합하지 말고 보고한다.
- 규약·설계 내용을 작업 항목 본문으로 다시 풀어쓰지 않는다 — 링크와 섹션 번호로 지목한다.


## 작업 목록 작성 가이드라인 요약

- plan의 **어떻게**를 **무엇을 어떤 순서로**로 옮기는 문서다. 설계를 새로 하지 않고, 있는 설계를 빠뜨리지 않는다.
- 독자는 이 문서의 항목 하나를 집어 바로 착수할 수 있는 개발자다. 명확한 작업 시나리오가 정의되어있어야 한다.
- 근거 없는 작업은 만들지 않는다. plan·spec에서 지목할 수 없는 항목이 생기면 그것은 설계 누락이므로 미결사항으로 남긴다.
- 체크박스는 이미 짜인 코드의 기록이다. 이 문서는 SDD 사슬에서 **유일하게 실행 상태를 담는 산출물**이므로, 다시 쓸 때 그 상태를 잃지 않는 것이 내용의 정확성만큼 중요하다.

## 개정 시 병합 규칙

기존 `tasks.md`가 있으면 새 목록을 만들어 갈아끼우지 않고 **제자리에서 병합**한다.

1. **대조**: 새로 도출한 작업 집합과 기존 작업을 하나씩 대조한다. 판단 기준은 ID가 아니라 **무엇을 어느 파일에 만드는가**이다.
2. **유지**: 의미가 그대로인 작업은 **ID와 체크 상태를 손대지 않는다.** 설명 문구를 다듬는 것은 허용하되, 대상 파일이나 산출물이 달라졌다면 그것은 같은 작업이 아니다.
3. **추가**: 새로 생긴 작업은 문서에 존재하는(폐기 섹션 포함) 최대 번호 + 1부터 ID를 부여하고, 속한 Phase의 알맞은 위치에 끼워 넣는다. 문서 순서와 ID 순서가 어긋나는 것은 정상이다.
4. **삭제**: 없어진 작업이 미착수(`- [ ]`)면 그냥 지운다. 완료(`- [x]`)면 지우지 말고 **"폐기된 작업" 섹션으로 옮긴다** — 이미 코드가 들어갔다는 뜻이므로 폐기 사유와 정리해야 할 범위를 함께 적는다.
5. **ID 재사용 금지**: 지우거나 폐기한 번호는 다시 쓰지 않는다.
6. **부수 섹션 갱신**: 작업 집합이 바뀌었으면 "의존성 및 실행 순서", 병렬 실행 예시, 구현 전략도 함께 맞춘다.

## 개요(Outline)

1. **셋업 · 신규/개정 판별**: `{SPEC_DIR}/tasks.md`의 존재 여부로 **신규 작성인지 개정인지**를 가른다. 이 갈래는 이후 모든 단계에서 그대로 이어진다.
    - **신규 작성**: 내용을 쓰기 전에 **빈 골격부터 디스크에 놓는다.** [`mino-sdd/template/tasks-template.md`](../../../mino-sdd/template/tasks-template.md)를 `{SPEC_DIR}/tasks.md`로 **그대로 복사**한다(`cp`). 이 시점의 tasks.md는 플레이스홀더가 남은 껍데기다.
    - **개정**: `{SPEC_DIR}/tasks.md`가 이미 존재하므로 **절대 복사하지 않는다.** 덮어쓰면 체크 상태가 통째로 소실된다. 기존 내용을 로드해 위 "개정 시 병합 규칙"에 따라 제자리 편집한다.

2. **설계 문서 로드**: SPEC_DIR에서 다음을 읽는다:
   - **필수**: plan.md(기술 스택, 라이브러리, 구조 — 헤더의 **버전**도 함께 읽어 둔다), spec.md(사용자 스토리),
   - **선택**: data-model.md(엔티티), contracts/(인터페이스 계약), research.md(결정 사항), quickstart.md(테스트 시나리오)
   - **존재하는 경우**: 프로젝트 원칙과 거버넌스 제약을 확인하기 위해 `docs/constitution.md`를 로드한다
   - 참고: 모든 프로젝트가 모든 문서를 갖고 있지는 않다. 사용 가능한 문서를 기준으로 작업을 생성한다.

3. **작업 생성 워크플로 실행**:
   - 사용자 스토리 단위로 조직된 작업을 생성한다(아래 "작업 생성 규칙" 섹션 참고)
   - 사용자 스토리 완료 순서를 보여주는 의존성 그래프를 생성한다
   - 사용자 스토리별 병렬 실행 예시를 만든다
   - 작업 완전성을 검증한다(각 사용자 스토리가 필요한 작업을 모두 갖고 있으며 독립적으로 테스트 가능한지)

4. **tasks.md 작성**: 다음 내용을 채운다:
   - 헤더 — 기능 이름(plan.md에서 가져온다), 대상 스펙 경로(`{SPEC_DIR}`), **기준 plan 버전**(2단계에서 읽은 `plan.md` 헤더의 버전), 최초 작성일, 최종 수정일
     - **신규 작성**: 최종 수정일은 최초 작성일과 같다.
     - **개정**: 최종 수정일만 오늘 날짜로 갱신하고, 최초 작성일은 그대로 둔다.
   - 각 단계의 작업 — 단계 구분은 아래 "단계 구조"를 따르고, 각 작업은 "체크리스트 형식"을 엄격히 지킨다
   - 각 단계에 포함할 것: 스토리 목표, 독립 테스트 기준, (요청된 경우) 테스트, 구현 작업
   - 스토리 완료 순서를 보여주는 의존성(Dependencies) 섹션
   - 스토리별 병렬 실행 예시
   - 구현 전략 섹션

## 완료 보고(Completion Report)

생성된 tasks.md의 경로와 요약을 출력한다:
- tasks.md 경로 및 기준 plan 버전 : `{SPEC_DIR}/tasks.md`, [plan 버전]
- 전체 작업 개수
- 사용자 스토리별 작업 개수
- 식별된 병렬 처리 기회
- 각 스토리의 독립 테스트 기준
- 형식 검증: 모든 작업이 체크리스트 형식(체크박스, ID, 라벨, 파일 경로)을 따르는지 확인
- 개정인 경우 — 유지·추가·삭제·폐기된 작업 개수와, 폐기가 있다면 그 사유 및 정리해야 할 코드 범위

### 다음 단계 안내

요약 끝에 다음 두 갈래를 제시한다.

- `/mino-analyze` — spec·plan·tasks 교차 검증(선택). 읽기 전용이며 파일을 고치지 않는다.
- `/mino-implement` — 구현 착수.

미결 사항이나 커버리지 공백을 하나라도 기록했다면 `/mino-analyze`를 먼저 권한다.

## 작업 생성 규칙

**매우 중요**: 독립적인 구현과 테스트가 가능하도록 작업은 **반드시** 사용자 스토리 단위로 조직해야 한다.

tasks.md는 즉시 실행 가능해야 한다. 각 작업은 담당자가 추가 컨텍스트 없이도 완료할 수 있을 만큼 **구체적**이어야 한다.

**테스트는 선택 사항**: 기능 명세에 명시적으로 요청되었거나 사용자가 TDD 방식을 요청한 경우에만 테스트 작업을 생성한다.

### 체크리스트 형식(필수)

모든 작업은 다음 형식을 엄격히 따라야 한다:

```text
- [ ] [TaskID] [P?] [Story?] Description with file path
```

**형식 구성 요소**:

1. **체크박스**: 항상 `- [ ]`(마크다운 체크박스)로 시작한다
2. **작업 ID**: `T` + 세 자리 번호(T001, T002, T003...). 신규 작성 시에는 실행 순서대로 부여한다. **한 번 부여한 ID는 바꾸지 않고, 지운 번호는 재사용하지 않는다** — 개정 후에도 T014가 계속 같은 작업을 가리켜야 커밋 메시지나 대화에서의 인용이 깨지지 않는다. 그래서 개정을 거치면 문서 순서와 ID 순서가 어긋날 수 있고, 실행 순서는 Phase 순서와 "의존성" 섹션이 말한다.
3. **[P] 마커**: 작업이 병렬화 가능한 경우에만 포함한다(서로 다른 파일이고, 완료되지 않은 작업에 의존하지 않음)
4. **[Story] 라벨**: 사용자 스토리 단계의 작업에만 필수
   - 형식: [US1], [US2], [US3] 등(spec.md의 사용자 스토리에 대응)
   - 셋업 단계: 스토리 라벨 없음
   - 기반 단계: 스토리 라벨 없음
   - 사용자 스토리 단계: 스토리 라벨 필수
   - 다듬기 단계: 스토리 라벨 없음
5. **설명**: 정확한 파일 경로를 포함한 명확한 행동

**예시**:

- ✅ 올바름: `- [ ] T001 Create project structure per implementation plan`
- ✅ 올바름: `- [ ] T005 [P] Implement authentication middleware in src/middleware/auth.py`
- ✅ 올바름: `- [ ] T012 [P] [US1] Create User model in src/models/user.py`
- ✅ 올바름: `- [ ] T014 [US1] Implement UserService in src/services/user_service.py`
- ❌ 틀림: `- [ ] Create User model` (ID와 스토리 라벨 누락)
- ❌ 틀림: `T001 [US1] Create model` (체크박스 누락)
- ❌ 틀림: `- [ ] [US1] Create User model` (작업 ID 누락)
- ❌ 틀림: `- [ ] T001 [US1] Create model` (파일 경로 누락)

### Task 구성 방법

1. **사용자 스토리(spec.md)로부터** — 주된 조직 기준:
   - 관련된 모든 구성 요소를 해당 스토리에 매핑한다:
     - 그 스토리에 필요한 모델
     - 그 스토리에 필요한 서비스
     - 그 스토리에 필요한 인터페이스/UI
     - 테스트가 요청된 경우: 그 스토리에 특화된 테스트
   - 스토리 간 의존성을 표시한다(대부분의 스토리는 독립적이어야 한다)

2. **계약(Contracts)으로부터**:
   - 각 인터페이스 계약 → 그것이 지원하는 사용자 스토리에 매핑
   - 테스트가 요청된 경우: 각 인터페이스 계약 → 해당 스토리 단계에서 구현 전에 수행할 계약 테스트 작업 [P]

3. **데이터 모델로부터**:
   - 각 엔티티를 그것이 필요한 사용자 스토리(들)에 매핑
   - 엔티티가 여러 스토리에서 쓰인다면: 가장 이른 스토리나 셋업 단계에 배치
   - 관계 → 적절한 스토리 단계의 서비스 계층 작업으로

4. **셋업/인프라로부터**:
   - 공유 인프라 → 셋업 단계(Phase 1)
   - 여러 스토리가 공통으로 쓰는 기반 작업 → 기반 단계(Phase 2)
   - 스토리 특화 셋업 → 해당 스토리 단계 내부

### 단계 구조

- **Phase 1**: 셋업(프로젝트 초기화)
- **Phase 2**: 기반(사용자 스토리들이 공통으로 쓰는 인프라 — 어떤 스토리 작업이 무엇을 쓰는지 작업 줄에 드러낸다)
- **Phase 3 이후**: 확인된 모든 사용자 스토리
  - 각 스토리 내부에서: 테스트(요청된 경우) → 모델 → 서비스 → 엔드포인트 → 통합
  - 각 단계는 완결되고 독립적으로 테스트 가능한 증분이어야 한다
- **마지막 단계**: 다듬기 및 횡단 관심사
