# mino-plan — SDD Plan 단계

## 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력을 **반드시** 고려해야 한다(비어 있지 않은 경우).

위 자리에 `$ARGUMENTS`가 문자 그대로 보이더라도, 그 내용은 **항상 이 대화 안에 있다** — 스킬을 호출한 사용자 메시지를 그대로 대상 지목으로 삼는다.
인자가 없으면 `docs/specs/` 하위 디렉터리 목록을 제시해 대상을 고르게 한다.

**기본적으로 설계의 입력은 `spec.md`를 고려하되 선택적으로 대화 컨텍스트를 수용한다.** 사용자가 함께 적은 보충 설명은 설계 판단의 힌트로 쓰고, spec에 없는 요구사항은 추가하지 않는다.

## 범위 가드 (Scope Guard)

이 스킬의 작업 범위는 `{SPEC_DIR}` 아래 Plan 단계 설계 산출물 작성으로 한정한다 — `plan.md`와 Phase 0/1 산출물(`research.md`·`data-model.md`·`contracts/`·`quickstart.md`)이다. 그 밖의 파일은 만들지도 고치지도 않는다.

- 이 단계에서는 구현하지 않는다. 애플리케이션 소스, Gradle 스크립트, 리소스, 테스트 파일을 만들거나 고치지 않는다.
- `spec.md`은 **절대 고치지 않는다.**
- 규약 문서(`docs/conventions/`·`docs/architecture/`)를 고치지 않는다. 규약과 spec이 충돌하면 설계로 봉합하지 말고 보고한다.
- 설계 판단을 규약 문서 본문으로 다시 풀어쓰지 않는다 — 링크로 지목한다.

## Plan 문서 작성 가이드라인 요약

- spec의 **무엇을·왜**를 **어떻게**로 옮기는 문서다. 요구사항을 새로 만들지 않고, 있는 요구사항을 빠뜨리지 않는다.
- 독자는 이 문서만 읽고 구현을 시작할 수 있는 개발자다. 화면 하나를 어느 모듈에 어떤 상태·의도 계약으로 만드는지가 결정되어 있어야 한다.
- 코드를 쓰는 문서가 아니다. 타입 이름·시그니처·모듈 경계까지 정하고, 함수 본문은 구현 단계에 남긴다.
- 규칙의 출처는 이 저장소의 규약 문서다. 규약을 요약해 옮기지 않고 링크로 지목한다.
- 근거 없는 빈틈은 지어내지 않는다. 합리적 기본값을 쓸 수 있으면 §9 설계 가정에 기록하고, 설계가 갈리는 지점이면 `[TBD]`로 남긴다.

## 개요
당신은 `{SPEC_DIR}/plan.md`에 있는 프로젝트의 개발 계획 지침(Plan)을 갱신하는 에이전트이다.

당신의 임무는 (a) `$ARGUMENTS`로 전달되는 내용 및 연관 Spec을 통해 구현 계획을 수집·도출하고 (b) 템플릿을 정확하게 갱신하는 것이다.

**참고**: `{SPEC_DIR}/plan.md`가 아직 존재하지 않는다면, 스킬 호출 과정에서 `mino-sdd/template/plan-template.md`로부터 초기화되었어야 한다. 파일이 없다면 먼저 템플릿을 복사한다.

다음 실행 흐름을 따른다:

1. **시작** : `{SPEC_DIR}/plan.md`의 기존 내용을 로드한다.
2. **컨텍스트 로드**: FEATURE_SPEC과 `docs/constitution.md` 헌법을 읽는다.
3. **Plan 워크플로우 실행**
   - Technical Context 채우기(알 수 없는 항목은 "NEEDS CLARIFICATION"으로 표시)
   - 헌법을 바탕으로 Constitution Check 섹션 채우기
   - 게이트 평가(정당화되지 않은 위반이 있으면 ERROR)
   - Phase 0: research.md 생성(모든 NEEDS CLARIFICATION 해소)
   - Phase 1: data-model.md, contracts/, quickstart.md 생성
   - 설계 이후 Constitution Check 재평가
4. 모든 절차가 완료되면 완료 보고를 진행한다.

## 완료 보고

커맨드는 Phase 1 설계 이후 종료된다. 브랜치, Plan 경로, 생성된 산출물을 보고한다.

## Plan 워크플로우
### Phase 0 : 개요 및 리서치

1. 위의 **Technical Context에서 미확정 항목 추출**:
   - 각 NEEDS CLARIFICATION → 리서치 작업
   - 각 의존성 → 모범 사례 조사 작업
   - 각 연동 지점 → 패턴 조사 작업

2. **리서치 에이전트 생성 및 배정**:

   ```text
   Technical Context의 각 미확정 항목에 대해:
     Task: "{feature context}를 위한 {unknown} 리서치"
   각 기술 선택에 대해:
     Task: "{domain}에서 {tech}의 모범 사례 찾기"
   ```

3. 다음 형식으로 `research.md`에 **조사 결과를 통합**한다:
   - Decision: [무엇을 선택했는가]
   - Rationale: [왜 선택했는가]
   - Alternatives considered: [그 외에 무엇을 검토했는가]

**출력**: 모든 NEEDS CLARIFICATION이 해소된 research.md

### Phase 1 : 설계 및 계약

**선행 조건:** `research.md` 완료

1. **기능 명세에서 엔티티 추출** → `data-model.md`:
   - 엔티티 이름, 필드, 관계
   - 요구사항에서 도출된 검증 규칙
   - 해당하는 경우 상태 전이

2. **인터페이스 계약 정의**(프로젝트에 외부 인터페이스가 있는 경우) → `/contracts/`:
   - 프로젝트가 사용자 또는 다른 시스템에 노출하는 인터페이스를 식별한다.
   - 프로젝트 유형에 적합한 계약 형식으로 문서화한다.
   - 예: 라이브러리의 공개 API, CLI 도구의 커맨드 스키마, 웹 서비스의 엔드포인트, 파서의 문법, 애플리케이션의 UI 계약
   - 순수하게 내부용인 프로젝트(빌드 스크립트, 일회성 도구 등)라면 건너뛴다.

3. **quickstart 검증 가이드 작성** → `quickstart.md`:
   - 기능이 엔드투엔드로 동작함을 증명하는, 실행 가능한 검증 시나리오를 문서화한다.
   - 선행 조건, 셋업 커맨드, 테스트/실행 커맨드, 기대 결과를 포함한다.
   - 계약과 데이터 모델의 세부 내용은 복제하지 말고 링크나 참조로 대신한다.
   - 전체 구현 코드, model/service/controller 본문, 마이그레이션, 완전한 테스트 스위트는 포함하지 않는다.
   - 이 산출물은 검증/실행 가이드로 유지한다. 구현 세부 사항은 `tasks.md`와 구현 단계에 속한다.

**출력**: data-model.md, /contracts/*, quickstart.md

## 핵심 규칙

- 파일시스템 작업에는 절대 경로를 사용하고, 문서 내 참조에는 프로젝트 기준 상대 경로를 사용한다.
- 게이트 실패나 해소되지 않은 명확화 항목이 있으면 ERROR 처리한다.

## 완료 조건

- [ ] 브랜치, 계획 경로, 생성된 산출물과 함께 완료가 사용자에게 보고되었다
