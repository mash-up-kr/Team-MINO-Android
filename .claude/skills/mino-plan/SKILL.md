# mino-plan — SDD Plan 단계

## 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력을 **반드시** 고려해야 한다(비어 있지 않은 경우).

위 자리에 `$ARGUMENTS`가 문자 그대로 보이더라도, 그 내용은 **항상 이 대화 안에 있다** — 스킬을 호출한 사용자 메시지를 그대로 대상 지목으로 삼는다.
인자가 없으면 `docs/specs/` 하위 디렉터리 목록을 제시해 대상을 고르게 한다.

**기본적으로 설계의 입력은 `spec.md`를 고려하되 선택적으로 대화 컨텍스트를 수용한다.** 사용자가 함께 적은 보충 설명은 설계 판단의 힌트로 쓰고, spec에 없는 요구사항은 추가하지 않는다.

## 범위 가드 (Scope Guard)

이 스킬의 작업 범위는 `{SPEC_DIR}` 아래 Plan 단계 설계 산출물 작성으로 한정한다 — `plan.md`와 Phase 0/1 산출물(`research.md`·`data-model.md`·`contracts/`·`quickstart.md`)이다. 그 밖의 파일은 만들지도 고치지도 않는다.

- 이 단계에서는 구현하지 않는다. 애플리케이션 소스, Gradle 스크립트, 리소스, 테스트 파일을 만들거나 고치지 않는다.
- `spec.md`은 **절대 고치지 않는다.**
- 규약 문서(`docs/conventions/`·`docs/architecture/`)를 고치지 않는다. 규약과 spec이 충돌하면 설계로 봉합하지 말고 보고한다.
- 설계 판단을 규약 문서 본문으로 다시 풀어쓰지 않는다 — 링크로 지목한다.

## Plan 문서 작성 가이드라인 요약

- spec의 **무엇을·왜**를 **어떻게**로 옮기는 문서다. 요구사항을 새로 만들지 않고, 있는 요구사항을 빠뜨리지 않는다.
- 독자는 이 문서만 읽고 구현을 시작할 수 있는 개발자다. 화면 하나를 어느 모듈에 어떤 상태·의도 계약으로 만드는지가 결정되어 있어야 한다.
- 코드를 쓰는 문서가 아니다. 타입 이름·시그니처·모듈 경계까지 정하고, 함수 본문은 구현 단계에 남긴다.
- 규칙의 출처는 이 저장소의 규약 문서다. 규약을 요약해 옮기지 않고 링크로 지목한다.
- 근거 없는 빈틈은 지어내지 않는다. 설계가 갈리는 지점이면 `[TBD]`로 남긴다.

## 버전 규칙

`plan.md` 헤더의 **버전**은 `MAJOR.MINOR.PATCH` 시맨틱 버저닝을 따른다. 신규 작성은 항상 `1.0.0`이다.

개정 시 등급 판단 기준은 **`tasks.md`의 작업 분해가 다시 쪼개져야 하는가**이다.

- **MAJOR**: 확정된 설계의 경계가 바뀌는 변경. 모듈 경계·인터페이스 계약·상태 계약의 변경, 구조 결정의 교체, Constitution Check 게이트 판정이 뒤집히는 경우 등 작업 목록을 다시 짜야 하는 경우.
- **MINOR**: 기존 설계를 유지한 채 늘어나는 변경. 새 컴포넌트·계약·엔티티 추가, `[TBD]`로 남겨둔 설계 선택의 확정. 작업이 붙기만 하고 기존 작업의 의미는 그대로다.
- **PATCH**: 의미를 바꾸지 않는 개선. 표현 명확화, 오타 수정, 규약 문서 링크 갱신, 근거 보강.

- 등급이 모호하다면, 확정하기 전에 근거를 제시한다.
- 버전을 올릴 때는 **최종 수정일**을 오늘 날짜로 갱신하고, **최초 작성일**은 그대로 둔다.
- **기준 spec 버전**은 실행할 때마다 읽어 들인 `spec.md` 헤더의 버전으로 갱신한다. 이 값은 하위 단계가 plan의 최신성을 판정하는 근거이므로 비워 두지 않는다.

## 부속 산출물 재생성 규칙

Phase 0/1이 만드는 `research.md`·`data-model.md`·`contracts/`·`quickstart.md`는 `plan.md`에 종속된 부속 문서다. **독자 버전을 갖지 않으며**, 최신성의 근거는 `plan.md` 헤더의 버전이다.

### 등급별 처리 범위

개정 시 어디까지 다시 만들지는 등급을 따른다.

- **PATCH**: 부속 산출물을 건드리지 않는다. Phase 0/1을 다시 돌리지 않는다.
- **MINOR**: 변경이 닿는 산출물만 갱신하고 나머지는 그대로 둔다.
- **MAJOR**: 네 산출물을 모두 재검토한다.

등급은 Phase 1 이후에 확정되므로, 개정 실행에서는 먼저 영향이 닿을 산출물만 열어 진행하고, 등급 확정 후 범위가 넓어졌다면 남은 산출물을 마저 처리한다.

### 산출물별 갱신 방식

- **`research.md` — 누적한다.** 기존 항목을 덮어쓰거나 지우지 않는다.
  - 각 결정 항목에 **어느 plan 버전에서 결정되었는지**를 적는다.
  - 이전 결정이 뒤집히면 그 항목을 지우지 말고 취소선과 함께 `재검토됨(plan X.Y.Z)`으로 표시한 뒤, 새 결정을 새 항목으로 덧붙인다. 기각 이력이 남아야 다음 개정에서 같은 후보를 다시 검토하지 않는다.
  - 새 항목의 `Alternatives considered`는 이전 이력을 참조로 지목하고 본문을 복제하지 않는다.
- **`data-model.md`·`quickstart.md` — 대체한다.** 현재 상태만 담는 문서이므로 과거 형태를 남기지 않는다.
- **`contracts/` — 대체하고 삭제를 감지한다.** 이번 설계에서 사라진 계약은 파일을 지운다. 지운 계약의 이름과 사유는 완료 보고에 싣는다 — `tasks.md`가 그 계약을 구현하는 작업을 갖고 있다면, 후속 `/mino-task`가 그 작업을 폐기 처리할 근거가 된다.

### research.md와 ADR의 경계

- `research.md`: **이 feature 안에서만 유효한 선택.** 다른 feature가 따라야 할 이유가 없는 결정.
- [`docs/adr/`](../../../docs/adr/README.md): **다른 feature에도 구속력을 갖는 결정.** 라이브러리 채택, 모듈 경계, 레이어 규칙 등.

리서치 중 후자에 해당하는 결정이 나오면 `research.md`에 기록하되, **완료 보고에서 ADR 승격을 제안한다.** 이 스킬이 ADR을 직접 쓰지는 않는다.

## 개요
당신은 `{SPEC_DIR}/plan.md`에 있는 프로젝트의 개발 계획 지침(Plan)을 갱신하는 에이전트이다.

당신의 임무는 (a) `$ARGUMENTS`로 전달되는 내용 및 연관 Spec을 통해 구현 계획을 수집·도출하고 (b) 템플릿을 정확하게 갱신하는 것이다.

다음 실행 흐름을 따른다:

1. **시작 · 신규/개정 판별**: `{SPEC_DIR}/plan.md`의 존재 여부로 **신규 작성인지 개정인지**를 가른다. 이 갈래는 이후 모든 단계에서 그대로 이어진다.
   - **신규 작성**: [`mino-sdd/template/plan-template.md`](../../../mino-sdd/template/plan-template.md)를 `{SPEC_DIR}/plan.md`로 **그대로 복사**한다(`cp`). 이 시점의 plan.md는 플레이스홀더가 남은 껍데기다.
   - **개정**: `{SPEC_DIR}/plan.md`가 이미 존재하므로 **복사하지 않는다.** 기존 내용을 로드해 그 위에서 제자리 편집한다 — 덮어쓰면 앞선 개정에서 확정한 설계와 그 근거가 사라진다.
2. **컨텍스트 로드**: FEATURE_SPEC(`{SPEC_DIR}/spec.md`)과 `docs/constitution.md` 헌법을 읽는다. spec 헤더의 버전을 기억해 두었다가 5단계에서 **기준 spec 버전**으로 기록한다.
3. **Plan 워크플로우 실행**
   - Technical Context 채우기(알 수 없는 항목은 "NEEDS CLARIFICATION"으로 표시)
   - 헌법을 바탕으로 Constitution Check 섹션 채우기
   - 게이트 평가(정당화되지 않은 위반이 있으면 ERROR)
   - Phase 0: research.md 생성(모든 NEEDS CLARIFICATION 해소)
   - Phase 1: data-model.md, contracts/, quickstart.md 생성
   - 설계 이후 Constitution Check 재평가
   - 개정인 경우, 어떤 산출물을 어디까지 손댈지는 위 "부속 산출물 재생성 규칙"을 따른다
4. **등급 확정 · 승인 게이트** (개정인 경우에만): Phase 1 설계와 Constitution Check 재평가가 끝난 뒤에 수행한다. 리서치와 설계를 마치기 전에는 설계가 얼마나 흔들리는지 알 수 없으므로, 이 게이트는 spec 스킬과 달리 워크플로 **뒤**에 온다.
   - 위 "버전 규칙"으로 판정한 등급(MAJOR·MINOR·PATCH)과 그 근거를 제시한다.
   - 같은 `{SPEC_DIR}`의 `tasks.md` 존재 여부를 확인해, 이 등급이 만드는 재작업 범위를 함께 제시한다.
   - 사용자에게 승인을 받는다(`AskUserQuestion`). 승인 전에는 헤더의 버전을 올리지 않는다.
5. **헤더 갱신**: 기능 이름, 대상 스펙 경로(`{SPEC_DIR}`), 명세서 링크, 기준 spec 버전, 최초 작성일, 최종 수정일, 버전을 채운다.
   - **신규 작성**: 버전은 `1.0.0`, 최종 수정일은 최초 작성일과 같다.
   - **개정**: 4단계에서 승인받은 등급으로 버전을 올리고, 최종 수정일을 오늘 날짜로 갱신한다. 최초 작성일은 그대로 둔다.
6. 모든 절차가 완료되면 완료 보고를 진행한다.

## Plan 워크플로우
### Phase 0 : 개요 및 리서치

1. 위의 **Technical Context에서 미확정 항목 추출**:
   - 각 NEEDS CLARIFICATION → 리서치 작업
   - 각 의존성 → 모범 사례 조사 작업
   - 각 연동 지점 → 패턴 조사 작업

2. **리서치 에이전트 생성 및 배정**:

   ```text
   Technical Context의 각 미확정 항목에 대해:
     Task: "{feature context}를 위한 {unknown} 리서치"
   각 기술 선택에 대해:
     Task: "{domain}에서 {tech}의 모범 사례 찾기"
   ```

3. 다음 형식으로 `research.md`에 **조사 결과를 통합**한다:
   - Decision: [무엇을 선택했는가]
   - Rationale: [왜 선택했는가]
   - Alternatives considered: [그 외에 무엇을 검토했는가]

**출력**: 모든 NEEDS CLARIFICATION이 해소된 research.md

### Phase 1 : 설계 및 계약

**선행 조건:** `research.md` 완료

1. **기능 명세에서 엔티티 추출** → `data-model.md`:
   - 엔티티 이름, 필드, 관계
   - 요구사항에서 도출된 검증 규칙
   - 해당하는 경우 상태 전이

2. **인터페이스 계약 정의**(프로젝트에 외부 인터페이스가 있는 경우) → `/contracts/`:
   - 프로젝트가 사용자 또는 다른 시스템에 노출하는 인터페이스를 식별한다.
   - 프로젝트 유형에 적합한 계약 형식으로 문서화한다.
   - 예: 라이브러리의 공개 API, CLI 도구의 커맨드 스키마, 웹 서비스의 엔드포인트, 파서의 문법, 애플리케이션의 UI 계약
   - 순수하게 내부용인 프로젝트(빌드 스크립트, 일회성 도구 등)라면 건너뛴다.

3. **quickstart 검증 가이드 작성** → `quickstart.md`:
   - 기능이 엔드투엔드로 동작함을 증명하는, 실행 가능한 검증 시나리오를 문서화한다.
   - 선행 조건, 셋업 커맨드, 테스트/실행 커맨드, 기대 결과를 포함한다.
   - 계약과 데이터 모델의 세부 내용은 복제하지 말고 링크나 참조로 대신한다.
   - 전체 구현 코드, model/service/controller 본문, 마이그레이션, 완전한 테스트 스위트는 포함하지 않는다.
   - 이 산출물은 검증/실행 가이드로 유지한다. 구현 세부 사항은 `tasks.md`와 구현 단계에 속한다.

**출력**: data-model.md, /contracts/*, quickstart.md

## 핵심 규칙

- 파일시스템 작업에는 절대 경로를 사용하고, 문서 내 참조에는 프로젝트 기준 상대 경로를 사용한다.
- 게이트 실패나 해소되지 않은 명확화 항목이 있으면 ERROR 처리한다.

## 완료 조건

- [ ] 계획 워크플로가 실행되고 설계 산출물이 생성되었다
- [ ] 개정이라면 기존 내용을 덮어쓰지 않았고, 승인받은 등급으로 버전과 최종 수정일이 갱신되었다
- [ ] 헤더의 기준 spec 버전이 이번 실행에서 읽은 `spec.md` 버전과 일치한다

- [ ] `contracts/`에서 사라진 계약이 있다면 파일을 정리하고 완료 보고에 실었다
