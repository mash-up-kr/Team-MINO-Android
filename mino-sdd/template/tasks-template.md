## 형식: `[ID] [P?] [Story] 설명`

- **[ID]**: `T` + 세 자리 번호. **한 번 부여한 ID는 바꾸지 않고, 지운 번호는 재사용하지 않는다.** 개정으로 추가되는 작업은 문서에 존재하는(폐기 섹션 포함) 최대 번호 + 1부터 부여하므로, 개정을 거치면 문서 순서와 ID 순서는 어긋날 수 있다. 실행 순서는 Phase 순서와 "의존성 및 실행 순서" 섹션이 말한다.
- **[P]**: 병렬 실행 가능 (서로 다른 파일, 의존성 없음)
- **[Story]**: 이 작업이 속한 사용자 스토리 (예: US1, US2, US3)
- 설명에는 정확한 파일 경로를 포함할 것

## 의존성 및 실행 순서

### 단계 간 의존성

- **셋업 (Phase 1)**: 의존성 없음 - 즉시 시작 가능
- **기반 작업 (Phase 2)**: 셋업 완료에 의존 - 모든 사용자 스토리를 차단함
- **사용자 스토리 (Phase 3 이후)**: 모두 기반 작업 단계 완료에 의존
  - 이후 사용자 스토리는 병렬로 진행 가능 (인력이 충분한 경우)
  - 또는 순서대로 순차 진행
- **마무리 (마지막 단계)**: 목표한 모든 사용자 스토리의 완료에 의존

### 사용자 스토리 간 의존성

- **사용자 스토리 1**: 기반 작업(Phase 2) 이후 시작 가능 - 다른 스토리에 대한 의존성 없음
- **사용자 스토리 2**: 기반 작업(Phase 2) 이후 시작 가능 - US1 과 통합될 수 있으나 독립적으로 테스트 가능해야 함
- **사용자 스토리 3**: 기반 작업(Phase 2) 이후 시작 가능 - US1/US2 와 통합될 수 있으나 독립적으로 테스트 가능해야 함

### 각 사용자 스토리 내부

- 테스트를 포함하는 경우, 구현 전에 반드시 작성하고 실패해야 함
- 모델 → 서비스 순서
- 서비스 → 엔드포인트 순서
- 핵심 구현 → 통합 순서
- 다음으로 넘어가기 전에 해당 스토리를 완료할 것

### 병렬 처리 기회

- [P] 로 표시된 모든 셋업 작업은 병렬 실행 가능
- [P] 로 표시된 모든 기반 작업은 병렬 실행 가능 (Phase 2 내에서)
- 기반 작업 단계가 끝나면 모든 사용자 스토리를 병렬로 시작 가능 (팀 여력이 되는 경우)
- 한 사용자 스토리에서 [P] 로 표시된 모든 테스트는 병렬 실행 가능
- 한 스토리 내에서 [P] 로 표시된 모델은 병렬 실행 가능
- 서로 다른 사용자 스토리는 서로 다른 팀원이 병렬로 진행 가능

## 구현 전략

### MVP 우선 (사용자 스토리 1 만)

1. Phase 1: 셋업 완료
2. Phase 2: 기반 작업 완료 (중요 - 모든 스토리를 차단함)
3. Phase 3: 사용자 스토리 1 완료
4. **중단하고 검증**: 사용자 스토리 1 을 독립적으로 테스트
5. 준비되면 배포/데모

### 점진적 전달

1. 셋업 + 기반 작업 완료 → 기반 준비 완료
2. 사용자 스토리 1 추가 → 독립 테스트 → 배포/데모 (MVP!)
3. 사용자 스토리 2 추가 → 독립 테스트 → 배포/데모
4. 사용자 스토리 3 추가 → 독립 테스트 → 배포/데모
5. 각 스토리는 이전 스토리를 망가뜨리지 않으면서 가치를 더함

### 팀 병렬 전략

개발자가 여러 명인 경우:

1. 팀이 함께 셋업 + 기반 작업을 완료
2. 기반 작업이 끝나면:
   - 개발자 A: 사용자 스토리 1
   - 개발자 B: 사용자 스토리 2
   - 개발자 C: 사용자 스토리 3
3. 각 스토리는 독립적으로 완료되고 통합됨
